AutoMem: improve the notebook workflow, then train its operator

2 min · 1 worked example · 2026-09-21

All methods

The idea: first improve the code/prompts that govern memory use, then train a model to operate that improved workflow.

Start with the released two-model Crafter example. The agent tried to craft an item, but it lacked wood.

1. LOG: the memory model sees what just happened

The scaffold gives it the previous action, current observation, notebook file list, and logging guidance.

It can search existing notes before deciding to add:

Crafting failed because wood was missing. Collect wood before retrying.

LOG is the phase allowed to write these notebook files.

2. PLAN: the memory model consults the notebook

A fresh planning conversation contains the current observation, goals, and file list.

The memory model reads the missing-wood note. The file—not the entire LOG conversation—carries the information between phases.

3. The gameplay model chooses the real action

The accumulated PLAN consultation is handed to a separate, frozen gameplay model. It can choose a valid wood-collection action.

A world-action tag produced by the memory specialist is stripped during handoff; that specialist does not directly commit the final world action.

4. The environment responds and the cycle repeats

The new inventory becomes the next observation. LOG can update useful notes, then PLAN consults them again.

No weight-training step happens between these ordinary game actions.

5. Offline, improve the scaffold itself

Run many episodes and inspect where this workflow fails.

Another model inspects the runs and can edit the logging prompts, file organization, or other scaffold code. Evaluate the candidate on the same protocol and retain improvements.

This changes how memory is operated, not merely what one episode's note says.

6. Select good memory operations for training

Inspect the resulting traces and select useful LOG/PLAN memory behavior. The selection uses recorded responses.

Deterministic processing removes final world-action commitments from memory-specialist training targets.

7. Train and evaluate the memory specialist

Supervised training teaches the specialist those memory operations. Evaluate it alongside the still-frozen gameplay model, and revise the data or training recipe if needed.

What persists: the improved scaffold and trained specialist across episodes. The selected scaffold resets each episode's notebook.

Feedback boundary: offline optimization can inspect completed runs and scores. Runtime LOG/PLAN only sees information supplied at that point in the episode.

The defining operation is: improve the memory workflow, then train a specialist to use it. Borrowing LOG/PLAN alone leaves out AutoMem's two offline improvement loops. Their exact interfaces are below.

Open implementation details, training, and sources

All memory methods · Short overview

AutoMem is not one fixed “summarize the past” prompt. It searches for a memory scaffold, then trains a model to operate that scaffold. To make this implementable, we will first run one concrete released scaffold: Crafter v5, two-model mode. Then we will separate its two offline improvement loops from its ordinary gameplay loop.

Source pin: AutoMem at 1987b8f. Do not assume the other environments or scaffold versions have identical prompts and operations.

1. Allocate episode files and two model clients

Maintain these conceptual objects:

episode:
  previous_action
  current_observation
  notebook_directory
  environment/scaffold state
  phase debug records

memory_client:
  LOG writing + PLAN memory consultation

gameplay_client:
  frozen base model making the final world-action choice

The notebook contains actual files that survive between steps of one episode. Initial files can contain supplied game knowledge or goals. Distinguish that supplied knowledge from facts the agent discovers.

The scaffold also computes context such as inventory, threats, map information, and action prerequisites. Therefore its performance is not attributable solely to a learned text compressor.

Episode reset clears/reinitializes the notebook for that episode. The scaffold code and trained adapter survive resets; a previous episode's discoveries do not automatically become a global knowledge bank. Runtime implementation

2. Begin LOG after observing the previous action's result

Construct a fresh LOG conversation containing:

  • the action just taken;
  • the current observation;
  • the notebook's file index;
  • the scaffold's logging instructions and computed warnings.

It is not a dump of the complete episode. The memory model can request file content when the index is insufficient.

Suppose an attempted crafting action failed because a resource is missing. A useful note should preserve the failed prerequisite and current resource status, not invent a successful craft.

Illustrative operations in the release's tag syntax:

<|SEARCH|>events.txt|craft<|END|>
<|TAIL|>events.txt|8<|END|>

Return the search/tail results as the next conversation message. The memory model can now avoid duplicating an existing note.

3. Execute notebook operations and finish LOG

Common operation forms are:

Operation Meaning
READ filename Read a file
SEARCH filename|keyword Return matching content
TAIL filename|N Read the last N lines
COUNT filename|keyword Count matching occurrences
APPEND filename|text Append a record
WRITE filename|text Replace file contents
CREATE filename Create a file

The operation name appears inside <|...|> and arguments terminate at <|END|>. The selected scaffold also has specialized map handling; these common file operations are not its entire parser.

An illustrative continuation is:

<|APPEND|>events.txt|Craft attempt failed: insufficient wood. Collect wood before retrying; do not repeat the same action with unchanged inventory.<|END|>
<|DONE|>

The harness performs the write, returns its result as needed, and terminates LOG on the completion marker or its bounded iteration limit. A valid LOG phase can choose to write nothing. “Store every observation” is not the rule.

The failure signal here comes from the observed environment/scaffold context. LOG does not receive an evaluator's future optimal action sequence.

4. Start PLAN as a new conversation

PLAN receives the current observation, goals, file index, and planning guidance. It does not inherit the entire LOG chat. The files are the durable connection between the phases.

During memory consultation, the memory client can use the permitted read operations. For example:

<|SEARCH|>events.txt|insufficient<|END|>

The result tells it the last attempt failed from missing wood. The consultation context now includes both the current inventory and the relevant prior failure.

PLAN is read-only with respect to these notebook operations in the selected scaffold. If your implementation accepts an APPEND from PLAN, you changed the phase contract; it is not merely a different prompt.

5. Hand the same PLAN conversation to the gameplay model

This handoff is an important implementation detail:

  1. Run the memory model's bounded consultation loop.
  2. Append its read requests and returned file contents to PLAN.
  3. If its response contains an ACTION tag, strip that commitment before handing off. Keep the permitted consultation material.
  4. Add the handoff instruction.
  5. Call the gameplay model with the accumulated PLAN conversation.
  6. Allow that model to inspect more memory if needed, then emit the actual action.
  7. Check scaffold prerequisites; a rejected action can trigger another bounded attempt.
  8. Return the accepted action to the environment.

Thus a trained memory specialist does not replace the frozen gameplay model. A memory-model ACTION is a transition out of consultation, not direct permission to execute that world action. Two-model PLAN loop

6. Trace two complete steps

Step t:
  Environment: craft failed, insufficient wood.
  LOG memory model: search notes → append missing-wood lesson → DONE.
  PLAN memory model: read the lesson and inventory.
  PLAN gameplay model: select an available wood-collection action.
  Environment executes action.

Step t+1:
  Observation: inventory now contains more wood.
  New LOG conversation: record a meaningful inventory change if useful.
  New PLAN conversation: consult prerequisites and choose the next action.

The unchanged elements are the frozen gameplay weights and scaffold implementation. The changed elements are notebook contents and environment state. No optimizer runs between these two gameplay steps.

7. Offline loop one: improve the scaffold

Run the current scaffold on a fixed training/evaluation protocol and retain full traces, final notebook files, failures, and scores. A meta-level model inspects these artifacts and proposes edits to the scaffold code and prompts. Evaluate the candidate with the same protocol, compare it with the incumbent, and retain improvements according to the loop's scoring logic.

Examples of the search space include what the LOG prompt exposes, how files are organized, and what planning guidance the harness supplies. These are candidate design changes, not additional runtime memory entries.

To reproduce a comparison, version the candidate source, model, seed/task set, action budget, and score aggregation together. Otherwise a better score cannot be assigned to the scaffold edit. See the scaffold evolution driver.

8. Offline loop two: select trace turns and train

The data engine selects the base model's own LOG turns and the memory-consultation part of PLAN. Selection is verbatim from traces, but the training pipeline then applies explicit deterministic transformations:

  1. Unwrap code fences around operation tags.
  2. End LOG targets at DONE.
  3. Remove PLAN's final ACTION commitment.
  4. Drop final responses with no remaining memory operation.
  5. Trim text after the last memory-operation terminator.
  6. Drop residual malformed fenced examples.

That distinction matters: “verbatim selection” does not mean the final SFT target includes the world action. Selection contract and transformations

Each selected example is a conversation for one phase, including its intermediate read results where present. The training target is an assistant memory-operation response in the same context form used at deployment. Do not concatenate an episode's separate phases into one invented conversation.

Train the memory specialist with the selected data and candidate LoRA recipe; evaluate it paired with the frozen gameplay model. The outer training engine can revise the data and recipe based on measured results. This is offline selection and supervised training, not online reinforcement learning at each game step. 9. Check the three feedback boundaries

Stage What can use feedback? What changes?
Runtime LOG/PLAN Observations, action results, scaffold guidance Episode notebook and next action
Scaffold evolution Completed runs, scores, traces, files Prompts/code/tool organization
Specialist training loop Selected traces and candidate evaluation Data selection and memory-model adapter

A meta-level learner seeing full completed episodes does not imply the runtime writer sees future observations. Preserve the original per-turn prompt in selected data.

Minimum tests: LOG writes survive into PLAN; PLAN cannot silently write; the memory model's ACTION is not executed; notebook reset removes episode discoveries; trained weights survive reset; deterministic target processing removes final action commitments. These tests identify the architecture before any benchmark score does.
