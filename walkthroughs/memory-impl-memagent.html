MemAgent: carry one short note through a long document

2 min · 1 worked example · 2026-09-21

All methods

The idea: read the document in chunks. After each chunk, replace a short memory note. At the end, answer from that note.

Our invented question is: “Which acquisition happened before the director resigned?”

1. Start with the question and no memory

The document is divided into ordered chunks. The model will not receive all of them at once.

The question is already known; it tells the writer what information to retain.

2. Read chunk 1 and write the first note

The first call receives the question, an empty-memory marker, and chunk 1.

Chunk 1 says Orion was acquired in 2018. The model writes:

Orion acquired in 2018.

That output becomes the memory.

3. Read chunk 2 with the old note

The second call receives the same question, the note above, and chunk 2. Chunk 1 is no longer in its input.

Chunk 2 says the director resigned in 2020 and another acquisition happened in 2022.

4. Replace the note

The model produces a new note combining the useful old and new facts:

Orion acquired in 2018; director resigned in 2020; another acquisition followed in 2022.

The program replaces the first note with this one. It does not keep appending every note to the prompt.

If the first note had lost “Orion, 2018,” the second call would not have chunk 1 available to recover it.

5. Make a separate answer call

After the last chunk, the model receives only the question and final memory.

It answers “Orion.” The answer call is separate from writing the final note.

How does the writer learn what to keep?

During training, the system samples several complete note-and-answer sequences. A verifier scores their final answers. That outcome trains the earlier note-writing choices as well as the answer.

At ordinary runtime, the writer gets the question, previous note, and current chunk—not the answer key.

What persists: only the latest generated note between chunk calls. A new document/question starts again.

The defining operation is: old note + next chunk → replacement note. Exact prompts, budgets, and the training objective are below.

What you are building

Process a long document in sequential chunks while keeping only a bounded generated memory between calls. The question is known while memory is written. After the last chunk, answer using the question and final memory.

This is not ordinary retrieval: the basic loop does not search the document or jump backward to a forgotten chunk. It is a learned overwrite policy for text memory.

The quickstart and recurrent implementation establish the runtime interfaces.

Step 1 — Choose separate input and output budgets

Keep four quantities distinct:

question tokens
chunk tokens C
previous-memory tokens, at most M
new-memory output budget M

The complete request must fit the model window, including template overhead and generation. The quickstart uses C=5,000 and M=1,024. It also clips contexts longer than 120,000 tokens to their beginning and end before chunking. That clipping is an evaluation-script limitation, not the recurrent method's definition.

Use the intended tokenizer to split the document. Character slicing changes the token budget and can cut encoding boundaries differently.

Step 2 — Construct a fresh memory-writing request

Each write receives exactly the task-specific evidence intended for that stage:

Instruction: update the memory to retain information useful for this question
<problem>question</problem>
<memory>previous generated memory</memory>
<section>current document chunk</section>
Request: updated memory

This is a shortened explanation of the released templates, not their verbatim prompt. Use the actual template for a reproduction.

The first memory is an explicit no-previous-memory marker. Later requests contain the previous output, not all earlier prompts. The writer is expected to retain still-useful old details while adding useful new ones.

Step 3 — Replace memory, rather than append to it

def run_memagent(question, chunk_texts, generate, memory_budget):
    memory = "No previous memory"
    calls = []
    for chunk in chunk_texts:
        prompt = {
            "question": question,
            "memory": memory,
            "chunk": chunk
        }
        new_memory = generate("update_memory", prompt, memory_budget)
        calls.append((prompt, new_memory))
        memory = new_memory
    answer_input = {"question": question, "memory": memory}
    answer = generate("answer", answer_input, memory_budget)
    return answer, calls

Here generate is the model adapter: it must render the selected template and make a fresh request. It is not a hidden retrieval or memory algorithm. The actual algorithm is the construction and replacement around that call.

The local calls list is a diagnostic/training record. It must not be appended to the model input, or the test no longer measures the intended bottleneck.

An API failure should stop or retry the affected call under an explicit policy. Treating an empty failed response as a valid memory would silently erase prior information; guarding against that is recommended harness engineering.

Step 4 — Trace a question that requires two chunks

Question: “Which acquisition preceded the director's resignation?”

chunk 1:
  The company acquired Orion in 2018.
  Many unrelated events follow.

model output M1:
  Acquisition: Orion, 2018.

chunk 2:
  The director resigned in 2020.
  Another acquisition occurred in 2022.

model output M2:
  Orion acquired in 2018; director resigned in 2020;
  later acquisition in 2022. Orion precedes the resignation.

final request:
  question + M2, no document chunks

answer:
  Orion

These are invented outputs. The important dependency is that chunk 2's call cannot recover “2018” if M1 lost it. At the same time, storing every unrelated event would consume the bounded memory.

This example explains why a memory writer can produce fluent summaries yet perform poorly: it must retain the particular relation needed by the eventual answer.

Step 5 — Make the final answer call

After consuming the selected chunks, switch to the answer template. It contains the question and final memory, but no new chunk. The released template requests a boxed answer for its evaluator.

The last memory write and the answer are different generations. Do not score the memory text as though it were the final answer. In batched recurrent inference, keep sample identities straight when documents have different chunk counts.

The recurrent code tracks which conversations are final and maps conversations back to original samples. That bookkeeping is essential for training credit.

Step 6 — Train the writer with Multi-Conv DAPO

For each document/question, sample a group of complete memory-and-answer rollouts. Verify each final answer against gold. Give every generated conversation in rollout i the same advantage:

\[ A_i=R_i-\mathrm{mean}(R_1,\ldots,R_G). \]

Do not divide by group standard deviation in this paper's formulation. Optimize the token-level clipped policy objective across group, conversation, and output-token axes, normalized by the total generated-token count; it uses separate lower/upper clipping bounds and a reference-KL term in the stated objective. Each token's probability must be computed under its own actual conversation input. Paper, Section 2.2

To implement the clipping, for each generated token \(u\) compute \(\rho_u=\exp(\log\pi_\theta(u\mid x)-\log\pi_{\mathrm{old}}(u\mid x))\), where \(x\) is that token's actual within-conversation prefix. Its reward term is:

\[ \min(\rho_u A_i,\operatorname{clip}(\rho_u,1-\epsilon_{\mathrm{low}},1+\epsilon_{\mathrm{high}})A_i). \]

Sum over generated tokens across conversations and divide by their total count; subtract the configured reference-KL penalty when maximizing this objective. The input mask prevents document and question tokens from becoming policy actions.

For illustrative rewards [1, 0, 1, 0], advantages are [+0.5, -0.5, +0.5, -0.5]. M1, M2, and the final answer of the first rollout all receive +0.5. That shared signal rewards a successful chain without claiming to know which individual memory sentence was responsible.

The training record you need is:

original sample ID
rollout-group ID
for every memory/answer conversation:
  exact prompt token IDs
  generated token IDs
  generated-token mask
  sampling-policy log probabilities
  final-conversation flag
final verified reward for the rollout

Gold is used by the final verifier. It is not an extra field in the runtime memory prompt. Parameter updates improve future writing; runtime memory remains ordinary text.

Implementation and reproduction tests

Use a fake model adapter that returns M1, M2, then the answer. Assert that the second call contains M1 and chunk 2 but not chunk 1; assert that the final call contains only the question and M2. Check overwrite rather than append, token-budget enforcement, sample-ID mapping, and reward broadcast.

For training, assert that output tokens from all conversations—not only the final answer—contribute to the intended loss, while prompt tokens are masked out.

A new question/document initializes its memory again. The trained model persists, but the previous task's generated notebook does not. Running the loop with an untrained model tests the interface; reproducing the paper's learned method requires its training procedure/checkpoint.
