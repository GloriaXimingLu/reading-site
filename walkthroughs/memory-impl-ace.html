ACE: improve a shared checklist

2 min · 1 worked example · 2026-09-21

The idea: keep one shared playbook, then improve it with small changes after seeing how it was used.

Our invented task is to calculate annual revenue growth. The source contains annual figures of 100 and 120, plus a quarterly figure of 30. The playbook initially says: “Extract the two values, then calculate growth.”

1. The Generator attempts the answer

“Generator” means the LLM call doing the task. It receives the question, source context, and current playbook.

It mistakenly compares the quarterly 30 with the previous annual 100 and answers −70%. Its output identifies the playbook bullet it used and the values it compared.

2. The task checker returns feedback

For this example, the checker says “incorrect.” The program saves that first-attempt result before making any improvements.

The answer text can be hidden while this correctness feedback is still available.

3. The Reflector diagnoses the mistake

“Reflector” is a separate LLM call. It reads the attempted reasoning, used advice, and permitted feedback.

It notices the mixed periods and recommends: “Use annual figures on both sides.” It also tags the used bullet as helpful, harmful, or neutral; the program updates its counters.

4. The Generator can retry

In the inspected adaptation loop, a wrong answer can trigger bounded reflection/retry rounds.

Now the Generator uses the annual 120 and 100 and answers 20%. This is a feedback-assisted result, not a replacement for the original −70% attempt.

5. The Curator proposes one addition

“Curator” is the LLM call deciding what to keep in the playbook. At a scheduled update, it proposes:

Before calculating growth, check that both values use matching periods and units.

It returns an ADD operation, not a rewritten copy of the entire playbook.

6. The program adds the new bullet

Ordinary code assigns the new bullet an ID and appends it. Unrelated advice stays in place.

The release also probes the same question again after curation. That result is recorded separately.

7. The next task receives the improved playbook

A later calculation starts with both the original advice and the new period/unit check.

What persists: the playbook, bullet IDs, and usage counters—not the full previous conversation. Model weights stay unchanged.

The defining operation is: feedback produces a small change to a shared checklist. Full output fields, retry settings, and supported operations are below.

What you are building

Build a persistent playbook that changes through feedback on solved examples. ACE separates doing the task, diagnosing the attempt, and deciding what to retain. Those are distinct model calls, while applying IDs and counters is ordinary code.

We use the pinned ACE release. Its actual adaptation loop includes retries and a post-curation generation. That is more specific than the conceptual Generator → Reflector → Curator diagram.

Step 1 — Represent the playbook and its identifiers

A useful in-memory view is:

playbook = {
    "calc-00001": {
        "section": "Calculation checks",
        "content": "Extract the two reported values before calculating growth.",
        "helpful": 2,
        "harmful": 0
    }
}
next_global_id = 2

This is our normalized representation. The release stores a formatted text playbook, parses its lines, and renders counters with each bullet. IDs are stable references: the Generator cites them; the Reflector tags them; the counter updater locates them.

Keep a section map and a monotonically increasing global ID counter. Persist the counter with the playbook, or reconstruct it safely when resuming. Reusing an ID would attach later feedback to the wrong instruction.

The Generator receives the playbook context. Do not silently replace this with your own top-k retrieval system and call that the same condition.

Step 2 — Run the initial Generator call and preserve its score

The Generator prompt takes question, task context, playbook, and reflection. The first reflection is empty. Its structured output has:

{
  "reasoning": "The values are 120 and 100, giving a 20% increase.",
  "bullet_ids": ["calc-00001"],
  "final_answer": "20%"
}

The content is an invented visible rationale, not a record from the paper. The crucial machine-readable parts are the answer and IDs. Resolve IDs against the playbook; do not treat an invented ID as an existing bullet.

Now evaluate the answer and save it as the pre-adaptation result. Subsequent retries must not replace that result when measuring first-attempt online performance.

Step 3 — Construct the Reflector input explicitly

The Reflector receives:

Ground truth, optionally The allowed reference-answer channel

Its job is to identify the failure or effective strategy and tag used bullets as helpful, harmful, or neutral. An illustrative complete output is:

{
  "reasoning": "The arithmetic is consistent with the extracted numbers, but the periods differ.",
  "error_identification": "A quarterly amount was compared with an annual amount.",
  "root_cause_analysis": "The extraction step did not check period compatibility.",
  "correct_approach": "Find values for matching periods, then recompute the change.",
  "key_insight": "Check units and reporting periods before applying a growth formula.",
  "bullet_tags": [{"id": "calc-00001", "tag": "neutral"}]
}

These fields follow the Reflector output contract. In the growth example, extracting two values was reasonable, but their reporting periods were incomparable. A neutral tag is plausible; it is a model judgment, not a mathematically determined attribution.

Important code-level feedback detail: in this release's single-sample adaptation function, correctness is checked against the target even when the full target is hidden from the Reflector. Step 4 — Apply tags in code, then follow the retry branch

The counter update is small and deterministic:

def apply_tags(playbook, tags):
    # Teaching representation; the release parses and rewrites text lines.
    for tag in tags:
        bullet = playbook.get(tag["id"])
        if bullet is None:
            continue
        if tag["tag"] == "helpful":
            bullet["helpful"] += 1
        elif tag["tag"] == "harmful":
            bullet["harmful"] += 1
        # "neutral" leaves both counters unchanged.

Counters are evidence about usage, not a probability of correctness.

If the initial answer was wrong, the inspected loop runs bounded reflection/regeneration rounds. Each regeneration receives the reflection plus current playbook; its answer is checked again. It can stop when corrected. If the initial answer was correct, the loop still reflects to tag useful bullets. Loop and configuration

This distinction explains why an implementation cannot account for ACE as exactly three model calls per example.

Step 5 — Ask the Curator for an operation list

At the configured curation frequency, pass the current playbook, recent reflection, task context, step information, token budget, and playbook statistics to the Curator. Ask for deltas, not a replacement essay.

{
  "reasoning": "The playbook lacks a reporting-period check.",
  "operations": [
    {
      "type": "ADD",
      "section": "Calculation checks",
      "content": "Compare matching reporting periods and units before calculating growth."
    }
  ]
}

The Curator parser expects the outer reasoning and operations fields. The section name here is illustrative and assumes that section already exists.

In the pinned implementation, ADD is the supported application operation. Comments mentioning UPDATE, MERGE, or DELETE do not implement those operations. Paper-level refinement and optional analyzer behavior must not be confused with an arbitrary-edit Curator API.

Step 6 — Apply the delta without rewriting unrelated bullets

For each accepted ADD: normalize the section, choose the release's fallback section if needed, allocate the next ID, initialize both counters to zero, and append the content to that section.

def add_bullet(playbook, next_id, section, content):
    # Demonstration ID prefix; use the release's section-slug mapping in a port.
    bullet_id = f"calc-{next_id:05d}"
    if bullet_id in playbook:
        raise ValueError("duplicate bullet ID")
    playbook[bullet_id] = dict(
        section=section, content=content, helpful=0, harmful=0
    )
    return next_id + 1

After our addition:

calc-00001: original extraction advice; helpful=2, harmful=0
calc-00002: new period/unit check; helpful=0, harmful=0
next_global_id: 3

The application layer owns these updates. Optional BulletpointAnalyzer refinement can merge overlap when enabled; report its configuration instead of assuming it always runs.

Step 7 — Generate after curation, then start the next example

The release makes another generation with the revised playbook and empty reflection, and records a post-adaptation result. On the next example, the persisted playbook is the reusable artifact; the previous example's entire conversation is not copied forward.

for example:
    initial = Generator(question, context, playbook, empty reflection)
    record initial answer and correctness
    if wrong:
        repeat up to configured reflection rounds:
            reflection, tags = Reflector(attempt, used bullets, allowed feedback)
            increment helpful/harmful counters
            attempt = Generator(question, context, playbook, reflection)
            stop retrying if corrected
    else:
        reflection, tags = Reflector(initial attempt, used bullets, feedback)
        increment counters
    if curation is scheduled:
        operations = Curator(playbook, latest reflection, context, budget)
        apply supported additions with stable IDs
        optionally run configured overlap analyzer
    final_probe = Generator(question, context, playbook, empty reflection)
    record post-adaptation result separately

What you should test before calling this ACE

Use a fake Generator/Reflector/Curator with predetermined outputs. Check that the correct branch uses one reflection; the wrong branch respects its retry cap; neutral tags do not change counters; ADD does not alter unrelated content; unsupported operation types do not magically mutate the book; and pre/post scores remain distinct.

Model weights remain frozen in this textual adaptation procedure. The paper explains grow-and-refine context adaptation; this chapter spells out the chosen release's orchestration, rather than assuming all ACE implementations have identical control flow.
