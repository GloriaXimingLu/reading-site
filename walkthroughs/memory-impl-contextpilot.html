ContextPilot: save the useful fact, remove the bulky message

2 min · 1 worked example · 2026-09-21

All methods

The idea: give the agent separate tools for saving facts, changing its active context, and loading saved facts again. Train it to choose useful sequences of those actions.

Our invented question is: “Why did Mira leave after the meeting?”

1. The agent finds and reads a passage

Search identifies chunk 17. The agent opens it.

The passage says Mira left because the meeting exposed a broken agreement. The tool result becomes message 8 in the active conversation.

Chunk 17 and message 8 are different objects: one is source text; the other is its current appearance in the prompt.

2. The agent saves the important fact

It calls the structured-memory tool with a chosen key, departure, and the fact:

Mira left because of the broken agreement.

The record also points back to chunk 17 and message 8. The program stores what the agent supplied; it does not consult an answer key to invent the fact.

3. The agent removes the bulky context

After the save succeeds, it chooses a context-editing tool to shorten or replace message 8.

The next prompt gets smaller. The saved memory and original source chunk remain available.

Writing the memory and removing the message are two separate actions.

4. The agent continues investigating

It reads other evidence. It no longer needs the complete meeting passage in every call.

A compact listing tells it that a saved memory named departure exists.

5. The agent loads that memory

It selects the listed key and calls loadMemory.

The tool returns the saved fact and related records. If exact wording matters, the source pointer lets the agent read chunk 17 again.

6. The agent answers from the recovered evidence

It can now explain the departure using the relevant fact without restoring the entire old conversation.

What does the training add?

During training, the system revisits important edit decisions and samples alternatives from before the edit. For example: save the reason before deleting the passage, or delete it without saving the reason.

It scores the final answers reached after each edit and uses those results to train the earlier choices. The correct answer is available to the grader, not to the runtime memory-writing call.

The defining operation is: save a fact and its source → shrink the active prompt → load the fact later. Tool schemas and branch-credit calculations are below.

Open implementation details, training, and sources

All memory methods · Short overview

ContextPilot has two pieces to implement: a tool-using agent that can edit its context, and an RL procedure that explores alternative edits. Giving a model the tools implements the harness, not the trained policy.

The tool examples follow the inference schema at 782cbb6. The training explanation adapts Pan et al.'s paper, Sections 4.2–4.3, available under CC BY 4.0. Worked numbers and example documents are invented.

1. Separate four kinds of state

Store Example How the model accesses it
Source chunks Chunk 17 of a novel Search an index, then read a chunk
Active messages Message 8 containing a retrieved passage Already in the next prompt, unless edited
Structured memories Key departure with facts and provenance Available-memory listing, then loadMemory
Simple notes Key open_questions with a task checklist Note listing, then readNote

A memory key, source chunk ID, and message ID are not interchangeable. Deleting message 8 need not delete source chunk 17 or the memory derived from it. Without this separation, “offload context” risks deleting the only evidence.

Keep stable message IDs even when you replace bodies. Do not use a shrinking list's current offset as a historical ID in your own implementation.

2. Run the read–write–offload cycle

Suppose the question is “Why did Mira leave after the meeting?”

  1. Make source metadata and the available tools visible.
  2. The model chooses a plan and index/search operations.
  3. A search returns candidate chunk IDs; the model calls readChunk to inspect a relevant passage.
  4. The returned passage becomes an addressable tool-result message.
  5. The model decides what to preserve and calls memorize or note.
  6. The tool stores the record and reports success.
  7. The model chooses a context-editing tool for the now-redundant message.
  8. The runner modifies that message, rebuilds the active prompt and the memory listings, and calls the model again.

Do not automatically perform steps 5–7 after every read and call it the same policy. In ContextPilot these are actions the policy chooses; the data-generation harness can impose additional cleanup guidance.

3. Make a complete memory call

If message 8 contains chunk 17, an illustrative schema-complete argument object is:

{
  "key": "departure",
  "summary": "Mira left because the meeting revealed the broken agreement.",
  "content": "Mira connects her departure to the broken agreement, not to the weather.",
  "entities": "Mira: person; agreement: commitment discussed at the meeting",
  "episodes": "Departure follows the meeting; exact calendar date unspecified",
  "relations": [
    {
      "source": "meeting",
      "target": "departure",
      "relation": "precedes",
      "description": "Mira leaves after the meeting.",
      "evidence": "chunk 17, message 8"
    }
  ],
  "source": {"chunk_ids": [17], "msg_ids": [8]}
}

This object is sent to memorize. The model must derive its content from the inspected passage; the example is not a reference answer injected by the harness.

Notice that entities and episodes are strings, whereas relations and source are structured JSON. All top-level fields are required. When nothing supports a relation, use an empty array; do not fabricate a graph edge just to populate the field.

The simpler note takes key, summary, and content. Use it for a checklist that does not require the entity/event schema.

4. Edit the active context without confusing the operations

Released tool Argument contract Change
deleteContext msg_id Replace the target with a placeholder
truncateContext msg_id, start_sentence, stop_sentence Keep an inclusive sentence span in an eligible read/search result
summarizeContext msg_id, summary Replace eligible tool-result text with the model-supplied summary
compressContext msg_id, compression_rate Ask the configured compressor to retain a percentage

For this example, the model could call summarizeContext with message 8 and a short, faithful statement of the meeting evidence. The writer supplies that summary; the tool is not secretly consulting the answer key.

The automatic compressor path is different: the inspected tool implementation attempts LLMLingua-2 and has a random-word-sampling fallback when compression is unavailable. That fallback can destroy evidence. Log which path ran, and consider making fallback an explicit failure in an adapted experiment. Do not describe it as guaranteed semantic preservation. Memory tool implementation

5. Read the memory later

After unrelated investigation, the active prompt lists departure. The model sends:

{"key": "departure", "max_related": 5}

to loadMemory. It receives the requested record and directly related memories. This is key-addressed loading with graph neighbors, not an arbitrary semantic query over all notes. The schema requires a key copied from the available-memory listing.

If the returned fact is insufficient, the model can use provenance to read chunk 17 again. The source, not a second summary of the summary, is the check on disputed wording.

To edit a stored record, updateMemory supports append, overwrite, and delete modes. Its strict schema still requires all update fields; delete uses empty payload fields. Editing a memory record does not itself remove the old source message.

The paper names readMemory and searchContext, while this schema uses loadMemory and searchEngine. The paper also discusses foldHistory, absent from this inspected inference schema. Copy the schema for the implementation you are actually running.

6. Reproduce the supervised stage

Collect teacher trajectories with the same source stores, message IDs, memory schema, and editing semantics as deployment. During collection, guidance can require reading retrieved evidence and cleanup near the context limit. Remove those generation-time hints from the final training input.

Filter for correct answers and usable context-management behavior, then segment at context edits. Save the actual model-visible prompt for each segment: an edited history cannot be reconstructed by simply taking a prefix of the raw transcript.

Train on the target assistant/tool-call tokens with input and tool-result tokens masked from the prediction loss. This teaches valid operations before optimizing which operations improve task success.

7. Explore alternative context edits during RL

Collect complete rollouts, then identify their context-edit boundaries. For each edit, compute:

\[ \Delta C=|L_{\mathrm{after}}-L_{\mathrm{before}}|/L_{\mathrm{before}}, \qquad \Delta H=H_{\mathrm{after}}-H_{\mathrm{initial}}, \qquad S=\alpha\Delta C+\beta\Delta H. \]

Here entropy is the average over the first \(k\) generated tokens following the relevant observation. The reference is the initial trajectory entropy, not the immediately preceding edit.

For an invented edit that changes length 10,000→2,000 and entropy 1.2→1.5, \(\alpha=\beta=1\) gives \(S=0.8+0.3=1.1\). This selects where to spend exploration, not whether the edit was good.

If the initial rollouts yield \(M\) snapshots below budget \(N\), rank candidate edits by sensitivity and use the remaining budget for partial rollouts. Branch from the parent of the selected edit, allowing a different edit to be sampled. Branching after the edit would never test whether that edit should have been different.

The paper's recipe starts with eight rollouts, up to eight snapshots each, and fills a 128-snapshot budget per query. These are training settings, not extra inference calls required at deployment.

8. Turn terminal outcomes into update weights

Grade each terminal branch using answer correctness, output format, and tool/context penalties. An intermediate snapshot gets the mean reward of terminal branches that descend from it:

def snapshot_value(descendant_rewards):
    if not descendant_rewards:
        raise ValueError("a snapshot needs a completed descendant")
    return sum(descendant_rewards) / len(descendant_rewards)

Illustratively, an edit that deleted the crucial reason has descendant rewards [0, 0]; its value is 0. A preserve-then-offload edit with [1, 1] has value 1. A common ancestor has value 0.5. These are sampled estimates, not proof that memory alone caused the result.

Standardize snapshot values against the mean and standard deviation of all snapshots for the same query, then use those advantages in a clipped GRPO update. Preserve each snapshot's real prefix, generated-token mask, and old-policy log probabilities. Inherited text must not become newly sampled output merely because it appears in multiple snapshots.

Ground truth belongs in the terminal grader. It is not added to the runtime memorize arguments. The gradient teaches the policy from outcomes across branches.

9. Minimum conformance tests

  • A schema-valid memory round-trips by its exact key.
  • Deleting a message leaves its source chunk and saved memory accessible.
  • Missing keys return a tool error, not a guessed memory.
  • Cleanup reduces the actual next prompt, not only a display log.
  • A training branch can choose a different edit at the same parent.
  • Snapshot values use all completed descendants; empty descendants are not reward zero.
  • Gold answers occur in grading records, not inference prompts.
  • Compressor failures and token-limit violations remain visible.

For a first implementation, make the tool semantics work with a frozen model. Treat that as the paper's tools-only baseline; add the snapshot collector and RL update only when reproducing the learned method.
