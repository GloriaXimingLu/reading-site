Agent Memory: A Precise Reading Edition

16 min · 14 methods and systems · 2026-09-20

Concise reading edition · Revised 20 September 2026. Start with the two-minute map, then check what each writer can see.

This condenses our existing survey around mechanisms we might actually use. It separates published methods from our possible adaptations; it does not choose an implementation plan. No new benchmark results are claimed.

1. The two-minute map

First distinguish two problems:

  • Across tasks: task A finishes; its experience helps a different, separately scored task B. Preserve the store within a declared task stream; reset it between independent streams. Tasks need not be short or independent.
  • Within one long task: the investigation continues after context fills or a session restarts. Preserve the current goal, evidence, uncertainties and next actions. Reset task memory before an unrelated independent task.

A session boundary is not necessarily a task boundary. Persistent files do not by themselves establish learning across tasks.

Three mechanisms can coexist: store information outside the prompt; retrieve the useful part; compact the active conversation. Notes plus search handle the first two, but do not automatically implement the third.

These are overlapping design choices, not nine interchangeable products. A second axis matters just as much: what feedback the writer can see. No ground-truth answer does not mean no environment feedback.

2. Feedback: what does the writer actually see?

Writer input and learning supervision are different. A model can write memory without seeing the correct answer, while a training algorithm later uses that answer to reward the memory-writing behavior.

Separate four signals:

  • Ordinary observations: tool results, test failures, browser state, retrieved documents or user messages.
  • Self-judgment: an LLM infers success/failure from the attempt. This is a fallible prediction, not an authoritative label.
  • Outcome feedback: a verifier or environment returns success/failure or a score, without necessarily revealing the correct solution.
  • Ground truth: an explicitly supplied reference answer, correct patch or target state.

Finding an answer in a source document is ordinary evidence access, not the same as receiving the evaluator's answer key. Also, an observer sees only the information routed to it—not automatically everything the solver or evaluator knows.

Timing changes the experiment

Across-task feedback can follow this order:

attempt A → record A's score → reveal permitted feedback → update memory → attempt B

Revealing A's answer after scoring can be valid supervised online learning if the protocol permits it. It is not observation-only learning, and cannot retroactively improve A's recorded score. Reattempting A after feedback is a separate feedback-assisted evaluation.

Within an unfinished task, a checkpoint can use observations already received, but not a final evaluator outcome that has not occurred. In offline RL, later reward can train earlier writing actions without having appeared in their input prompts.

For comparisons, match who receives feedback, its contents and when it arrives. Keep hidden evaluation information separate unless the declared protocol allows it.

3. The likely practical candidates

Codex compaction: replace the working history

In the inspected readable path, a model summarizes the conversation; the client builds a replacement history from selected recent real user messages plus that summary, with initial context handled separately. It does not simply preserve a recent raw tool-call tail. “Local compaction” means client-orchestrated, not necessarily on-device inference. This description is pinned to the inspected Codex implementation.

The attraction is direct control of prompt growth. The risk is irreversible omission from the working view: a good-sounding handoff may discard an exception or leave an untested hypothesis looking established.

Provider compaction is a different interface. OpenAI's standalone endpoint returns a canonical replacement window containing an opaque encrypted compaction item and potentially retained items; pass the entire output onward unchanged. Its input must still fit the model window. Automatic server-side compaction uses a threshold and different chaining rules. Neither should be described as an editable Markdown summary. Official guide

For us: “instructions + checkpoint + recent complete tool interactions” could be a useful design, but it is our adaptation, not this pinned Codex algorithm.

ShadowFrog: the solver maintains a code-indexed notebook

Write: initialize a .shadow/ tree mirroring source files and symbols. During work, the solver records behavioral discoveries with scope, provenance and verification status. It can use observed tests and user feedback, but verification status is not a hidden benchmark success label. Cross-file knowledge has references/backlinks; updates and consolidation maintain the notebook.

Read: consult preferences and relevant cross-cutting findings, then the relevant file/symbol notes before modifying code. Hooks can surface bounded reminders. The organization is part of the retrieval method, not cosmetic formatting. Pinned skill and schema

For us: a concrete candidate for durable knowledge in repeated coding work. Extending file/symbol anchoring to papers or research claims would be a domain adaptation.

It is not a universal post-tool observer, a full interaction archive, or a context compactor. The solver must notice what deserves preservation; later code changes can invalidate notes. Preserve its write/read instructions, verification rules and triggering behavior before calling a port faithful. Optional autonomous exploration is an extra source of work and cost, not free memory maintenance.

Claude-Mem: a separate observer maintains searchable notes

Write: tool-event hooks feed an observer with the primary agent's tool inputs/results. The observer writes structured observations—facts, narrative, concepts and file references—and progress summaries. Its prompt explicitly gives it no independent investigation tools. A failed test is visible only if supplied in its captured events; an unseen evaluator result is not. Pinned observer prompt

Read: inject bounded recent context and use staged lookup: search for candidates, inspect their timeline, fetch selected observations, optionally recover captured tool-use records. SQLite persistence and the search/indexing pipeline support this workflow. Search workflow

For us: a concrete observer-written-memory candidate. It separates recording from task execution, but adds inference cost and a readiness problem: an accepted event may not yet be a searchable memory.

Do not assume a lossless archive. In the inspected implementation, raw tool-use storage is best-effort with capped fields. Also, replacing its retrieval with plain grep, or replacing its observer with our common note schema, changes the method. Tool-use storage

Memex / MemexRL: shrink the prompt, retain indexed blocks

Loop: CompressExperience stores selected blocks and replaces working history with an indexed summary, preserving instructions and the task. ReadExperience(index) retrieves a stored block.

Important correction: blocks can be model-authored text or verbatim spans selected through anchors. Exact retrieval returns what was stored; it does not make an authored paraphrase exact original evidence.

MemexRL jointly trains memory and task actions using task reward plus efficiency/format penalties. Giving an untrained model these tools is an interface baseline, not reproduction of the trained result. Method and training

For us: the most direct candidate when the problem is evidence loss after compaction. Its failure point is navigation: if the summary loses the only discoverable pointer, an intact archive may still be practically useless.

The paper's episode starts with an empty store. Persistence across separate tasks is an additional setting, not established by that loop.

PRO-LONG: preserve the log and make the reader powerful

The writer is largely mechanical: append interactions to a structured log. The agent uses file access, regular-expression search and Python to locate, compare and compute over past states. This shifts work from deciding in advance what to summarize toward selecting information when needed. Paper

For us: an important comparator to sophisticated writers, especially when exact sequences or relationships matter. Grep can locate an event; code can compare all occurrences or reconstruct a trajectory.

The paper's tool ablations show that programmatic access contributes beyond file reading alone. Its ARC-AGI-3 scores are benchmark scores, not simply percentages of games solved. The evaluated per-game memory does not establish transfer between games.

A larger archive is not a larger active prompt. The agent still needs to choose bounded outputs, and reader capability, tool budget and log structure matter. Giving only grep would not reproduce the full programmatic reader.

4. Across-task experience: three different approaches

ReasoningBank: distill a reusable lesson

After an attempt, an LLM judge assesses success or failure from the query and trajectory without a ground-truth reference; a writer uses that proxy signal to extract reusable reasoning lessons. Before the next problem, similarity retrieval supplies relevant past experience. The learning is in external memory, not model-weight updates. MaTTS adds test-time sampling and should be counted separately. Paper

Use it to understand the basic cross-task loop. The key danger is extracting a confident but false general rule from a misunderstood failure. Model judgment is not ground-truth feedback; our experiment must declare which feedback the writer can see.

ACE: maintain a playbook without rewriting everything

A Generator attempts the task, a Reflector extracts lessons, and a Curator proposes localized changes to ID-addressed bullets. Deterministic merging and refinement maintain the playbook; bullets carry helpful/harmful metadata. The central idea is incremental maintenance, not repeatedly compressing all knowledge into one new summary. Feedback is a configurable experimental condition: the paper marks GT-label access to the Reflector separately, and no-label runs may still have execution feedback. Paper

Use it when lessons accumulate and need revision. It does not automatically bound the active prompt: a richer injected playbook can cost more tokens. Replacing playbook injection with our own retrieval policy is a separate adaptation. For online evaluation, score the current prediction before incorporating its allowed feedback.

MemRL: learn which experiences are useful

Store intent, experience and a utility value. First retrieve semantically plausible candidates; then select using usefulness as well as similarity. Environmental outcome feedback updates memory utilities while the underlying LLM remains frozen. Separately, an LLM summarizes trajectories into new memories. A reward updating a utility value is not the same as a gold answer entering that writer's prompt. Paper

Use it when “similar” does not reliably mean “helpful.” Here RL changes retrieval values, unlike MemexRL's model-policy training. Rewarding a retrieved item after a successful task does not prove that item caused success. Availability of valid feedback, changing task distributions and misleading high-utility memories are central questions.

5. Training is a separate choice, not an afterthought

Text memory can use frozen API models, a trained writer/reader, or a jointly trained solver. We should not silently restrict the survey to prompted wrappers. A training reward is supervision for parameter updates, not necessarily information visible during a memory-writing call.

Candidate What is learned Why read it / main qualification
MemAgent RL trains repeated overwriting of a bounded text memory while reading chunks The writer knows the question, not the reference answer. Training rewards compare its final answer with ground truth. Unknown future questions are a harder setting.
AgentFold SFT teaches context folding at different scales Individual steps and completed subproblems can be compressed differently. Folding is lossy; inference code alone does not establish a complete training reproduction.

For AgentFold and AutoMem, this edition does not establish exact gold-label visibility during demonstration construction or scaffold optimization; audit those inputs before claiming a label-free reproduction. SFT targets are also not automatically inputs supplied to the deployed writer.

For training through compaction, preserve each segment's actual conditioning prefix; a reconstructed full transcript is not equivalent. MemexRL's segmented training

Latent memory: compress the representation itself

  • Cartridges: for a particular corpus, generate synthetic conversations and optimize a compact KV prefix against a full-context teacher, keeping the backbone frozen. Reuse that prefix for many queries. Think “prepare a reusable representation of a corpus,” not “write a running note.” Preparation and rebuild costs matter; reported KV-memory or throughput gains are not equivalent to total-GPU-memory or per-request-latency gains.
  • Still: train a general compactor that maps full KV states to compact synthesized states in a forward pass. Unlike Cartridges, it amortizes learning across contexts rather than fitting each corpus separately. It still has cache-construction costs; iterative cache growth is not constant-sized infinite memory. The prior survey did not verify an official implementation/checkpoint.

These require access to model internals. They are not drop-in note stores behind a standard text-only API. They remain relevant if repeated corpus use or serving-memory cost is our main problem.

6. One example makes the distinctions concrete

Illustrative, not a benchmark result: a research agent learns that “20% improvement” is relative, only holds for one subgroup, and uses a changed evaluator. It has not yet resolved the evaluator difference.

  • A checkpoint must preserve the unresolved comparison and next action.
  • A scoped note preserves the conditional claim and its source, rather than “method X is better.”
  • An observer can record that finding only if the captured events contain it.
  • An indexed archive can recover the exact passage, provided it was stored exactly and remains findable.
  • A programmatic reader can compare evaluator outputs across the full history.
  • A cross-task lesson might be “check denominator, subgroup and evaluator version.” It is not the old task's to-do list.
  • A latent representation may retain enough to answer expected questions but needs testing on an unexpected question about the evaluator.

The same pattern applies to coding: “single-tenant test passes” must not become “cache bug fixed” while a two-tenant regression remains unresolved.

Suppose the note instead says “the fix failed.” Was that inferred by the model, observed in a runnable test, returned by a hidden grader, or learned by seeing the reference patch? Preserve that provenance. These signals justify different conclusions even when the note's wording is identical.

7. What we should carry into brainstorming

The first decision is the failure we want to fix: losing ongoing state, failing to reuse experience, failing to recover evidence, or paying too much for long context. “Add memory” is underspecified.

My reading priority—not a locked implementation order—is:

  1. Compaction, ShadowFrog and Claude-Mem: understand history replacement versus solver-written versus observer-written knowledge.
  2. Memex and PRO-LONG: compare selective indexed storage with an append-all archive and powerful reader.
  3. ReasoningBank, ACE and MemRL: compare lesson extraction, maintenance and usefulness-based selection across tasks.
  4. The training and latent section: decide whether learning the policy or representation is central to our question.

Before calling anything a faithful port, pin its writer input, feedback source/content/recipient/timing, prompts, write timing, schema, read policy, context replacement and persistence/reset rules. Record training supervision separately from deployment-time writer inputs. Removing a UI or daemon can preserve the method if behavior stays equivalent. Changing these contracts usually does not.

The earlier V0–V3 ladder is a proposed set of controlled adaptations/ablations, not faithful reproductions of the named systems. It belongs after choosing the methods and stating their contracts, not at the beginning of the survey.

Finally, compare task outcomes at a declared total budget: solver plus writer/observer calls, retrieval, compaction, training and preparation where relevant. Report observation-only/self-judged, outcome-feedback and gold-answer-feedback conditions separately, with matched access across methods. Keep evaluator-only labels out of agent-visible memory unless the protocol explicitly permits that feedback. Retrieval accuracy, successful restart and task success are different evidence.
