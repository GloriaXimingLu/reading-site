Implementing compaction: readable handoffs and opaque continuation state

6 min · 1 implementation chapter · 2026-09-21

All memory methods · Short overview

What you are building

Compaction changes the input window for the next model call. Saving a note on disk does not do that by itself.

There are two interfaces to understand: a readable handoff constructed by a client, and the provider's opaque compaction state. The existing source audit covers the pinned readable Codex path; the provider integration below follows the current official compaction guide.

The opaque provider's internal compression algorithm is not public. We can explain how to implement its caller, not invent an implementation of its hidden compressor.

Step 1 — Keep active input separate from your diagnostic log

Your harness can maintain:

state = {
    "instructions": "Task and tool-use instructions",
    "active_items": [],       # actually sent on the next request
    "diagnostic_log": [],     # retained for your own inspection
    "compaction_count": 0
}

This is an illustrative client state object, not an SDK schema. Its purpose is to avoid a common mistake: keeping a full transcript on disk does not mean the next model call receives it.

Append completed assistant outputs and tool responses to the active input according to your API's item schema. Preserve tool-call identities and matching results. For a teaching harness, choosing completed tool-exchange boundaries simplifies compaction bookkeeping; it is our boundary choice, not a claim that native compaction always waits for those boundaries.

Step 2 — Decide when to compact

Let the model context capacity be \(W\), your reserved generation/tool headroom be \(R\), and the active input size be \(L\). A client-controlled example trigger is \(L>W-R\). The choice of \(R\) is yours, not a universal Codex constant.

Compact while the submitted window still fits. Triggering only after an oversized request has already been rejected may leave the compressor unable to accept that same window.

Count the actual serialized model input, including instructions and tool definitions, rather than only the visible prose. Token estimates are approximate unless the provider supplies an authoritative count.

Step 3A — For a readable handoff, make a separate summarization call

Supply the available conversation to a writer with a handoff instruction. The output should tell the next solver what remains to do and what evidence established the current state.

An authored teaching contract is:

Produce a continuation handoff containing:
- current user goal and constraints
- completed actions and their observed results
- relevant file/resource locations
- unresolved questions and unverified assumptions
- next actions still needed
Do not report unrun checks as passed.

This is not the literal Codex prompt. Use the pinned handoff prompt from the source audit for a faithful port.

The audited readable path retains selected real-user messages under an approximately 20K-token retention budget and combines them with the handoff and initial-context handling. It does not generally promise to retain a raw recent-tool tail. A portable “summary plus recent exchanges” policy is a different retention choice.

Step 4A — Replace the active window, do not merely append the handoff

Suppose the pre-compaction history contains a cache investigation, an edit, and one targeted passing test. A useful handoff is:

Goal: isolate cache entries by tenant.
Changed src/cache.py to include tenant identity in key construction.
The targeted two-tenant regression passed.
The full suite has not run.
Next: inspect adjacent call sites, then run the remaining checks.

The state transition is:

active before:
  instructions + user requirements + long investigation

active after:
  initial context + retained user messages + generated handoff

diagnostic log:
  still contains the original investigation, if your harness retained it

Appending the handoff to the unchanged long history saves no context. Conversely, replacing the history means omitted facts are unavailable unless another tool/store exposes them.

After a successful replacement, increment your compaction count and continue with the ordinary solver. Repeated compaction summarizes summaries, so evaluate whether crucial facts survive multiple cycles.

Step 3B — For standalone provider compaction, preserve returned items

The standalone endpoint accepts the current input and returns a compacted output array. Feed that array into the next response request. It includes opaque continuation state; extracting only human-readable output discards the object you needed. Endpoint contract

def compact_and_continue(client, model_id, instructions, active_items, next_message):
    compacted = client.responses.compact(
        model=model_id,
        instructions=instructions,
        input=active_items,
    )
    replacement = list(compacted.output)
    continued = client.responses.create(
        model=model_id,
        instructions=instructions,
        input=replacement + [{"role": "user", "content": next_message}],
    )
    return replacement + [{"role": "user", "content": next_message}] + list(continued.output)

This is an integration sketch, not an API call executed by this tutorial. Choose a supported model and SDK version in your application. The replacement and new user message become the next active window; subsequent tool outputs still need normal handling.

Treat each returned item as an API object. Do not stringify the entire array into one chat message, decode encrypted content, or discard an unfamiliar item type because it lacks output text.

Step 4B — Or use server-side compaction, without a standalone call

Server-side compaction configures context_management on the response request. The server checks the threshold and emits compaction state as needed. Continue either by carrying the output items in a stateless input array or by using previous_response_id chaining; these are distinct state-management patterns. Official server-side flow

An illustrative request option is:

{
  "context_management": [
    {"type": "compaction", "compact_threshold": 20000}
  ]
}

The number is illustrative, not a recommended threshold for every model. Use the guide's full schema and a budget appropriate to the selected model. You do not also need to call the standalone endpoint merely because the server-side feature is enabled.

Follow one concrete continuation

Before compaction, the solver knows that one targeted test passed. After compaction, ask it to continue validation.

In the readable path, inspect whether that fact and the unrun-suite caveat appear in the handoff. In the opaque path, inspect the subsequent behavior: does the solver distinguish completed checks from pending ones? You cannot audit opaque memory by reading its internal representation.

A correct client can still receive a lossy or mistaken handoff. Client transport correctness and information preservation are separate tests.

Feedback and what to test

The writer sees supplied conversation state, which may contain test output or user corrections. Compaction does not grant a separate answer-key channel.

Test that replacement actually shortens the active window; user constraints survive; pending tool calls are handled consistently; instructions are resent as required; opaque output objects are passed intact; and an API failure leaves the old active state recoverable. The rollback behavior is recommended client engineering.

There is no Cartridges-style per-corpus gradient update or published Still-style KV architecture established by this interface. A provider compaction object should not be labeled either one simply because it is numerical or opaque.
