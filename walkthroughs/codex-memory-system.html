Codex Memory: Sessions, Consolidation, and Retrieval

2 min · 1 implementation deep dive · 2026-09-21

All memory methods · Separate topic: in-session compaction

The idea: a background writer extracts lessons from individual sessions; a consolidation agent turns them into a shared handbook; the next solver receives a small index and searches for the details it needs.

This is cross-session memory, not the compaction that shortens an unfinished conversation. The following example is invented; no private session data is reproduced.

1. A coding session leaves evidence

In a fictional project, Juniper, a product cache returns tenant A's data to tenant B. The agent discovers that the cache key omits the tenant ID. It patches the key and passes a two-tenant regression. The full suite remains unrun.

The saved session contains the request, investigation, tool results, patch, and qualification about tests.

2. A separate writer extracts that session

Later, after the session becomes eligible, a background model call reads its filtered record. It produces a session recap and candidate reusable lessons.

The lesson is specific: “In Juniper's product cache, check tenant identity in the key.” It must not turn “one regression passed” into “all tests passed.”

3. The program stages the writer's output

It stores the structured result in a database. A later consolidation pass materializes selected results as Markdown files.

Important: the file named raw_memories.md already contains LLM-written notes, not the original conversation.

4. A consolidation agent creates higher-level memory

It reads what changed, updates a searchable handbook, and writes a compact index. If another session establishes a similar failure in an authorization cache, it can connect those findings.

A defensible abstraction is: “For Juniper caches whose results depend on identity, check which identity inputs the key omits.” It preserves which sessions support the claim.

A repeated, verified workflow may also become a skill.

5. A new solver receives the small index

A later request mentions wrong cached results. Codex supplies the memory index and instructions for consulting it.

The entire handbook and all old conversations are not automatically added to the prompt.

6. The solver searches, reads, and verifies

It searches the handbook for terms such as “Juniper,” “tenant,” and the cache function name. It opens the relevant block and, if needed, its linked session recap or skill.

Then it checks today's code. Historical memory suggests where to look; it does not prove the current bug has the same cause.

What changes: external files and database records—not model weights. What the writer sees: recorded evidence, including available tests and user corrections; no additional answer-key channel.

Version boundary: this walkthrough teaches Codex's V1 file hierarchy. The pinned source also contains V2, which removes some layers. Read the version comparison before choosing an implementation.

Phase 1: exactly how one session becomes memory

1. Trigger background work; do not wait for a goodbye message

An eligible root session's startup triggers the pipeline asynchronously. The startup path skips ephemeral sessions, disabled memory features, non-root agents, and an unavailable state database. A quota guard can also skip generation.

It processes eligible earlier sessions, not the just-started session. The memory store is not freshly rebuilt synchronously before that session's first answer. Eligibility does not require a user to declare a task finished: the current thread is excluded; candidate threads must have memory generation enabled, an allowed interactive source, a sufficiently recent last update, enough idle time, and an extraction needing an update. Claims/leases prevent duplicate workers.

At this source revision, the relevant defaults are 6 idle hours, 10 days maximum rollout age, and 2 rollout candidates per startup. These are snapshot defaults, not requirements for our research harness. Extraction has a concurrency cap of 8 even though the default per-startup batch is smaller.

Startup · Eligibility query · Limits

2. Build the extractor's input from recorded evidence

The program loads the rollout and filters it. It retains eligible user/assistant messages, tool calls/results, and inter-agent communication. It excludes developer messages, recognized injected AGENTS/skill instruction fragments, reasoning items, compaction items, and non-selected event/metadata records.

It supplies the rollout path, working-directory hint, and serialized filtered conversation to the extraction prompt. Secrets are redacted. Oversized V1 input is truncated, keeping head and tail, to a budget computed as 70% of the model's effective input window; the fallback is 150,000 tokens.

Consequence: “the writer reads the session” does not mean it sees every original byte. Important middle evidence can be omitted. A faithful implementation must record truncation rather than pretend extraction was exhaustive.

3. Make one structured model call—not a tool-using investigation

Phase 1 constructs an extraction prompt with a strict JSON output schema. It does not separately load the global handbook; any earlier memory echoed in retained session messages or tool results may still appear as evidence. Its runtime collects the model's text response; it does not run a shell-tool loop to revisit the repository.

The V1 response has exactly these fields:

{
  "rollout_summary": "Markdown account of this session's useful tasks and evidence",
  "rollout_slug": "juniper-tenant-cache",
  "raw_memory": "Markdown candidate lessons, with task boundaries and retrieval handles"
}

Those strings explain the fields; they are not a complete example of the required Markdown inside them. The exact linked prompt defines that internal format. The schema permits a null slug; the prompt prefers a string, including an empty string for no-op.

The writer is prompted to:

  1. Separate distinct tasks inside the session.
  2. Classify each as success, partial, fail, or uncertain from available evidence.
  3. Preserve concrete user requests/corrections and verified environmental facts.
  4. Record useful commands, paths, error strings, failed approaches, and successful pivots.
  5. Keep uncertain proposals and unverified completion claims labeled as such.
  6. Return all-empty fields if there is no durable signal worth retaining.

This is an instructed behavior, not a guarantee that the model's judgments are correct.

4. Follow the Juniper evidence into the two outputs

An illustrative rollout-summary excerpt:

Task: isolate Juniper's product cache by tenant.
Observed cause: product_key omitted tenant_id.
Change: include tenant_id in the product-cache key.
Validation: the two-tenant regression passed.
Limit: full test suite not run.

An illustrative raw-memory excerpt:

Reusable knowledge:
- Juniper's product_key must distinguish tenants for tenant-dependent results.

Failures and how to do differently:
- A one-tenant test did not expose cross-tenant reuse.
- Reproduce with identical product IDs in two tenants.

References:
- src/product_cache.py; product_key; tenant_id
- tests/test_product_cache.py::test_two_tenants

The raw note is already a first abstraction from an event to future guidance. It is narrower and more reusable than a chronological transcript. Consolidation supplies the next abstraction across sessions.

5. Persist the result, with provenance

The program parses the schema, redacts generated fields, and stores a successful extraction in the memory database with its thread and source-update information. Empty output is a legitimate no-output outcome. In V1, an empty raw_memory or an empty rollout_summary causes the result to be treated as no-output; retaining only the other field is not a successful extraction. Failures use retry/lease handling.

This is not “the main solver appends a lesson to MEMORY.md after every answer.” The ordinary solver, per-session extractor, and consolidator have different jobs.

There is also an explicit-update route: if the user asks to remember, correct, or forget something, the read instructions direct the solver to create a small note under extensions/ad_hoc/notes/. Consolidation applies it. That is separate from automatic session extraction.

Phase 2: exactly how consolidation creates abstractions

1. Select the input set and acquire one global lock

Consolidation is serialized for the selected memory namespace. The program claims the global job before changing the workspace.

It selects up to 256 eligible nonempty stage-1 records by default. Selection prioritizes usage count, then last usage—or source_updated_at for never-used memories—with further deterministic tie-breaks. A default 30-day unused window limits eligibility. The selected set is returned in stable ascending thread-ID order for file generation.

This is a retention policy, not query similarity retrieval and not proof that a frequently used memory is correct.

Selection SQL · Phase-2 controller

2. Materialize the evidence and compute what changed

The program writes:

  • One selected session's recap per file in rollout_summaries/.
  • The selected raw notes into raw_memories.md, with thread IDs, source times, working directories, rollout paths, and summary filenames.
  • phase2_workspace_diff.md, a Git-style diff against the previous successful consolidation baseline.

Summary filenames combine a timestamp, short hash, and sanitized slug. Do not derive filenames merely from the model's slug; use the actual produced path.

Unselected summaries are pruned. Their deletion appears in the diff. This is how the next writer learns that some older evidence no longer supports the current memory set.

If the synchronized workspace is unchanged and required artifacts validate, the controller can skip the model agent.

File materialization · Diff and dispatch

3. Spawn an internal agent that can read and edit files

Unlike Phase 1, Phase 2 is an actual agent session with a local file-editing workflow. Its working directory is the memory root.

It is ephemeral, does not generate further session memories, does not inject the usual memory context into itself, and cannot recursively delegate. MCP servers, apps, and plugins are disabled for this worker.

For a managed parent sandbox, it gets memory-root write access and no network. Important qualification: this revision preserves a parent's explicitly disabled or external sandbox profile; “always network-isolated under all configurations” would be false.

Its input includes the consolidation instructions and diff path. The prompt tells it not to open original rollout transcripts. It works from the staged notes, summaries, existing memory, and applicable extension inputs.

4. Update a task-oriented handbook—not just concatenate notes

For a first build, the agent reads the available inputs and creates the artifacts. For an incremental update, it uses the diff to locate additions, modifications, deletions, and the affected existing blocks.

Each V1 handbook block has a task-group heading, scope/applicability, task-specific source references and keywords, followed by consolidated preferences, reusable knowledge, and failure guidance where supported.

A shortened teaching excerpt, not a full production block:

# Task Group: Juniper identity-dependent caches
scope: product and authorization cache isolation
applies_to: cwd=/work/juniper; reuse_rule=verify current cache semantics

## Task 1: Product cache tenant isolation, targeted regression passed
### rollout_summary_files
- rollout_summaries/<actual-produced-filename>.md
  (cwd, rollout_path, updated_at, and thread_id retained)
### keywords
- Juniper, product_key, tenant_id, cross-tenant, test_two_tenants

## Reusable knowledge
- Product results varied by tenant; product_key omitted that input. [Task 1]

## Failures and how to do differently
- One-tenant tests missed the collision; vary tenant while holding product ID fixed. [Task 1]

The real format includes concrete metadata values, not the explanatory placeholders above. Similar words alone are not sufficient reason to merge two unrelated projects or tasks.

5. Promote only the abstraction supported by the evidence

Suppose a second Juniper session finds that an authorization cache ignores role, and a two-role test verifies the fix.

Now the consolidator can group the two cases and write:

For the identity-dependent Juniper caches examined, vary the relevant identity input while holding the object fixed; verify that keys separate outputs that should differ.

This is a synthesis of two observations. It should retain both source references and the Juniper scope.

It should not infer “all cache keys everywhere must include tenant and role.” It should not infer a user's global preference from a single task-specific instruction.

There is no separate trained abstraction model or formal rule-learning algorithm here. A prompted LLM reads evidence and edits text. Grouping, deduplication, promotion, contradiction handling, and uncertainty preservation are part of that editorial task.

6. Optionally package a repeated procedure as a skill

The prompt recommends a skill when a reliable procedure recurs more than once and saves time or errors. Merely remembering a fact does not require a skill.

For the two cache cases, an illustrative procedure excerpt could be:

When to use: suspected cross-identity cache reuse in Juniper.
1. Identify inputs that change the uncached result.
2. Inspect which inputs participate in the key.
3. Build a paired test: same object, different relevant identity input.
4. Verify the failure before the patch.
5. Change the key, then rerun the paired test and adjacent checks.
Stop if the result is not identity-dependent; investigate another cause.

The complete skill lives in skills//SKILL.md, with trigger/inputs, steps, pitfalls, verification, and optional scripts/templates/examples. These are external instructions and helpers, not weight updates or automatic execution. A later solver has to read and follow the skill.

Handbook and skill formats

7. Write the small index last, then validate completion

The consolidator writes memory_summary.md after the handbook and skills reflect the final state. It includes a brief user profile, reusable preferences, general tips, and a “What's in Memory” navigation section. Its first line must be v1.

A routing entry might mention Juniper cache isolation with the exact searchable handles product_key, tenant_id, and authorization cache. The point is to help a future solver choose a useful lookup without injecting the entire handbook.

After the agent completes, the controller validates artifacts, verifies lock ownership, advances the workspace baseline, and records successful input snapshots. V1's runtime checks are structural: a MEMORY.md file, the required summary header, and symlink safeguards—not a semantic fact-check of every lesson.

Do not assume this code provides an atomic, all-files publication transaction merely because it uses Git. For our evaluator, an explicit successful-consolidation barrier is advisable.

Read path: exactly how search and retrieval work

1. Automatically supply the index, not the whole library

When memory use is enabled and a nonempty summary exists, the extension reads memory_summary.md, caps it at 2,500 tokens, renders the read instructions around it, and contributes developer-policy context.

That summary is the automatic part. The ordinary solver decides which additional files to search/read. It is not a separate retrieval subagent, and the code does not automatically attach a top-k embedding result here.

The consolidation prompt loosely calls this “system prompt” loading; the actual extension contributes a developer prompt fragment.

Summary loader · Prompt integration · Token cap

2. Let the model choose search words

In the example, the current task mentions a tenant leak. The index mentions the Juniper cache task family. The model chooses terms from both: tenant_id, product_key, and cross-tenant.

An illustrative shell lookup, run from the selected memory root:

rg -n -i -C 4 'tenant_id|product_key|cross-tenant' MEMORY.md

This command is a teaching example, not a fixed string hardcoded in Codex. The model chooses the query; ripgrep does lexical matching. If the terms are poor, retrieval can fail.

3. Read the relevant block; follow a small number of pointers

A search hit identifies a useful region. The solver reads that block with a bounded file read, including its scope, evidence, and warnings—not only the matching keyword line.

The V1 read prompt then directs it to open the one or two most relevant linked rollout summaries or skills when needed. It does not recommend scanning every recap.

That distinction matters: search finds an address; reading obtains the lesson and its qualifications. Returned file text enters the current conversation as tool output, which makes it available to the next solver call.

4. Escalate to original evidence only when needed

If the recap is insufficient for an exact command, error, or chronology, the V1 reader may use its rollout_path to examine the original session.

That allowance belongs to the later solver's read path. The consolidation prompt separately forbids opening original transcripts. Do not give both roles the same evidence access by accident.

For the initial memory pass, the prompt suggests roughly 4–6 search steps, stops on no relevant hits, and allows another pass if execution reveals a likely connection. This is prompt guidance, not a hard-coded search-loop counter.

Exact V1 retrieval instructions

5. Verify present-day facts before acting

The old lesson says where a bug was found. It does not establish today's function implementation, branch state, API version, or test result.

The solver inspects the current owning source when the claim can drift and matters. If it relies on historical information without refreshing it, the read instructions require appropriate qualification.

This prevents a useful memory from becoming an unquestioned instruction to repeat an obsolete fix.

6. Distinguish optional dedicated tools from embeddings

When memories.dedicated_tools is enabled, the extension can expose memories.list, memories.search, memories.read, and memories.add_ad_hoc_note. This switch is separate from V1/V2 and defaults to false in the audited source.

The local search backend performs substring matching. It supports case handling, optional alphanumeric normalization, any-query matches, all queries on one line, or all within a line window. It returns paths, line numbers, context, and pagination; results are ordered by path and line—not a semantic relevance score.

Neither this local backend nor the shell-based V1 path requires an embedding model or vector database. The model's semantic judgment is in writing searchable memory, selecting query terms, interpreting hits, and deciding what to read next.

Feedback, forgetting, and failure boundaries

Ground truth. There is no separate gold-answer input in the extractor's request. It can see tests, user corrections, and other feedback included in the filtered record. If a task's tools exposed a reference answer, that text could become input; absence of a special answer-key field does not itself prove an experiment is leakage-free.

Outcome labels. Phase 1 infers success/partial/fail/uncertain. These are textual judgments used in memory writing, not an externally verified reward or gradient update.

Usage. The read prompt requests source citations, including rollout IDs. The code parses those references and supports incrementing cited stage-1 usage counts and last-use time. Shell-read telemetry also exists, but it should not be confused with evidence that a remembered procedure succeeded. Retention favors use; it does not perform MemRL-style reward learning.

Forgetting. Pruning removes inputs from the selected set. The diff instructs consolidation to remove guidance supported only by deleted inputs, while preserving guidance that still has other support. This cleanup is partly an LLM task; provenance and regression tests matter.

Explicit corrections. User-authorized remember/forget/correction notes feed the consolidation process. Do not silently rewrite generated memory as though it were the authoritative user request.

Trust. Both writers are instructed to treat recorded content as evidence, not executable instructions. Redaction and prompts reduce risk, but do not constitute a guarantee against secret retention, prompt injection, false abstraction, or stale advice.

What I would implement first for our experiment

Proposal, not a claim about native Codex behavior: start with the V1 architecture because the object of interest is session extraction → cross-session abstraction/skills → agent-directed text retrieval. Keep compaction fixed and separate.

Minimal components

  1. An append-only task/session evidence log.
  2. A schema-constrained per-session extractor using a pinned prompt and explicit evidence policy.
  3. A stage-1 store keyed by session ID and source revision.
  4. A single consolidation worker with bounded inputs, source references, and a restricted file workspace.
  5. A small summary injected before a new task; bounded search/read tools for everything else.
  6. A completion barrier before the next evaluated task uses the new memory snapshot.

The high-level control flow is:

AFTER AN ALLOWED SOURCE SESSION BECOMES ELIGIBLE:
  evidence := filter_and_budget(recorded_session)
  extracted := model_call(extraction_prompt, evidence, strict_schema)
  validate_and_store(extracted, source_id, source_revision)

AT A CONSOLIDATION CHECKPOINT:
  acquire_single_writer_lease()
  selected := choose_retained_stage1_records()
  materialize_selected_notes_and_recaps(selected)
  diff := compare_with_previous_successful_baseline()
  if diff_exists OR required_artifacts_invalid:
    run_consolidation_agent(diff, existing_memory_workspace)
    validate_artifacts()
  record_successful_snapshot()
  release_lease()

ON THE NEXT SOLVER TASK:
  context := task + memory_read_instructions + bounded_summary
  solver chooses search/read calls when relevant
  returned memory text becomes tool context
  solver checks current evidence and performs the task

This is control-flow pseudocode, not executable Codex Rust and not a complete failure-handling implementation. Native startup is asynchronous; a synchronous evaluation checkpoint would be our deliberate adaptation.

Trying the native feature is different from porting it

Local memories are off by default. In a build supporting the audited settings, this explicitly selects the V1 architecture:

[features]
memories = true

[memories]
version = "v1"
generate_memories = true
use_memories = true
dedicated_tools = false

This is a configuration example, not a change made to your settings. Extraction/consolidation model overrides exist, but the fallback model comes from the configured provider; there is no single model ID hardcoded by this tutorial.

Benchmark integration trap: the native extraction candidate list uses interactive session sources; it does not include the noninteractive Exec source. Merely turning on memories for a runner using codex exec is therefore not a verified way to learn from its completed benchmark runs. A port needs an explicit ingestion adapter and checkpoint policy. Confirm the runner's actual session source before relying on automatic collection.

Feature gate · Allowed session sources · Model selection

Fix the evidence policy before comparing scores

For CL-style tasks, specify what is allowed after task A: observations only, a success/failure score, or a reference answer. Keep any hidden evaluator answer out of extraction and retrieval unless the protocol explicitly permits it. Score A before writing memory for B.

Do not let consolidation read future-task materials. Decide whether the memory is per-user, per-project, or per-benchmark stream. Native Codex uses a broader user/host-local store and preserves project scopes inside its text; blindly sharing that store across evaluation splits would change the experiment.

Tests that would make me trust the first version

  • A writer preserves “targeted test passed; full suite unrun.”
  • A single instruction does not become an unsupported global preference.
  • A second verified example supports a scoped abstraction without erasing provenance.
  • A search hit leads to reading scope and caveats, not keyword-only action.
  • No matching memory leads to normal work, not endless searching.
  • A deleted source removes only exclusively supported claims.
  • A changed source is re-extracted; stale revisions are not silently reused.
  • A failed writer or incomplete consolidation is not presented as a completed new snapshot.
  • V1 and V2 artifacts never leak into each other's reader namespace.
  • No-memory, raw-recap-only, handbook, and handbook-plus-skills conditions share the same solver, evidence permissions, and compaction policy.

Those comparisons are proposed ablations, not results. This tutorial inspected source and tests its teaching examples/site behavior; it does not claim to have run Codex's Rust suites, model extraction, consolidation, or a benchmark.

The central design to copy: preserve evidence once, extract per-session knowledge, consolidate across sessions with source links, and let the solver retrieve only what the next task needs.
