Memory Benchmarks: Across Tasks vs Within One Long Task

45 min · 15 papers · 2026-09-16

Two-setting framing and concrete task descriptions updated 16 September 2026. A guided review of 15 papers plus benchmark releases, infrastructure, and a field report. Task formats checked against primary sources; prior results/release audit through 15 September. Recommendations and experimental extensions are my synthesis—not reproduced results.

Companions: memory methods · baseline experiments · Q&A notes. This page asks a different question: what evidence would convince us that a memory system is actually useful?

The two-minute version

We now have two independent research settings, not one ladder of increasingly difficult benchmarks:

  1. Across tasks within one benchmark: multiple separately scored short-horizon tasks share a memory store. Start with a CL-Bench domain stream, with a declared per-task budget; add ContinualSkillBench for skill consolidation. STATE-Bench’s Learning Track is the complementary offline, frozen-memory variant—not online learning.
  2. Within one super-long-horizon task: one continuing objective spans a long action trajectory, possibly multiple sessions and compactions. SWE-Marathon is the main long-task substrate; controlled memory comparisons are our extension. MemoryArena is a shorter dependent-session precursor, not evidence of the same horizon.

A session boundary is not a task boundary. Start a fresh memory store for each independent stream in Setting 1, and for each independent long-task trial in Setting 2. Do not carry experience between SWE-Marathon tasks and call the resulting score purely within-task memory.

Shared diagnostics: use LongMemEval-V2 for searching experience and HELMET + OOLONG for compression. They help explain failures in either setting, but do not replace end-to-end evaluation. Remembering an answer, using evidence in an action, and improving from prior tasks remain different capabilities.

Choose the claim, then the benchmark

Setting or diagnostic Strong starting point Boundary of the evidence
1 · Online experience across tasks CL-Bench, ContinualSkillBench One benchmark/domain stream at a time; measure each task's horizon rather than assume every domain is short
1 · Offline experience → held-out tasks STATE-Bench Learning Track Training histories become a frozen artifact; read-only test retrieval, not online updates
2 · One super-long task SWE-Marathon Native long tasks; memory arms and checkpoint resets are our additions
2 · Shorter continuity proxy MemoryArena Dependent sessions inside one episode; do not equate this with super-long execution
Shared · Find past evidence LongMemEval-V2, Mem2ActBench Supplied histories test retrieval/use, not an online stream or full long-task rollout
Shared · Preserve information under a budget HELMET, OOLONG, MemoryAgentBench Long input and incremental ingestion are not themselves long action horizons
Extensions · Non-coding work LAB, HANDBOOK.md, τ³-Banking Define a within-benchmark stream or a genuinely long objective; memory protocol is usually an adaptation

Why use a portfolio? The two settings determine what memory is allowed to cross. Retrieval, action, updating, and compression diagnose what fails inside that setting. Neither cross-benchmark transfer nor outer-harness optimization is required by either primary definition.

What does “related tasks” mean here?

Read each entry with four questions in mind: What is shared? What changes? What resets? Does the agent's earlier action change the later problem? There are several different answers:

  • Reusable knowledge: new requests benefit from a familiar schema, codebase, or procedure. The previous answer need not become an input to the next task.
  • Accumulating evidence: successive observations reveal different parts of one hidden world. Memory must combine evidence, not just retain a better problem-solving recipe.
  • Continuing work: earlier edits, purchases, or decisions become the state from which later steps proceed. This is the dependency inside our Setting 2.
  • Shared source only: separately scored questions consult a fixed archive or corpus. Repeated source access alone is not learning from the agent's task experience.

“Separately scored” does not mean iid; “related” does not mean a chain of actions. Where a source does not establish a sampling model, this walkthrough describes the concrete relationship instead of claiming statistical independence. The six CL-Bench streams below illustrate why this matters.

A. Setting 1 — memory across short tasks within one benchmark

The experimental unit is a stream of separately scored tasks. Carry only declared memory between tasks; reset task-local context and environments as required by the benchmark. Compare the same task sequence with and without prior-task experience. Keep domains and independent streams isolated unless a broader transfer experiment is explicitly declared.

1. CL-Bench — the anchor for online learning

Paper, June 2026 · Methods · Code. Priority: core.

What does the agent actually do? There are six different jobs—not six versions of a recall question:

  • Codebase adaptation: receive a bug report and a repository at its starting commit; inspect/edit code through the shell and submit a patch. Hidden regression tests determine correctness; solving with fewer steps earns more reward.
  • Database exploration: receive a natural-language question about an unfamiliar SQLite database; discover its schema, run SQL, and submit an answer. Reward requires correctness and favors fewer exploratory queries. A midstream migration invalidates some schema knowledge.
  • Cohort studies: receive patient data and coding notes from successive studies of a fictional disease; use analysis tools to submit survival probabilities for 36 cohorts at three time points. Predictions are scored against population truth, relative to a study-average baseline. Population-level evaluation scores are not revealed between instances; in-tool fit feedback on the current biased sample is different.
  • Spectrum monitoring: receive a radio-frequency scan; report occupied frequency intervals, retaining evidence of transmitters that are temporarily silent. Reward measures channel-map overlap; see the paper/code scoring distinction below.
  • Poker: play a complete heads-up hand through betting actions against an opponent with a recurring strategy. Stacks reset each hand; reward is chip profit measured in big blinds.
  • Sales prediction: receive one store's recent sales and a product catalog; analyze them and submit a five-year demand forecast covering 75 product/location/year cells. Scoring penalizes forecast error; the workspace can retain analysis code and models.

These are paraphrases of the official task specifications and scoring rules.

What crosses the boundary? Schema/encoding discoveries, debugging procedures, opponent models, or accumulated statistical evidence—not answers to identical repeated questions. Terminology warning: the paper calls the whole sequence a task and each scored problem an instance. Our Setting 1's “short tasks” correspond to those instances.

How exactly are successive CL-Bench instances related?

The default streams have different dependencies. They are not six versions of “solve unrelated questions one by one.”

Stream What connects successive instances? What changes or resets?
Codebase adaptation Learn repository structure, conventions, and debugging routines across bugs in the same project. Default: 9 tablib issues, then 10 tenacity. Each issue starts in a fresh container at its own base commit; your previous patch does not carry over. The curated issues come from chronological windows, not an iid randomized sample.
Database exploration Forty questions reuse discoveries about one database's hidden schema and encodings—for example, which category stores prices in cents. After question 20, a scheduled migration changes schema/data. Queries are read-only: your previous answer does not alter the next database. Old schema notes can become wrong.
Cohort studies Successive studies provide different, biased views of one stable disease population. Earlier evidence helps estimate cohorts poorly represented in the current study. Five study blocks, 20 scored instances: measured variables and coding differ. Predictions do not change later patient data, and population-level evaluation scores are not given between instances. This is evidence accumulation, not correction from population-level labels.
Spectrum monitoring Ninety scans reveal parts of one persistent transmitter map. A transmitter seen earlier can remain relevant while silent now. Which transmitters are visible changes; the target transmitter set remains fixed. Reporting a channel map does not change future transmissions. The challenge is remembering incomplete observations, not adapting to a newly created world.
Poker Repeated hands reveal an opponent's policy; previously encountered strategies return, making retained opponent models useful. Over 120 hands, opponent policies switch on a preset schedule. Cards, pot, and stacks reset between hands; previous winnings do not become the next hand's bankroll. Betting changes the current hand, not the opponent-policy schedule.
Sales prediction Twelve rounds expose partial sales data generated by stable demand relationships; observations across stores/years help fit a better forecast model. Visible store, schema, and distractors change. Forecasts do not determine later sales. Workspace files/code/models can persist, so this is not naturally a notes-only comparison.

Sources: paper Appendix A and pinned task implementations. Counts describe default schedules, not every possible variant.

The key distinction: database migration and opponent-policy switches change the environment's rules. In spectrum, cohort, and sales, much of the change is in what the agent can observe about stable underlying structure. Forgetting old evidence can therefore hurt even when the current observation is accurate.

Implication for our memory experiments (our interpretation): codebase/database streams emphasize searchable environment knowledge; poker emphasizes recognizing and recalling an opponent model; spectrum/cohort/sales also demand retained evidence or statistical summaries. A method that stores only reusable “tips” could miss the last group's main learning opportunity. All remain Setting 1 under our definition because each instance has its own prediction/action score—not because their instances are unrelated.

Two implementation details to preserve: sales feedback exposes only the elapsed forecast year, not all five future years. Spectrum's paper describes occupied-spectrum IoU, but the pinned scorer complements occupied intervals and scores available-spectrum IoU. Pin the evaluator before comparing results.

What to measure. The paper compares a stateful system with the same system run statelessly on matched instances. In its notation:

\[ g_t = r_t^{\mathrm{sf}} - r_t^{\mathrm{sl}}, \qquad \widehat g = \frac{\bar r^{\mathrm{sf}}-\bar r^{\mathrm{sl}}}{r_{\max}-\bar r^{\mathrm{sl}}}. \]

Here \(r_t\) is reward on instance \(t\), the bars are averages, and \(r_{\max}\) is the task’s maximum reward. The second quantity expresses improvement relative to remaining headroom. Report raw reward too: near-ceiling denominators make normalized gains fragile.

Sharp takeaway. A rising score is not enough—later instances might simply be easier. A strong absolute score is not enough either—it might come entirely from pretrained ability.

For notes + grep. Add an external-file memory adapter. The paper’s notepad baseline carries notes into context; it is not automatically a filesystem-search baseline. Compare with no persistence and full-history ICL. The reported strength of simple ICL makes it an essential control, not a straw man to omit. The repository supplies containerized tasks and system implementations; domain setup still needs validation.

Setting fit: native across-task learning. For our short-horizon setting, select a domain and predeclare the per-task action/time budget; report observed lengths. Do not pool six domains into one shared memory or silently truncate official tasks to manufacture a short-horizon score.

2. STATE-Bench Agent Learning Track — experience to held-out action

Repository · Learning-track protocol. Priority: core; official release documentation reviewed.

The task, concretely:

  • Given: a simulated customer's request, a task-local database, and tools for inspecting policies/records and changing bookings, orders, or carts.
  • Do: talk to the customer to resolve ambiguity, look up the applicable rules, then perform the authorized operations. Travel covers bookings and changes; support covers refunds/returns/warranties; shopping covers product selection, carts, promotions, and compatibility.
  • Produce and score: the correct final database state and required conversational procedure—not just a plausible answer. Report average completion over five runs (pass@1), success on all five (pass^5), and conversation quality separately. Official task/metric overview.

Released training example, paraphrased: a customer names headphones to cancel, then ambiguously asks to cancel “the accessory,” while keeping the rest of the order. The agent should handle the named item and clarify which accessory before changing it. The released trace instead cancels an accessory prematurely: an apology does not undo the wrong database action. Actual trajectory.

Where memory enters: build reusable lessons from 100 provided training trajectories per domain; evaluate on 50 held-out tasks per domain. The next customer's order details are new, but a lesson about resolving ambiguity before an irreversible action may transfer.

The learning interface is unusually direct: retrieve_learnings(query, top_k=3) returns relevant strings. The official track fixes five runs, top-three retrieval, and the simulator/judge configuration. Retrieval is read-only during evaluation; offline memory construction is up to the researcher.

Setting fit: offline Setting 1. Training-task experience helps other tasks within the benchmark. Freeze memory before held-out evaluation; each test task reads the same artifact rather than learning from preceding test tasks.

Sharp takeaway. This isolates “did prior experience help a new task?” more cleanly than appending a memory store to an unrelated leaderboard. It does not establish continuous online improvement: test-time memory writes would change the official protocol.

For notes + grep. Build query-blind notes from training trajectories, then implement retrieval with lexical search over those files. Compare identical task agents with no retrieval, raw-trajectory search, and distilled-note search. Keep the official hook constraints; free-form shell navigation is a separate variant.

Caution. Task completion, five-run reliability, and judged conversational quality answer different questions. The official cost field need not include offline extraction or embedding costs: add those to the research accounting. Synthetic environments and a fixed LLM judge also deserve spot checks before interpreting small gains.

3. ContinualSkillBench — does experience become a reusable procedure?

Paper, August 2026 · Code. Priority: second wave, especially consolidation.

The task, concretely:

  • Given: one problem, its source material/files, and the agent's current skill library. Each of the paper's five domain streams—healthcare, law, mathematics, finance, and office—contains 100 problems.
  • Do: solve the current problem using the task's tools and required output format; then receive evaluator feedback and optionally create or revise a skill for the next problem.
  • Produce and score: an answer or artifact, not a skill document alone. Short answers use exact match/F1, numerical answers use tolerances, open responses use rubrics, and executable/file tasks use programmatic checks. Protocol and evaluators, §3.

Actual released example, paraphrased: Finance Task 001 supplies a company's balance-sheet excerpt and asks for cash/cash-equivalent amounts for two years, in a specified order. The agent must write a JSON answer file. Other tasks require calculations or a sequence of trading positions; a persuasive narrative cannot replace the requested fields. Released finance task instructions.

Why memory might help: reuse a procedure for reading table units, checking year order, computing a ratio, or validating output—not the previous company's numbers. Tasks are heterogeneous and curated for possible skill reuse, rather than repetitions of one identical workflow.

Setting fit: native Setting 1. Use separate stores for domain streams and independent trials. Log per-task horizon and retain the benchmark's task boundaries; a long sequence of tasks is not one long task.

Insight. Learning a procedure and accumulating task-specific notes are different. Measure skill reuse and the downstream benefit, not the number of files produced. More skills can mean fragmentation rather than better learning.

Caution. Sequential execution combines history, feedback, and explicit skills. In the paper’s three-domain ablation, ordinary ICL and explicit skill maintenance have similar average normalized reward; this is not a universal five-domain conclusion. Preserve matched independent-task baselines, inspect invalid-output handling, and report domain results separately. The deliberately curated ordering is a useful learning opportunity, but not evidence of robustness to arbitrary deployment order.

B. Setting 2 — memory within one super-long-horizon task

The experimental unit is one continuing objective and its terminal evaluation. Sessions, compactions, and subgoals remain inside that unit. Start every independent task/trial with fresh memory; retaining work products inside the task is allowed and must be accounted for. Test complete trajectories, with checkpoint recovery as a diagnostic—not as a substitute for the full task.

4. SWE-Marathon — the main long-task substrate

Paper, June 2026 · Methods and task descriptions · Project/release. Priority: primary Setting 2 candidate; pilot cost and variance first.

The task, concretely:

  • Given: a substantial software specification plus a runnable workspace, task-specific assets, and a multi-hour budget.
  • Do: implement, run, debug, and test the system through many dependent steps. The deliverable is working software or an evaluated ML/optimization artifact—not an explanation of how to build it.
  • Produce and score: submit the finished workspace. Task-specific verifiers test behavior; some product tasks also require browser-based usability checks. The suite contains 20 tasks, with 2–10-hour limits and five trials per agent–model/task combination; four tasks need GPUs.

Actual task, paraphrased: slack-clone. Build a multi-node chat service plus an IRC gateway. Messages must stay consistently ordered across nodes, surviving crashes and a Redis outage. The verifier checks backend correctness and drives the frontend through user workflows; both must pass. A chat screen that looks right but loses messages is not a solution. Task specifications, Appendix C.

What memory must retain: unresolved failures, cross-component contracts, tested assumptions, and which changes are already complete while the same implementation continues.

Important correction. The headline 27.2M tokens per attempt is cumulative input plus output accounting, including cached input. It is not 27.2M unique facts, nor a 27.2M-token simultaneous context window.

Sharp takeaway. A long task can fail because of memory, planning, bad tests, premature stopping, or inability to implement the solution. Low success by itself does not diagnose memory failure.

Our extension. Compare the normal context-management policy, summaries, searchable notes, and source-backed notes over complete task rollouts. Also fork an identical checkpoint; preserve its environment/work products, clear conversational context, and resume under each memory condition. Charge both checkpoint construction and recovery; keep final hidden verifiers inaccessible to the writer. Report final success, total cost, and duplicated work after compaction. These are memory/reset experiments on SWE-Marathon, not an existing official memory leaderboard. Pin release and harness: twenty task identities make uncertainty important, even with repeated rollouts.

Do not mix settings. A new SWE-Marathon task starts with an empty experience store. Carrying notes from earlier benchmark tasks would add Setting 1 and require a separately labeled experiment. Setting 2 can be pursued independently of any cross-task result.

5. MemoryArena — remembering must change what the agent does

Paper, February 2026 · Code. Priority: shorter continuity proxy for Setting 2.

The task, concretely: the agent completes a sequence of dependent sessions, rather than merely answering questions about an old transcript.

  • Shopping: search/click/buy products in WebShop. Later purchases must match earlier ones and satisfy selection rules; the final bundle is checked for compatibility.
  • Group travel: construct itineraries as more travelers join, keeping earlier arrangements and each person's constraints consistent.
  • Progressive search: answer successive searches as new constraints are added; the final answer must satisfy the accumulated conditions.
  • Formal reasoning: solve a chain of mathematical or physics subproblems whose earlier conclusions support the final problem.

Concrete dependency from the benchmark design, paraphrased: after selecting a television, a later shopping session needs a compatible stand. Remembering only “bought a TV” is insufficient; its relevant dimensions and constraints must survive. The agent must actually select the later item, not just recall the earlier purchase. Environment definitions, §3.1.

Setting fit. Use the whole dependent episode as the continuing objective, and reset memory between independent episodes. Session-level subtasks do not make this Setting 1 under our definition. It tests continuity, but does not by itself demonstrate super-long-horizon capability.

Read the score carefully. Partial success counts passed subtasks. Overall success is domain-dependent: shopping/travel check joint constraints; search/formal reasoning depend on the final subtask. “Success” does not mean the identical all-subtasks-pass rule across every domain.

Sharp takeaway. This tests whether memory is usable under action, where a mistaken note can create more mistaken experience. It complements an offline archive benchmark, whose histories are fixed regardless of the candidate memory system.

For notes + grep. Use the memory boundary between sessions, with the same solver and tools. Add an oracle-evidence diagnostic: if even correct evidence does not rescue performance, retrieval may not be the bottleneck. Do not mistake a long dependent workflow for broad transfer to unrelated tasks. The public code calls itself a preview and has separate setup guides for each environment; pilot one domain before committing to all four.

Shared diagnostic: archive retrieval is neither full setting

6. LongMemEval-V2 — closest to a searchable experience archive

Paper, May 2026 · Code and release updates. Priority: shared retrieval diagnostic; paper marked work in progress.

The task, concretely:

  • Given: a pre-collected archive of browser-agent runs, including actions, page observations, and screenshots; later, a question about those customized websites.
  • Do: organize the archive, then retrieve evidence for the new question. In the main evaluation, the memory module returns context to a fixed reader, which answers; it does not return to the live website to perform the workflow.
  • Produce and score: a factual/procedural answer, or an explanation of a false premise. Structured answers use deterministic matching; gotcha and false-premise explanations use a binary LLM judge. There are 451 questions, with histories reaching roughly 500 trajectories and 115M tokens.

Actual example, paraphrased: compare two ServiceNow forms in past screenshots and identify the extra top-right button on the Incident form: Resolve. This requires finding the relevant states, not using generic ServiceNow knowledge. Question examples and scoring.

Why it is particularly relevant. The released baselines include raw retrieval, retrieval plus notes, and AgentRunbook-C, which stores trajectories as files and uses a coding agent with manifests and inspection helpers. This gives notes + search a concrete competitor beyond vector retrieval.

Sharp takeaway. A memory system is a writer and a reader. Better search can rescue an uncompressed archive; clever summaries cannot recover evidence they discarded. Factor the two components rather than attributing every gain to note quality.

Boundary. This is evidence-gathering QA, not a closed-loop agent success test. The paper allows up to 200K returned-context tokens, so it is not already a stringent small-memory test. Sweep smaller budgets explicitly and label that extension. Keep the same downstream reader, compare query latency, and charge preprocessing separately. The August AgentRunbook-C update must not be silently equated with the May paper configuration.

Relationship between instances: questions probe supplied archives of earlier website runs. Answering a question neither resumes those runs nor generates experience required for the next question. Use it to debug archive organization or compression in either setting; archive size alone does not establish a super-long task.

C. Compression: what was lost, and did it matter?

Compression needs a curve, not one ratio: task quality versus retained tokens or KV bytes, plus write/read latency and compute. In Setting 1, the next task is normally unknown when notes are written: preserve reusable knowledge without seeing future requests. In Setting 2, the current objective is already known, so task-aware compression is legitimate—but future observations and hidden grading data are not available. Long-context suites below isolate information loss; neither long input nor a large corpus proves a long action horizon.

7. HELMET — application diversity instead of needle-only confidence

Paper, ICLR 2025 · Code.

The task, concretely: HELMET is seven task families, not one agent workflow. The input may be a large key–value collection, retrieved passages, candidate search results, labeled examples, a novel, or legal documents. Depending on the family, the model must return a value, answer with or without citations, ranked document IDs, a classification label, or a summary.

Actual examples, paraphrased: in its retrieval-augmented QA setup, identify the winner of the 1 February 2015 Australian Open men's final from passages mixed with distractors. In passage reranking, return the ten most relevant passage IDs in order—not an answer to the search query.

Scoring: task-specific: answer matching for retrieval QA, NDCG@10 for ranking, accuracy for classification, model-based judging for NarrativeQA/summaries, and ROUGE F1 for ∞Bench open QA. Memory is the supplied context for that instance; persistent cross-task experience is not native. Task definitions and examples, Table 3 and Appendix E.

Use it for: a common reader with raw context, text summaries, extractive compression, and—where model access permits—learned latent/KV compression. Watch: changing both model and compressor defeats attribution. Holding token count fixed does not hold KV memory or hardware cost fixed across architectures. This is a compression substrate, not a native lifelong-agent protocol.

8. OOLONG — preserve enough information to aggregate, not just retrieve

Paper, November 2025 · Code.

The task, concretely:

  • Given: in OOLONG-synth, many short text records with dates/user IDs plus category definitions. The category of each record must be inferred from its meaning.
  • Do: classify the relevant records, then aggregate: count them, compare categories, or identify a user/date. One official template asks which user has the most records of a specified category. Finding one matching passage cannot establish the maximum.
  • A different concrete task: OOLONG-real supplies Critical Role transcripts; one template asks how many dice rolls were natural 1s or 20s in an episode.
  • Scoring: numeric errors receive exponentially decreasing partial credit; categorical/string answers use exact matching, and real-task lists use set overlap. Several questions can share the same source, but answering one does not provide online learning feedback for the next. Task templates and scoring, §2–3 and Appendix B.

Sharp takeaway. A summary can retain every salient anecdote yet destroy the sufficient statistics for an aggregate question. Test whether notes preserve counts, exceptions, and scope. If a method uses programmatic scans over the full archive, count that access rather than calling the small final prompt the entire memory budget. OOLONG-Pairs, used in RLM work, is a derivative task; keep its results separate from original OOLONG.

9. MemoryAgentBench — incremental memory with several failure types

Paper, ICLR 2026 · Code.

The task, concretely: feed a long source to a memory system one chunk at a time, then ask questions that require the accumulated information. The source is supplied; the agent does not create it by acting in a live environment.

What the questions ask: retrieve facts from documents/conversations; infer classification labels from examples; recommend movies; understand a novel; or answer using the latest facts after earlier facts have been superseded. An actual released document-QA example asks whether Scott Derrickson and Ed Wood share a nationality. A consolidation task instead makes remembering the old answer insufficient: later updates must change the answer. Released data example.

Scoring: varies by subset—answer matching, classification accuracy, recommendation Recall@5, or model-based grading. The output contract matters: classification parsing can reject extra prose around an otherwise correct label. Official metric mapping.

Relationship between instances: successive chunks build knowledge from a supplied source, including updates or labeled examples. Questions test that accumulated knowledge, not lessons from previously completed live agent tasks. Later source chunks are not consequences of the agent's earlier answers.

Caution. Processing a history incrementally is not the same as an agent generating that history through actions. Report the four competency families separately; a compressor that remembers old facts but cannot supersede them may look good in an average while being unsuitable for deployment.

10. LongMemEval V1 — a strong conversational control, not the whole story

Paper, ICLR 2025 · Code and data revisions.

The task, concretely: the system processes timestamped user–assistant chat sessions, then receives a dated question about that user's history. It must answer from the remembered sessions, combine multiple mentions when needed, use updated information rather than superseded facts, or abstain when the requested fact was never supplied.

Actual paper example, paraphrased: on 27 April 2023, the user asks which airline they used most during March and April. The system must recover travel mentions, respect the date range, and aggregate across sessions. The example demonstrates the time filter; the paper's table does not supply the final airline answer.

Scoring: 500 questions, with reference-based GPT-4o judging under question-type-specific instructions; retrieval recall can be measured separately. Memory crosses sessions in the supplied history. The final question comes afterward; this is not a task agent taking new actions. Examples and evaluation, Appendix A.4 and Table 11.

Caution. Conversational QA is not evidence of improved coding or research actions. Pin the cleaned data release; report abstention and update failures rather than only aggregate accuracy. Multiple questions can depend on related histories, so question count need not equal the number of independent experimental units.

11. MemFail — a diagnostic microscope

Paper, May 2026.

The task, concretely: first let the system store facts from ungraded conversations; freeze its memory database; then ask questions in separate conversations. The four task families probe conditional rules, compatible preferences, retrieving the correct person's facts/abstaining, and following a chain of facts stored separately.

Illustrative case from the paper—not a released test row: learning that someone likes pizza, then learning that they like ramen, should retain both preferences. A later question about their food preferences must not treat the newer fact as a replacement. Other tests ask whether a rule applies under a particular condition; Long-Hop asks for the endpoint of a fact chain from five options.

Scoring: check whether required information was written, preserved faithfully, retrieved, and used correctly. Most checks use an LLM judge; Long-Hop's final choice is parsed deterministically. The result localizes failures rather than scoring a completed research/coding project. Task families and evaluators, §4–5 and Appendix D.

Borrow the distinction: mutually exclusive updates should replace old state; coexisting facts should accumulate. “Always overwrite” and “never forget” each fail for different reasons. Treat the authors’ observed system failures as findings for their tested configurations, not permanent architectural impossibility claims.

12. Memory portability — do another model and a later version understand the notes?

Study, September 2026.

The task, concretely: a writer processes one of 48 scripted histories into raw text, a retrieval index, notes, or a fixed-schema graph. A reader answers 160 questions per history. Then a component changes—reader, writer, or embedding configuration—and the same questions test whether the inherited memory still works.

Illustrative example from the paper—not a released test row: a history specifies a project's Friday deadline. After a model swap, can the new reader recover that deadline from the previous writer's representation? The actual evaluation covers temporal updates, contradictions, relationships, and aliases; answer values are randomized codes scored by exact match.

Scoring: compare inherited-store accuracy with that reader's own-store accuracy, and measure repair cost. This is a controlled migration study, not a live task benchmark: two sub-10B models, synthetic histories, and artifacts available upon request rather than a verified public turnkey suite. Protocol and availability statement.

Protocol to borrow: cross writer A/B with reader A/B; separately change the embedder; then try repair with and without the raw source. If only the original writer can use its notes, the system has acquired a hidden interface dependency. Keep raw evidence where feasible: store-only rewriting cannot recreate a discarded fact.

D. Broader work: research, professional tasks, and enterprise agents

These are not all native memory benchmarks. They test whether a memory improvement survives contact with useful work. For Setting 1, define a sequence of separately scored tasks within the chosen benchmark and an explicit opportunity for reusable experience. For Setting 2, select a genuinely extended, single-objective trajectory and report its action/time horizon. A 100M-token corpus or difficult question alone does not establish that horizon. These are adaptations unless stated otherwise.

13. Harvey Legal Agent Bench — work products, not isolated legal QA

Original release · Code, tasks, and evaluation. Priority: professional-work extension; cost pilot required.

The task, concretely:

  • Given: a partner's assignment and a matter filesystem containing contracts, correspondence, templates, and irrelevant material.
  • Do: inspect/search the files, analyze the matter, and write the requested professional deliverable. The standard harness offers shell and file tools, including grep.
  • Actual example, paraphrased: review eight contracts for change-of-control risks in the fictional acquisition of Crestview Software Solutions. Write a memorandum identifying contract-specific risks, financial exposure, and mitigations—not just a list of retrieved clauses.
  • Scoring: that example has 57 binary rubric criteria covering nine planted issues. All-pass requires every criterion; criterion-level scores show partial progress. Official example and grading · Agent tool interface.

Relationship between instances: base LAB scores separate assignments over supplied matter files; the Law Firm Knowledge variant below shares one firm corpus across requests. Neither natively makes the agent's answer to one request a prerequisite for the next. Carrying lessons between assignments would be our extension.

Version trap. The launch described 1,250 tasks. The repository inspected for this review describes 1,671. Trajectory’s report uses a 120-task holdout. These are not interchangeable denominators or directly comparable protocols.

Memory extension. Group allowed inputs by matter or organization, construct notes without seeing future requests, and evaluate on held-out matters or requests with the same agent. Prevent source-document or rubric leakage across the split. Generic task improvements do not automatically demonstrate persistent memory.

Particularly relevant variant: Law Firm Knowledge. Its synthetic firm corpus spans 9,288 files and 108M tokens, with 250 tasks. This is a compelling setting for searchable notes, corpus compression, and amortization over many queries. Repeated use of one corpus is still reuse, not necessarily learning online. Broad corpus access, parsing, and rubric judging make a full run a potentially substantial project; no all-in cost was reproduced here.

What a firm-knowledge task asks: search the shared firm corpus to reconstruct precedents, client preferences, patterns, or matter outcomes, then answer against task-specific rubrics. Illustrative request—not a verified released question: find all matters with both a 10% escrow and a two-year non-compete, with supporting documents. 14. BrowseComp-Plus — research with a fixed evidence collection

Paper · Code. Priority: research-agent extension.

The task, concretely:

19. Mem2ActBench — the small bridge from recall to action

Paper, ACL 2026 · Code.

The task, concretely:

  • Given: a prepared conversation/tool history containing preferences, updates, and distractions; then an underspecified request and tool information.
  • Do: retrieve the missing constraints and put them into a structured tool call. In the paper's main comparison, the correct tool is supplied, so the central test is filling its arguments from memory.
  • Official illustrative example: an earlier interaction establishes a $500 flight budget; a later request refers back to it. The call must use the remembered value, such as price=500, rather than ask the user to repeat it or invent another budget.
  • Scoring: 400 tasks, with parameter F1, BLEU-1, and the authors' Tool Accuracy metric. The output is a generated call—not a verified completed booking in a live environment. Task definition, examples, and metrics.

Relationship between instances: each request uses supplied historical conversations and recorded tool interactions. It does not depend on tool calls generated by the evaluated agent for earlier benchmark requests. Treat Tool Accuracy as a call-level metric, not end-to-end action success; check the pinned evaluator alongside parameter F1.

Why keep it: “Can state be recalled?” and “Does the correct value reach the tool argument?” are different tests. This is a focused probe of that gap, with less scope than a full enterprise environment. It is not a substitute for an online, self-generated multi-session trajectory, and synthetic consistency may underrepresent messy real histories.

E. Your other pointers: useful, but different kinds of evidence

Reef — learning-loop infrastructure, not a benchmark

Code and recipes.

Reef connects serving, feedback collection, learning, candidate evaluation, and versioned updates. It supports recipes that change weights and recipes that improve a harness around a frozen API. This is relevant to both inner-agent memory and an eventual outer optimizer.

What is the task? Reef does not prescribe one common task or success test. You supply the environment/task stream and evaluator; Reef runs the learning/update machinery around them. A Reef recipe's score therefore needs the underlying task and evaluation protocol attached.

What to borrow. Keep feedback traceable to the experience that produced it; evaluate a candidate before replacing the serving version; retain the artifact and evaluator version. These are useful system-design ideas independently of any particular recipe’s score.

What not to infer. A tutorial’s few passing coding tasks are not broad learning evidence. Repeated optimization of one scientific problem, learning across a task stream, and improving from simulated user feedback are different protocols. Choose the benchmark and untouched evaluation split separately. Reef is optional infrastructure for that experiment, not a prerequisite for notes + grep.

Trajectory’s “cheap enough to meter” — a provider report to interrogate

The report describes post-training on legal work and evaluating a 120-task Harvey LAB holdout: the task is still produce a legal work product from a matter's files, as in the Harvey entry above, not answer a separate memory quiz. It reports an 8.3% all-pass rate and reducing average output from about 90K to 37K tokens per task while preserving the same ten all-pass tasks across the two trained variants.

The relevant idea is quality per unit of compute. But shorter generated reasoning is not demonstrated context compression, and a trained policy is not evidence that persistent notes caused the gain. These are provider-reported results; this review does not reproduce the training recipe, data separation, or full cost accounting.

For our research, retain all-pass and criterion diagnostics, then add ingestion, memory maintenance, training amortization, and inference cost. “No regression” on five tasks per practice area is weak evidence about that entire area. retention-bench — borrow the reset boundary, not a headline result

Repository.

The authors describe this as a workbench, using a CL-Bench runner and explicit process resets. Only declared persistent state survives; controls include clearing that state and avoiding resets. That boundary is directly useful for testing whether an apparent memory gain is actually hidden process/session state.

Treat it as exploratory instrumentation, not an independently validated benchmark standard. Its small example runs do not establish broad capability. Pin the underlying CL-Bench dependency, and check that a no-reset control does not enjoy an unreported compute or information advantage.

F. Turn these readings into a fair experiment

Start small without narrowing the research question

Run two independent pilots:

  • Setting 1: one CL-Bench domain stream with measured per-task horizons; add STATE-Bench for an explicitly offline held-out variant or ContinualSkillBench for consolidation. Do not combine their scores into one learning number.
  • Setting 2: a predeclared SWE-Marathon task subset, with complete rollouts and a few paired checkpoints. MemoryArena can debug continuity more cheaply, but does not replace the long-task endpoint.

Use LongMemEval-V2 to diagnose search and HELMET/OOLONG to diagnose compression in parallel. Neither primary setting must succeed before the other is worth studying.

“Pilot” means a predeclared subset for integration, cost, and variance estimates—not a new official benchmark score. There is no verified dollar estimate in this review; measure one before committing to full runs.

For Setting 1, the minimal online loop is:

Choose one benchmark stream, order, feedback rules, budgets, and seeds.
Initialize an empty declared memory store for each method and stream.
For each separately scored task in that stream:
    Reset task-local context and environment as the benchmark requires.
    Solve using only current inputs and allowed prior-task memory.
    Score the task before writing lessons from its permitted feedback.
    Update memory without seeing the next task or hidden grading data.
    Charge solving, note-writing, indexing, retrieval, and maintenance.
Compare with the matched stateless run on the same task schedule.
Repeat independent streams; report gains, costs, and uncertainty.

For a Setting 2 checkpoint diagnostic, a minimal loop is:

Choose tasks, reset points, budgets, and seeds before running.
Run to a checkpoint using only allowed task-visible information.
Snapshot environment and work products; protect hidden grading data.
Branch the same checkpoint into the declared memory conditions.
Construct each memory from the same allowed pre-reset observations.
Charge any summarization, indexing, and note-writing work.
Clear model context, session handles, caches, and undeclared state.
Restore the same environment checkpoint in each branch.
Resume with the condition's allowed read interface and budget.
Keep post-reset work and task verification identical in scope.
Record task quality, repeated work, reads, latency, tokens, and cost.
Repeat across tasks and seeds; report paired differences and uncertainty.

This fixed-checkpoint test isolates recovery. It cannot measure how a memory system would have changed earlier behavior. Also run a complete closed-loop task where each system writes and acts throughout the trajectory, including repeated compactions and delayed dependencies. Diverging experiences are then part of the outcome, not a reason to force identical actions. Compare the normal context-management policy too; forced resets are a stress test, not the definition of Setting 2. Clear all cross-task memory before the next independent task/trial.

Six traps worth discussing in reading group

  1. What survives the reset? Repository files, browser state, caches, server-side session IDs, and tool logs can all act as memory. A context reset is not necessarily a memory reset.
  2. What was the writer allowed to know? In Setting 1, future task requests are hidden; in Setting 2, the current objective is known. Neither grants future observations or hidden graders. Post-task feedback and task-aware compression are different information regimes.
  3. What is the memory unit? Disk bytes, prompt tokens, GPU KV bytes, and trained weights are different resources. A tiny prompt backed by an unlimited searchable archive is not source-free compression.
  4. What did the extra compute buy? Extra exploration can help before any note is written. Charge write, index, search, maintenance, and training costs; report amortization assumptions rather than hiding them in “offline.”
  5. What is the independent unit? Correlated questions, repeated seeds, and tasks from one environment do not provide interchangeable evidence. Use paired comparisons and uncertainty clustered by task/history where appropriate.
  6. Was the test used to improve the method? A memory or outer optimizer can overfit the acceptance set. Keep development feedback separate from untouched final evaluation, and report backward retention as well as forward gains.
