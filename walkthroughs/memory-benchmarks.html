Memory & Continual Learning: Benchmark Review

23 min · 15 papers · 2026-09-15

A guided review of 15 papers plus benchmark releases, infrastructure, and a field report. Source cut: 15 September 2026. Recommendations and experimental extensions are my synthesis—not reproduced results.

Companions: memory methods · baseline experiments. This page asks a different question: what evidence would convince us that a memory system is actually useful?

The two-minute version

Start with LongMemEval-V2 → STATE-Bench’s Agent Learning Track → CL-Bench. They form a useful evidence ladder: can the system recover experience, can that experience improve actions on held-out tasks, and can it improve while encountering a stream of tasks? Add MemoryArena for dependent sessions and HELMET + OOLONG for compression. SWE-Marathon is a later, expensive horizon stress test—not the only definition of agent memory.

The most important distinction is between remembering an answer, using experience, and learning online. A system can be excellent at the first and poor at the others. Equally, a good task solver can hide a bad memory module by re-solving everything.

Reading routes: decision map · continual learning · notes, search, and resumption · compression · non-coding work · Reef and Trajectory · fair experiments · versions and readiness.

Choose the claim, then the benchmark

Claim we want evidence for Strong starting point Boundary of the evidence
Search a large archive of past agent experience LongMemEval-V2 Answers questions; does not execute the next live task
Turn past experience into better new-task actions STATE-Bench Learning Track Offline extraction and read-only test retrieval, not ongoing online updates
Improve through sequential feedback CL-Bench, ContinualSkillBench Must compare with a matched stateless agent, not just an upward score curve
Carry information between dependent sessions MemoryArena Workflow continuity is not necessarily transfer to independent new tasks
Sustain work through a very long task SWE-Marathon Controlled reset/resume is an extension we would add
Preserve useful information with less context HELMET, OOLONG, MemoryAgentBench Compression is not automatically continual learning
Use memory for real work beyond coding LAB, HANDBOOK.md, τ³-Banking Native versions generally do not isolate learned persistent memory

Why use a portfolio? Recall exposes missing information; action exposes unusable information; a task stream exposes failure to update; compression exposes the quality–resource trade-off. One aggregate leaderboard cannot identify all four failures.

A. Does experience improve later tasks?

1. CL-Bench — the anchor for online learning

Paper, June 2026 · Methods · Code. Priority: core.

Walkthrough. The agent encounters successive instances sharing something learnable: a codebase’s organization, database structure, outbreak dynamics, radio signals, demand patterns, or an opponent’s strategy. It acts, receives feedback, and carries state forward. Domain variants can change the underlying structure, so remembering and revising both matter.

What to measure. The paper compares a stateful system with the same system run statelessly on matched instances. In its notation:

\[ g_t = r_t^{\mathrm{sf}} - r_t^{\mathrm{sl}}, \qquad \widehat g = \frac{\bar r^{\mathrm{sf}}-\bar r^{\mathrm{sl}}}{r_{\max}-\bar r^{\mathrm{sl}}}. \]

Here \(r_t\) is reward on instance \(t\), the bars are averages, and \(r_{\max}\) is the task’s maximum reward. The second quantity expresses improvement relative to remaining headroom. Report raw reward too: near-ceiling denominators make normalized gains fragile.

Sharp takeaway. A rising score is not enough—later instances might simply be easier. A strong absolute score is not enough either—it might come entirely from pretrained ability.

For notes + grep. Add an external-file memory adapter. The paper’s notepad baseline carries notes into context; it is not automatically a filesystem-search baseline. Compare with no persistence and full-history ICL. The reported strength of simple ICL makes it an essential control, not a straw man to omit. The repository supplies containerized tasks and system implementations; domain setup still needs validation.

2. STATE-Bench Agent Learning Track — experience to held-out action

Repository · Learning-track protocol. Priority: core; official release documentation reviewed.

Walkthrough. For each of travel, customer support, and shopping, use 100 provided training trajectories to build a memory artifact. Evaluate on 50 held-out tasks per domain. The agent must gather information, follow policy, and take appropriate actions; remembering a fact alone is not the endpoint.

The learning interface is unusually direct: retrieve_learnings(query, top_k=3) returns relevant strings. The official track fixes five runs, top-three retrieval, and the simulator/judge configuration. Retrieval is read-only during evaluation; offline memory construction is up to the researcher.

Sharp takeaway. This isolates “did prior experience help a new task?” more cleanly than appending a memory store to an unrelated leaderboard. It does not establish continuous online improvement: test-time memory writes would change the official protocol.

For notes + grep. Build query-blind notes from training trajectories, then implement retrieval with lexical search over those files. Compare identical task agents with no retrieval, raw-trajectory search, and distilled-note search. Keep the official hook constraints; free-form shell navigation is a separate variant.

Caution. Task completion, five-run reliability, and judged conversational quality answer different questions. The official cost field need not include offline extraction or embedding costs: add those to the research accounting. Synthetic environments and a fixed LLM judge also deserve spot checks before interpreting small gains.

3. ContinualSkillBench — does experience become a reusable procedure?

Paper, August 2026 · Code. Priority: second wave, especially consolidation.

Five streams—healthcare, law, mathematics, finance, and office—each contain 100 tasks, ordered for increasing difficulty and possible skill reuse. After task feedback, the agent may create or revise skills for later tasks. Evaluation mixes exact, numerical, rubric, and programmatic scoring.

Insight. Learning a procedure and accumulating task-specific notes are different. Measure skill reuse and the downstream benefit, not the number of files produced. More skills can mean fragmentation rather than better learning.

Caution. Sequential execution combines history, feedback, and explicit skills. In the paper’s three-domain ablation, ordinary ICL and explicit skill maintenance have similar average normalized reward; this is not a universal five-domain conclusion. Preserve matched independent-task baselines, inspect invalid-output handling, and report domain results separately. The deliberately curated ordering is a useful learning opportunity, but not evidence of robustness to arbitrary deployment order.

B. Can an agent find and use its past experience?

4. LongMemEval-V2 — closest to a searchable experience archive

Paper, May 2026 · Code and release updates. Priority: core; paper marked work in progress.

Walkthrough. Insert histories of web/enterprise agent trajectories into memory. Then ask a question about a local workflow, changing state, interface detail, recurring trap, or mistaken assumption. The memory system gathers evidence, and a fixed reader answers. There are 451 manually curated questions, with histories reaching roughly 500 trajectories and 115M tokens. Histories include screenshots—not just plain text.

Why it is particularly relevant. The released baselines include raw retrieval, retrieval plus notes, and AgentRunbook-C, which stores trajectories as files and uses a coding agent with manifests and inspection helpers. This gives notes + search a concrete competitor beyond vector retrieval.

Sharp takeaway. A memory system is a writer and a reader. Better search can rescue an uncompressed archive; clever summaries cannot recover evidence they discarded. Factor the two components rather than attributing every gain to note quality.

Boundary. This is evidence-gathering QA, not a closed-loop agent success test. The paper allows up to 200K returned-context tokens, so it is not already a stringent small-memory test. Sweep smaller budgets explicitly and label that extension. Keep the same downstream reader, compare query latency, and charge preprocessing separately. The August AgentRunbook-C update must not be silently equated with the May paper configuration.

5. MemoryArena — remembering must change what the agent does

Paper, February 2026 · Code. Priority: core for dependent sessions.

Walkthrough. Solve interconnected subtasks across sessions in bundled shopping, group travel, progressive information search, and formal reasoning. Earlier actions and observations supply information needed later. Memory is accumulated within the episode instead of treating all questions as independent recall tests.

Read the score carefully. Partial success counts passed subtasks. Overall success is domain-dependent: shopping/travel check joint constraints; search/formal reasoning depend on the final subtask. “Success” does not mean the identical all-subtasks-pass rule across every domain.

Sharp takeaway. This tests whether memory is usable under action, where a mistaken note can create more mistaken experience. It complements an offline archive benchmark, whose histories are fixed regardless of the candidate memory system.

For notes + grep. Use the memory boundary between sessions, with the same solver and tools. Add an oracle-evidence diagnostic: if even correct evidence does not rescue performance, retrieval may not be the bottleneck. Do not mistake a long dependent workflow for broad transfer to unrelated tasks. The public code calls itself a preview and has separate setup guides for each environment; pilot one domain before committing to all four.

6. SWE-Marathon — stress the working state of a long-running agent

Paper, June 2026 · Methods and task descriptions · Project/release. Priority: horizon stress test after cheaper diagnostics.

Walkthrough. Twenty tasks cover library reproduction, product clones, ML engineering, and optimization. Executable environments and layered verifiers assess the resulting work. The paper uses five trials per agent–model/task combination, with per-task limits of 2–10 hours; four tasks need GPUs.

Important correction. The headline 27.2M tokens per attempt is cumulative input plus output accounting, including cached input. It is not 27.2M unique facts, nor a 27.2M-token simultaneous context window.

Sharp takeaway. A long task can fail because of memory, planning, bad tests, premature stopping, or inability to implement the solution. Low success by itself does not diagnose memory failure.

Our extension. Fork an identical task checkpoint; preserve its environment/work products, clear conversational context, and resume with either no notes, a summary, or searchable notes. Count the cost of reaching the checkpoint as well as recovery. Keep final hidden verifiers inaccessible to the writer. Report end-to-end success and duplicated work after reset. This is a reset experiment on SWE-Marathon, not an existing official reset leaderboard. Pin release and harness: twenty task identities also make uncertainty important, even with repeated rollouts.

C. Compression: what was lost, and did it matter?

Compression needs a curve, not one ratio: task quality versus retained tokens or KV bytes, plus write/read latency and compute. Distinguish query-aware compression (the question is already known) from query-blind memory (future questions are unknown). The latter is the relevant default for notes saved for a new task.

7. HELMET — application diversity instead of needle-only confidence

Paper, ICLR 2025 · Code.

Seven long-context task categories provide configurable lengths and application-oriented evaluations. The paper finds synthetic needle-style performance is a poor proxy for downstream capabilities. Use retrieval, long-document understanding, and summarization tasks to catch different losses.

Use it for: a common reader with raw context, text summaries, extractive compression, and—where model access permits—learned latent/KV compression. Watch: changing both model and compressor defeats attribution. Holding token count fixed does not hold KV memory or hardware cost fixed across architectures. This is a compression substrate, not a native lifelong-agent protocol.

8. OOLONG — preserve enough information to aggregate, not just retrieve

Paper, November 2025 · Code.

Tasks require reasoning and aggregation across long collections, including semantically classifying records before combining them. This makes it a useful counterweight to sparse-fact retrieval: an excellent search system can still miss evidence needed for a count or comparison.

Sharp takeaway. A summary can retain every salient anecdote yet destroy the sufficient statistics for an aggregate question. Test whether notes preserve counts, exceptions, and scope. If a method uses programmatic scans over the full archive, count that access rather than calling the small final prompt the entire memory budget. OOLONG-Pairs, used in RLM work, is a derivative task; keep its results separate from original OOLONG.

9. MemoryAgentBench — incremental memory with several failure types

Paper, ICLR 2026 · Code.

This combines converted long-context datasets and constructed tasks to test accurate retrieval, test-time learning, long-range understanding, and selective forgetting through incremental interactions. It is a useful controlled screen for a writer/compressor before adding expensive live environments.

Caution. Processing a history incrementally is not the same as an agent generating that history through actions. Report the four competency families separately; a compressor that remembers old facts but cannot supersede them may look good in an average while being unsuitable for deployment.

10. LongMemEval V1 — a strong conversational control, not the whole story

Paper, ICLR 2025 · Code and data revisions.

Five hundred questions probe extraction, multi-session reasoning, updates, temporal reasoning, and abstention over user–assistant histories. Retain it for comparison with established memory methods and to test whether compression loses dates, provenance, or changed preferences.

Caution. Conversational QA is not evidence of improved coding or research actions. Pin the cleaned data release; report abstention and update failures rather than only aggregate accuracy. Multiple questions can depend on related histories, so question count need not equal the number of independent experimental units.

11. MemFail — a diagnostic microscope

Paper, May 2026.

Targeted cases expose different failures in faithful storage, conditional details, coexisting facts, updates, and retrieval/reasoning. Use this to understand a loss seen on larger suites: did summarization erase a condition, or did the reader fail to retrieve a retained fact?

Borrow the distinction: mutually exclusive updates should replace old state; coexisting facts should accumulate. “Always overwrite” and “never forget” each fail for different reasons. Treat the authors’ observed system failures as findings for their tested configurations, not permanent architectural impossibility claims.

12. Memory portability — do another model and a later version understand the notes?

Study, September 2026.

The study compares raw histories, retrieval, natural-language notes, and a fixed-schema graph under component changes. Its scope is small: 48 synthetic histories and two sub-10B open-weight models. It is inspiration for migration testing, not frontier-model validation.

Useful extension: cross writer A/B with reader A/B; separately change the embedder; then try repair with and without the raw source. If only the original writer can use its notes, the system has acquired a hidden interface dependency. Keep raw evidence where feasible: store-only rewriting cannot recreate a discarded fact.

D. Broader work: research, professional tasks, and enterprise agents

These are not all native memory benchmarks. They test whether a memory improvement survives contact with useful work. The adaptation must make the opportunity to reuse information explicit, rather than merely adding a notes tool and hoping it matters.

13. Harvey Legal Agent Bench — work products, not isolated legal QA

Original release · Code, tasks, and evaluation. Priority: professional-work extension; cost pilot required.

Tasks provide a request and matter files and ask for a professional deliverable. Expert-authored criteria grade the result; all-pass requires every criterion to pass. This makes the metric strict but can obscure meaningful partial progress. Report official all-pass alongside criterion-level diagnostics, not a substitute score mislabeled as all-pass.

Version trap. The launch described 1,250 tasks. The repository inspected for this review describes 1,671. Trajectory’s report uses a 120-task holdout. These are not interchangeable denominators or directly comparable protocols.

Memory extension. Group allowed inputs by matter or organization, construct notes without seeing future requests, and evaluate on held-out matters or requests with the same agent. Prevent source-document or rubric leakage across the split. Generic task improvements do not automatically demonstrate persistent memory.

Particularly relevant variant: Law Firm Knowledge. Its synthetic firm corpus spans 9,288 files and 108M tokens, with 250 tasks. This is a compelling setting for searchable notes, corpus compression, and amortization over many queries. Repeated use of one corpus is still reuse, not necessarily learning online. Broad corpus access, parsing, and rubric judging make a full run a potentially substantial project; no all-in cost was reproduced here.

14. BrowseComp-Plus — research with a fixed evidence collection

Paper · Code. Priority: research-agent extension.

Unlike live-web BrowseComp, this supplies a fixed corpus with human-verified supporting documents and hard negatives. That lets us study retrieval, citation, and context management without changing search-engine results confounding each run.

Experiment to borrow. Compare query-time raw search with query-blind precomputed notes and compressed corpus representations. Evaluate answer quality and evidence support, and amortize ingestion over the number of queries actually served. Make clear whether the agent can reopen original documents: recoverable compression and source-free compression are different problems.

Scaling watchlist: BrowseCompPlusCM, August 2026, projects the task into a much larger corpus but retains a smaller fully grounded question set. Interesting for extreme-scale retrieval; not automatically a better first measurement because bigger corpora do not supply more independent questions.

15. HANDBOOK.md — when remembered policy becomes dangerous

Official release and code · Project.

Enterprise tasks require consulting extensive policies while using tools across finance, medical billing, insurance, logistics, and HR. Crucially, task-specific handbooks alter rules and thresholds from base handbooks: yesterday’s rule can be wrong today.

Sharp takeaway. A good procedural memory says where and how to check the current policy, not merely what the old policy said. This is a strong stress test for overgeneralized notes and lossy policy summaries.

Use the current handbook as authoritative, retain source/version pointers in notes, and measure harmful stale-rule reuse as well as success. The release includes containerized tasks and a Harbor/OpenHands-based harness. Cross-task persistence is an experimental extension, and the changed policies mean naïvely sharing notes can legitimately make performance worse.

16. τ³-Banking — retrieval followed by policy-compliant action

Official repository and release notes.

The banking_knowledge domain combines simulated customer interaction, domain tools, and knowledge retrieval, with configurable RAG and shell-based search. This gives notes/search a non-coding action endpoint. Pin agent, user simulator, retriever, and tool configuration; improving document access and improving dialogue policy are different interventions.

Version trap. The official v1.0.1 update corrected banking tasks and changed grades; earlier scores are not directly comparable. Also distinguish one-run success from reliability across repeated runs. It is not a native cross-task learning stream: treat persistent notes across customers as a separate, privacy-scoped extension, and never let one customer’s private facts become another customer’s memory.

17. EnterpriseOps-Gym — remember workflow structure, verify final state

Paper, March 2026 · Code.

Containerized enterprise environments cover eight domains including email, calendars, IT service management, and cross-domain work. SQL verifiers inspect final database state rather than demanding one prescribed action sequence.

Useful distinction. The environment is stateful; that does not mean the agent is learning across tasks. Add memory as a controlled intervention with separately reset environments. Reusable schema/tool knowledge is promising; stale record IDs are not. Pin available split, database snapshots, tool-discovery mode, and image digests. The paper’s full task collection and the publicly runnable subset must not be silently treated as the same evaluation.

18. LABBench2 — a scientific-research generalization check

Paper, April 2026 · Code.

Applied-biology research tasks provide a broader scientific endpoint, including literature, tables, figures, and source-quality assessment. The harness distinguishes file, text-injection, and retrieval modes; different modes expose different information and tools.

Use it for: testing whether corpus notes or compression help scientific evidence handling beyond software. Watch: multimodal assets, gated data access, and runner-dependent filesystem support. Run the text-oriented families first if implementation simplicity matters, while labeling the subset honestly. The native benchmark does not itself establish cross-task continual learning. Do not confuse LABBench2 with Harvey’s Legal Agent Bench.

19. Mem2ActBench — the small bridge from recall to action

Paper, ACL 2026 · Code.

Four hundred tool-use tasks test whether an agent implicitly applies remembered preferences and state to tool selection and parameter grounding. Histories are synthesized from heterogeneous sources; the paper reports human checks of memory dependence.

Why keep it: “Can state be recalled?” and “Does the correct value reach the tool argument?” are different tests. This is a focused probe of that gap, with less scope than a full enterprise environment. It is not a substitute for an online, self-generated multi-session trajectory, and synthetic consistency may underrepresent messy real histories.

E. Your other pointers: useful, but different kinds of evidence

Reef — learning-loop infrastructure, not a benchmark

Code and recipes.

Reef connects serving, feedback collection, learning, candidate evaluation, and versioned updates. It supports recipes that change weights and recipes that improve a harness around a frozen API. This is relevant to both inner-agent memory and an eventual outer optimizer.

What to borrow. Keep feedback traceable to the experience that produced it; evaluate a candidate before replacing the serving version; retain the artifact and evaluator version. These are useful system-design ideas independently of any particular recipe’s score.

What not to infer. A tutorial’s few passing coding tasks are not broad learning evidence. Repeated optimization of one scientific problem, learning across a task stream, and improving from simulated user feedback are different protocols. Choose the benchmark and untouched evaluation split separately. Reef is optional infrastructure for that experiment, not a prerequisite for notes + grep.

Trajectory’s “cheap enough to meter” — a provider report to interrogate

Field report, August 2026.

The report describes post-training on legal work and evaluating a 120-task Harvey LAB holdout. It reports an 8.3% all-pass rate and reducing average output from about 90K to 37K tokens per task while preserving the same ten all-pass tasks across the two trained variants.

The relevant idea is quality per unit of compute. But shorter generated reasoning is not demonstrated context compression, and a trained policy is not evidence that persistent notes caused the gain. These are provider-reported results; this review does not reproduce the training recipe, data separation, or full cost accounting.

For our research, retain all-pass and criterion diagnostics, then add ingestion, memory maintenance, training amortization, and inference cost. “No regression” on five tasks per practice area is weak evidence about that entire area. Avoid interpreting the vendor’s model comparison as a controlled ablation of memory.

retention-bench — borrow the reset boundary, not a headline result

Repository.

The authors describe this as a workbench, using a CL-Bench runner and explicit process resets. Only declared persistent state survives; controls include clearing that state and avoiding resets. That boundary is directly useful for testing whether an apparent memory gain is actually hidden process/session state.

Treat it as exploratory instrumentation, not an independently validated benchmark standard. Its small example runs do not establish broad capability. Pin the underlying CL-Bench dependency, and check that a no-reset control does not enjoy an unreported compute or information advantage.

F. Turn these readings into a fair experiment

Start small without narrowing the research question

My suggested first portfolio is LongMemEval-V2 small-tier pilot + STATE-Bench Learning Track pilot + a CL-Bench stream. It separates evidence retrieval, held-out action, and online adaptation. Add MemoryArena when session dependencies matter. Run HELMET/OOLONG alongside, not only after coding succeeds, if compression is a main contribution. Promote SWE-Marathon after establishing a cheaper signal.

“Pilot” means a predeclared subset for integration, cost, and variance estimates—not a new official benchmark score. There is no verified dollar estimate in this review; measure one before committing to full runs.

A clean notes + grep comparison

Condition What persists Question it answers
No persistence Nothing beyond allowed task/environment state Is past experience needed?
Full history, where feasible Prior context under the declared context limit Can ordinary ICL already solve it?
Raw archive + search Exact allowed observations and feedback Is note-taking needed beyond competent search?
Running summary A bounded summary Does simpler compression suffice?
Notes + grep Model-written notes with source references Does abstraction help quality or search cost?
Notes + source fallback Notes plus recoverable raw evidence Is the failure irreversible loss or poor access?

These are proposed interventions, not six official baselines shared by every benchmark. Use each benchmark’s permitted interface. Keep model, tools, inference effort, feedback access, and evaluator fixed; also compare quality–cost frontiers, since equal prompt tokens alone are not equal compute.

For a reset/resume extension, a minimal loop is:

Choose tasks, reset points, budgets, and seeds before running.
Run to a checkpoint using only allowed task-visible information.
Snapshot environment and work products; protect hidden grading data.
Branch the same checkpoint into the declared memory conditions.
Construct each memory from the same allowed pre-reset observations.
Charge any summarization, indexing, and note-writing work.
Clear model context, session handles, caches, and undeclared state.
Restore the same environment checkpoint in each branch.
Resume with the condition's allowed read interface and budget.
Keep post-reset work and task verification identical in scope.
Record task quality, repeated work, reads, latency, tokens, and cost.
Repeat across tasks and seeds; report paired differences and uncertainty.

This fixed-checkpoint test isolates recovery. It cannot measure how a memory system would have changed earlier behavior. Follow it with a closed-loop test where each system writes and acts throughout the trajectory. Diverging experiences are then part of the outcome, not a reason to force identical actions.

Six traps worth discussing in reading group

  1. What survives the reset? Repository files, browser state, caches, server-side session IDs, and tool logs can all act as memory. A context reset is not necessarily a memory reset.
  2. What was the writer allowed to know? Query-aware compression, query-blind notes, post-task feedback, and access to final rubrics are different information regimes. Hold out future questions and hidden graders.
  3. What is the memory unit? Disk bytes, prompt tokens, GPU KV bytes, and trained weights are different resources. A tiny prompt backed by an unlimited searchable archive is not source-free compression.
  4. What did the extra compute buy? Extra exploration can help before any note is written. Charge write, index, search, maintenance, and training costs; report amortization assumptions rather than hiding them in “offline.”
  5. What is the independent unit? Correlated questions, repeated seeds, and tasks from one environment do not provide interchangeable evidence. Use paired comparisons and uncertainty clustered by task/history where appropriate.
  6. Was the test used to improve the method? A memory or outer optimizer can overfit the acceptance set. Keep development feedback separate from untouched final evaluation, and report backward retention as well as forward gains.

Before accepting a benchmark, verify the complete data/scorer path and license, pin the canonical configuration, run a small cost-and-variance pilot, and inspect whether failures actually involve memory. Unknown cost is unknown—not zero, and not automatically prohibitive. Prefer complementary failure modes over collecting many nearly redundant leaderboards.

If you remember three things

  1. Find experience → use experience → improve with experience are three separate tests. LongMemEval-V2, STATE-Bench, and CL-Bench make that distinction tangible.
  2. Compression must preserve what future work needs, not just what reads like a good summary. Include aggregation, updates, stale-policy traps, and non-coding action.
  3. A benchmark name is not a protocol. Versions, information boundaries, reset semantics, costs, and controls determine what a score actually means.
