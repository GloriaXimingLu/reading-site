Implementing MemRL: candidate filtering, value-aware retrieval, and reward updates

6 min · 1 implementation chapter · 2026-09-21

All memory methods · Short overview

What you are building

Build an experience retriever with a learned utility attached to each memory. The solver model stays frozen. A task outcome changes which memories are likely to be used next time.

There are two explicit implementation targets: the paper's normalized similarity-plus-utility selection, and the pinned release's Q-sorted epsilon-greedy selector. We implement the paper's deterministic ranking below, then identify the code variant. Never combine them accidentally.

Step 1 — Store intent, experience, and utility separately

memory = {
    "id": "B",
    "intent": "Move an object to a destination",
    "embedding": [0.7, 0.7141428429],
    "experience": "Inspect the destination before attempting placement.",
    "q": 0.4
}

The embedding supports relevance filtering. The experience is the text injected into the solver. Q is an estimate of the return obtained when that experience is used, not a score computed by asking the model whether the prose sounds good.

Your durable store needs to update Q by stable ID without changing the text or retrieval key. The released updater also records visits, last reward, and timestamps. Those bookkeeping fields are useful, but distinct from the retrieval algorithm.

Step 2 — Build the relevant candidate set

Embed the current query. Compute cosine similarity against past intent embeddings. Reject memories at or below threshold \(\delta\), then keep at most \(k_1\) highest-similarity memories.

If no memory qualifies, call the solver without one. Do not select an unrelated high-Q memory to fill the quota.

For teaching, assume the embedding backend already returned these similarities:

rows = [
    {"id": "A", "sim": 0.90, "q": 0.00, "experience": "Use the shortcut."},
    {"id": "B", "sim": 0.70, "q": 0.40, "experience": "Inspect destination."},
    {"id": "C", "sim": 0.30, "q": 0.90, "experience": "Unrelated procedure."},
]

With \(\delta=0.5\) and \(k_1=2\), C is removed despite its high Q.

Step 3 — Normalize and rank within that set

The paper's rule combines z-scored similarity and Q:

\[ s_i=(1-\lambda)\widehat{\mathrm{sim}}_i+\lambda\widehat Q_i. \]

The following code implements that rule. Its zero-variance convention and deterministic tie-breaking are explicit teaching choices, not unspecified paper defaults:

from math import sqrt

def zscore(values):
    mean = sum(values) / len(values)
    sd = sqrt(sum((v - mean) ** 2 for v in values) / len(values))
    return [0.0] * len(values) if sd == 0 else [(v - mean) / sd for v in values]

def choose_memories(rows, threshold, k1, k2, utility_weight):
    if k1 < 1 or not 0 <= k2 <= k1 or not 0 <= utility_weight <= 1:
        raise ValueError("invalid retrieval configuration")
    candidates = sorted(
        [r for r in rows if r["sim"] > threshold],
        key=lambda r: (-r["sim"], r["id"]),
    )[:k1]
    if not candidates:
        return []
    similarities = zscore([r["sim"] for r in candidates])
    utilities = zscore([r["q"] for r in candidates])
    ranked = [
        ((1 - utility_weight) * sim + utility_weight * q, row)
        for row, sim, q in zip(candidates, similarities, utilities)
    ]
    ranked.sort(key=lambda pair: (-pair[0], pair[1]["id"]))
    return [row for _, row in ranked[:k2]]

For A and B, normalized similarities are \(+1,-1\), and normalized utilities are \(-1,+1\). With \(\lambda=0.75\), scores are \(-0.5,+0.5\). For \(k_2=1\), B wins.

The LLM receives "Inspect destination." It does not receive a magical reward signal merely because B has a high selection score.

Step 4 — Solve and remember exactly which IDs were injected

Construct a prompt containing the current task and the chosen experience texts. Run the ordinary task solver. Keep the injected IDs alongside the attempt record.

This ID list matters: the terminal reward updates memories actually used in the prompt, not all \(k_1\) candidates and not all semantically similar records.

If two memories were injected, both can receive the same outcome update. That is coarse credit assignment. It does not demonstrate that each memory causally helped.

Step 5 — Apply the reward update

For the terminal version:

\[ Q_i\leftarrow Q_i+\alpha(r-Q_i). \]
def update_utilities(bank_by_id, injected_ids, reward, alpha):
    if not 0 <= alpha <= 1:
        raise ValueError("alpha outside [0,1]")
    for memory_id in set(injected_ids):
        row = bank_by_id[memory_id]
        row["q"] += alpha * (reward - row["q"])

If B has \(Q=0.4\), \(\alpha=0.2\), and the task succeeds with \(r=1\), B becomes \(0.52\). If its next use receives \(r=-1\), it becomes \(0.216\). A and C stay unchanged if they were not injected.

These values are illustrative. Choose the reward encoding explicitly; success/failure and a continuous task score are not interchangeable without scaling considerations.

Step 6 — Write a new experience independently

A separate builder takes the current query and trajectory and creates the new payload: a trajectory, a generalized script, or both, depending on the selected builder. Store it under a new ID, with the current intent embedding and the configured initial utility. Do not inherit B's updated utility.

The ALFWorld runner, builders, and updaters make this division concrete. A success-validation updater can skip failed attempts; a failure-adjustment updater can run reflection on failure. Thus “MemRL writes a summary” is not a complete builder configuration.

What each builder actually does

  • Trajectory: return the supplied trajectory unchanged; no writer-model call.
  • Script: make one model call with the trajectory and instructions to extract three to five high-level steps and important decision points. Keep the strategy transferable, rather than listing every low-level action.
  • Proceduralization: make the same script call, then concatenate a SCRIPT section and a TRAJECTORY section containing the original trace.

For example, a successful trace that searched several rooms, found an object, navigated to the destination, and placed it might yield: inspect likely locations; pick up the target; verify the destination; navigate and place; check completion. This is an invented script, not a guaranteed model output.

The released script prompt receives the trajectory; the task-description parameter in the builder is not itself forwarded as a separate prompt field. This is another reason to inspect the assembled writer input rather than infer it from a method name.

The whole lifecycle

load persistent bank
for task:
    retrieve relevant candidate intents
    select memories using the declared ranking policy
    retain selected IDs and inject their experience texts
    run frozen solver to completion
    obtain the allowed task reward
    update Q for injected IDs only
    build a new experience according to the chosen updater
    if updater accepts it:
        insert new ID + intent embedding + payload + initial Q
    persist both utility changes and any new experience

The bank and Q values survive into the next task. A new model call alone does not erase them. A benchmark reset protocol must state which task streams share a bank.

If you use the released selector instead

The inspected ValueAwareSelector sorts by Q, uses similarity to break ties, and with probability epsilon samples from its candidate set. Its configuration declares additional optional filters and recency behavior. Do not assume a declared threshold is enforced inside this selector: inspect the caller that supplies candidates.

Its Q updater can include a discounted next-value term; the single-step configuration uses \(\gamma=0\). This is a different implementation choice from silently reproducing the paper's weighted z-score ranking. Exact selector and updater

Feedback and the tests that establish the implementation

The utility updater sees reward. The memory builder's inputs are separate: inspected builder interfaces consume trajectories, while updater variants can receive success/failure and supply failure feedback to a reflector. They do not have a separate gold-answer argument. That does not prove arbitrary task data contains no reference leakage.

Test empty retrieval, threshold rejection, opposing similarity/Q order, constant Q, one candidate, \(k_2=0\), utility updates for selected IDs only, and new-record initialization. Run a sequential toy stream and check that a repeatedly rewarded experience rises in ranking. This verifies mechanics, not the benchmark performance of the paper.
