ReasoningBank: learn from a failed attempt

2 min · 1 worked example · 2026-09-21

All methods

The idea: finish a task, turn the attempt into reusable advice, and give that advice to a later task.

Follow one invented example. The agent must find a chair narrower than 60 cm. Its memory bank starts empty.

1. The agent tries the task

With no old advice to retrieve, the agent searches normally. It chooses a chair from a search result without checking the width.

What we have now: the task and a record of the agent's attempt. No new memory yet.

2. A judge call checks the attempt

A separate LLM call reads the task and the recorded attempt. In the self-judged setting, it has no answer key.

It concludes: “The agent never established that the chair meets the width requirement.”

This is the judge's assessment, not a guaranteed benchmark verdict.

3. A writer call turns the failure into advice

The failure assessment selects the failure-extraction prompt. The writer reads the attempt and writes a transferable procedure, such as:

Before choosing a product, open its specifications and check every required attribute.

It saves a lesson, not “choose a different chair.”

4. The program saves the lesson so another task can find it

The program stores the lesson alongside the old task's query. It also stores a numerical representation of that query so similar future tasks can find it.

The old task is over. Its answer and score do not change.

5. A new task retrieves the lesson

A later task asks for a desk under a height limit. The program compares this query with the saved queries and selects a similar past experience.

The next solver prompt contains the new task plus the saved verification procedure.

6. The agent uses the advice on new evidence

The agent opens the desk's specifications and checks its height. After this attempt, judging and lesson-writing can run again.

What persists: a growing bank of experiences. Model weights do not change.

What the writer knows: whether the judge thinks the attempt succeeded, plus the recorded attempt. This example does not reveal a correct answer.

The defining operation is: a completed attempt becomes advice for another task. Exact prompts, retrieval code, and other feedback settings are below.

What you are building

Build an agent that starts task B with procedural lessons distilled from earlier tasks. The solver, judge, and extractor can use the same underlying model, but they are separate calls with different inputs. The method does not train model weights or require the solver to edit a global policy document.

We will implement the single-attempt, self-judged loop. The WebArena code at this pinned revision is our implementation reference. MaTTS is an additional rollout policy, described separately below.

Step 1 — Define the two persistent records

Keep the experience payload and its retrieval key separately:

experience = {
    "task_id": "task_17",
    "query": "Find an item meeting the requested constraints",
    "status": "fail",
    "memory_items": [
        {
            "title": "Verify eligibility on the detail page",
            "description": "Use when search results omit a required attribute.",
            "content": "List constraints; inspect each candidate's detail page; "
                       "verify every constraint before choosing."
        }
    ]
}
embedding_record = {
    "id": "task_17",
    "text": experience["query"],
    "embedding": [0.8, 0.6]  # invented unit vector for this lesson
}

This dictionary is a normalized teaching representation. The released extractor emits Markdown items and saves a JSONL experience containing query, trajectory fields, status, and split memory text. Do not feed the dictionary above directly into that parser without an adapter.

The retrieval key answers “which earlier task resembles this one?” The item content answers “what procedure should I apply?” A title alone is not the entire memory.

Step 2 — Retrieve before you solve or write the new experience

Normalize stored embedding vectors and compare them with an embedding of the new task. The code's Gemini path uses an instruction-wrapped query for matching against cached past-query embeddings. Use a compatible embedding model/dimension for both sides; changing the embedding model without rebuilding the cache breaks this contract.

The basic paper setting selects one prior experience. That experience can contain several memory items. “Top 1” therefore does not mean “inject one sentence.”

Here is the deterministic core once embeddings exist:

from math import sqrt

def unit(v):
    norm = sqrt(sum(x * x for x in v))
    if norm == 0:
        raise ValueError("zero embedding")
    return [x / norm for x in v]

def select_experience(query_vector, rows):
    if not rows:
        return None
    q = unit(query_vector)
    def similarity(row):
        v = unit(row["embedding"])
        if len(v) != len(q):
            raise ValueError("embedding dimensions differ")
        return sum(a * b for a, b in zip(q, v))
    return max(rows, key=similarity)["id"]

This is a readable reconstruction of cosine ranking, not a replacement for the repository's embedding client. The retrieval code also persists the new query embedding during retrieval, but computes similarity against the previously loaded cache. Do not accidentally retrieve an unfinished task's own empty experience.

With no prior experiences, skip the memory block and run the ordinary solver.

Current environment observation

Then run the existing action–observation loop until its stopping condition. Memory does not execute those actions for the solver. If the lesson says to inspect a detail page, the solver still has to issue the browser action and interpret the new result.

Record the attempt. Keep task identity, generated actions, visible results, and final output in your harness logs. The released WebArena extraction path specifically formats recorded think/action fields. That is not a promise that every observation from the full browser log enters the extractor.

Step 4 — Judge the completed attempt

Make a new judge call, not another environment action. In the self-judged setting, its evidence comes from the task and recorded attempt, not a reference solution. The result selects which extraction prompt runs.

An illustrative judgment could be:

{"success": false, "reason": "The selected item was never checked for the required width."}

This JSON is our explanatory interface; use the actual evaluator parser when porting the release. Its self-evaluation result is read as a reward field, and an available explanation can be forwarded to the extractor.

The distinction that matters: “the judge thinks this failed” is not “the benchmark certifies this failed.” Log both separately if a hidden benchmark evaluator exists. Only pass benchmark feedback into memory if that is an explicitly chosen experimental condition.

Step 5 — Extract the lesson using a success-specific or failure-specific prompt

Do not leave this as an unexplained function named "summarize." The actual prompt contracts tell the extractor to:

  1. Inspect why the attempt succeeded or failed.
  2. Produce no more than three distinct items.
  3. Make each item actionable for future similar tasks.
  4. Give it a title, a short applicability description, and procedural content.
  5. Avoid copying task-specific product names or literal query strings into what should be a transferable procedure.

The failure path is therefore not “save the failed answer.” It should extract a prevention or correction procedure. In our example, save the missing verification step, not the incorrect product ID.

The released format uses a Memory Item heading with Title, Description, and Content subheadings. A faithful port should keep the supplied prompt and parser together. A JSON-normalized store is an engineering adaptation that can preserve those semantics, but changing the prompt itself should be recorded.

Step 6 — Append and continue

Persist the new experience and ensure its embedding ID resolves to it. Do not overwrite the previous nearest neighbor. The next task can retrieve either old or newly appended experience, depending on similarity.

The complete orchestration is:

load bank and embedding cache
for task in ordered task stream:
    retrieve prior experience by task-query similarity
    assemble solver input with that experience's lessons
    execute task and retain its attempt record
    obtain self-judgment from task + attempt evidence
    choose success or failure extraction instruction
    extract up to three title/description/content items
    persist task -> extracted items
    make its query embedding available for later tasks

The loop is sequential with respect to memory visibility. Parallel tasks need a declared snapshot/order policy; otherwise different scheduling changes what each solver sees.

Follow one attempt all the way through

Task A: choose an item with a width limit. The agent finds a relevant search result, fails to open the specification page, and returns that item. The judge marks failure because eligibility was not established.

The extractor writes the eligibility-check item shown above. On task B, the query concerns a different product category but also contains several constraints. Suppose its embedding is closer to A than to an unrelated account-settings task. A is retrieved. B's solver input now contains the verification procedure. It opens the specification page and checks the new measurements.

What changed: the prompt for B. Neither the underlying model nor A's already recorded score changed. Whether B now succeeds is an empirical question, not guaranteed by the memory write.

Feedback, variants, and an implementation test

The extraction entrypoint supports both self-evaluation and ground-truth reward criteria. The latter uses the benchmark's outcome to select the extraction path. Label the criterion in the run configuration.

MaTTS changes the evidence available before extraction: parallel mode obtains multiple attempts at one task; sequential mode asks the agent to inspect and refine its previous attempt. These extra calls are not part of the single-attempt loop. Consult the paper's MaTTS procedure before claiming a MaTTS reproduction.

Before running a benchmark, test that an empty bank yields no injection; a known query selects the expected ID; a failure invokes the failure prompt; an appended record becomes retrievable; and a judge error is not silently treated as task failure. The last behavior is recommended harness error handling, not a claim about every release script.
