AgentFold: fold completed steps into a shorter record

2 min · 1 worked example · 2026-09-21

All methods

The idea: let the acting model choose which completed steps to replace with a summary. Keep the newest interaction detailed.

Our invented agent is checking whether a candidate meets several requirements.

1. Begin with three history blocks

The next prompt contains the question, tools, and:

  • Steps 0–1: candidate A was rejected.
  • Step 2: candidate B looks promising.
  • Step 3: the full result confirming B's affiliation.

These blocks form the current working history.

2. The model chooses a fold and a new action

In one response, it says:

Replace steps 2–3 with “B's affiliation is confirmed; its date still needs checking.”

It also chooses the next search to verify the date.

Both decisions were made before that search returned anything.

3. The runner executes the new search

The search returns a dated announcement.

In the inspected code, tool execution happens before the already-generated fold is applied. The fold still cannot include this new result: the model had not seen it.

4. The runner replaces only the selected blocks

Steps 2 and 3 disappear from active history. One block covering 2–3 takes their place.

The earlier rejection of A remains unchanged.

5. The runner appends the newest interaction

The next prompt now contains:

  • Steps 0–1: A rejected.
  • Steps 2–3: B's affiliation confirmed; date still needs checking.
  • Step 4: the new search action and its full result.

The model now has the date evidence and can decide what to do next.

6. Repeat at the next call

The model can summarize just step 4 or fold it together with older blocks. The summary must retain facts still needed by the task.

Discarded raw details have no built-in archive-read operation in this runner. The agent may need to revisit the external source.

How it is learned: supervised training teaches the model to imitate validated responses that contain both the fold decision and next action. It is not an RL loop in this paper.

Feedback boundary: each fold sees the current task/history, not the result of the action generated alongside it.

The defining operation is: replace a chosen interval of history, then append the new interaction. Field names, interval code, and training pairs are below.

All memory methods · Short overview

AgentFold makes the acting model also decide how to rewrite its working history. You will implement an ordered list of step blocks, parse a fold directive from the model, replace a suffix of those blocks, and put the resulting list into the next prompt. There is no embedding search or persistent experience bank in this loop.

This chapter follows the released inference file, pinned at f72f75d. The examples are invented; the validated helper below deliberately adds checks missing from that file.

1. Store intervals, not a growing chat transcript

Use the release's three fields:

steps = [
    {"start": 0, "end": 1, "content": "Candidate A fails the date requirement."},
    {"start": 2, "end": 2, "content": "Candidate B appears eligible; verify affiliation."},
    {"start": 3, "end": 3, "content": "Motivation: check affiliation. Tool: visit(B). Result: B joined in 2012."},
]

The first entry represents two past actions. The last entry is the latest interaction, including motivation, tool call, and tool response. Older entries are folded summaries. The release numbers turns from zero; the paper's equations use one-based steps.

Keep a separate full diagnostic log if you need to inspect failures. Do not send that log back alongside the folded list: that would undo the context reduction. A new question initializes an empty list.

2. Assemble precisely what the model sees

Every iteration creates a fresh two-message request:

SYSTEM:
  Instructions for the structured response.
  Search and visit tool schemas.

USER:
  Question: Which candidate satisfies the date and affiliation constraints?
  Previous Steps:
    [compressed range 0–1] Candidate A fails the date requirement.
    [compressed step 2] Candidate B appears eligible; verify affiliation.
    [latest step 3] Motivation + visit call + its full result.

The labels here are explanatory rather than copied formatting. The release's formatter uses its own Step/CompressedStep labels.

The model sees the task, summaries, and latest observation. It does not see a hidden reference answer. Although the model generates deliberation, the next stored interaction keeps its concise motivation rather than appending all that deliberation.

3. Parse one output containing both memory and action decisions

After its deliberation, the model emits a compression block, motivation, and action. Here is a synthetic compression block in the released field names:

<compress>
{"compress_range": [2, 3], "compress_text": "Candidate B meets the affiliation constraint: joined in 2012. Date constraint still needs primary-source verification."}
</compress>
<motivation>Verify the remaining date constraint from a primary source.</motivation>

A search or visit call follows using the runner's tool-call format. The fold and action are generated in the same model call. Consequently, the fold cannot include the result of the new action that has not executed yet.

The paper calls the corresponding fields range and summary. Sending those names unchanged to this release's parser will fail; its updater expects compress_range and compress_text.

4. Apply the fold to whole existing blocks

The simple upstream updater removes entries whose start is inside the requested interval, appends the new block, and sorts by start. It does not fully validate overlapping ranges.

Here is a defensive implementation of the paper's whole-block suffix operation. Its validation is an engineering addition, not a claim about upstream behavior:

def fold_suffix(steps, start, end, summary):
    if not steps or not isinstance(summary, str) or not summary.strip():
        raise ValueError("fold needs existing steps and a nonempty summary")
    ordered = sorted(steps, key=lambda step: step["start"])
    if any(step["start"] > step["end"] for step in ordered):
        raise ValueError("invalid existing interval")
    if any(a["end"] + 1 != b["start"] for a, b in zip(ordered, ordered[1:])):
        raise ValueError("existing steps must be a contiguous partition")
    starts = [step["start"] for step in ordered]
    if start not in starts or end != ordered[-1]["end"]:
        raise ValueError("fold must cover whole blocks through the latest step")
    first = starts.index(start)
    return [
        *[dict(step) for step in ordered[:first]],
        {"start": start, "end": end, "content": summary},
    ]

Applying fold_suffix(steps, 2, 3, new_summary) leaves block 0–1 unchanged and replaces blocks 2 and 3 with one block 2–3. Requesting 1–3 is rejected: step 1 is buried inside block 0–1, so that boundary would split an already compressed block.

Granular condensation: choose only the latest step. Deep consolidation: choose a suffix beginning at an older block boundary. Both use the same deterministic replacement function; the model chooses the boundary and text.

5. Execute the tool and construct the next state

In the pinned runner, the order is:

  1. Generate and parse the response from the old context.
  2. If it contains a final answer, terminate; that branch skips folding.
  3. Execute the new tool call.
  4. Apply the already generated fold to the previous steps.
  5. Append the new motivation, call, and returned observation as a fresh single-step block.
  6. Reformat that list for the next call.

The paper describes folding before acting; the release executes the tool before applying the fold. The information boundary is the same: the fold was authored before the tool result existed.

There is a practical consequence: if parsing the compression JSON fails after a tool executes, an unguarded retry can repeat the external action. This web-search runner is not a safe transaction design for payments or other irreversible tools. For those environments, validate the full response before execution and deduplicate action IDs; those are adaptations.

6. Follow the example across a call boundary

Before call 4:
  [0–1] A rejected.
  [2]   B candidate.
  [3]   B affiliation source, full tool response.

Call 4 generates:
  fold 2–3 → B affiliation confirmed; date still unverified
  action → search for B's dated announcement

Tool result:
  announcement dated 2016

Before call 5:
  [0–1] A rejected.
  [2–3] B affiliation confirmed; date still unverified.
  [4]   Search motivation + query + full announcement result.

Call 5 can preserve the date when it folds step 4. It cannot recover an omitted detail from steps 2–3 through a built-in archive read: this runner provides no such memory dereference operation. It would need to revisit the external source.

7. Train the policy, if you do not use an existing checkpoint

The paper's Fold-Generator collects structured teacher responses, rejects malformed steps and trajectories with excessive environment errors, then performs supervised fine-tuning, not RL. Its training examples are current-context/validated-response pairs. Paper, Section 3.4

For the example above, the training input must be the state before call 4, and the target is the teacher's response that selected fold 2–3 and the next search. The newly returned announcement belongs to the next input, not the current input. Training on the full final transcript as every input would leak future observations.

Implement ordinary causal next-token cross-entropy on the response tokens; mask the system/user input tokens. Save the exact input snapshot rather than reconstructing it later from the final, already-folded history. This paragraph spells out the mechanics of SFT, not undisclosed teacher prompts or rejection thresholds.

8. Tests that distinguish this from generic summarization

  • A one-step fold and a multi-block fold both preserve chronological coverage.
  • The example retains block 0–1 byte-for-byte while replacing only 2–3.
  • A fold cannot begin inside an existing block.
  • The current tool result appears only in the new latest interaction, never in the previously generated summary.
  • The next prompt excludes discarded raw history.
  • A new question begins with no prior question's step blocks.
  • A malformed response cannot silently execute an irreversible tool twice in an adapted runner.

The core implementation is small: structured prompt → fold/action response → interval replacement → latest interaction append. The learned part is deciding which interval to fold and what its summary must preserve.
