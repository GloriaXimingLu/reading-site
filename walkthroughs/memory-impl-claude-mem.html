Claude-Mem: an observer remembers tool results

2 min · 1 worked example · 2026-09-21

All methods

The idea: capture the solver's tool activity, let a separate observer write useful notes, and let future solvers retrieve those notes.

This is an engineering system. Use the same invented cache bug throughout.

1. The solver reads code and runs a test

The test reports that two tenants receive the same cache key.

Hooks capture the relevant read and test events, including their inputs and results.

2. A separate observer writes a discovery

The observer receives those captured events. It produces a structured note such as:

Cache keys collide across tenants; the two-tenant test failed.

The worker parses and stores the note. Search indexing follows asynchronously: “event accepted” does not yet mean “note searchable.”

3. Later events produce a second note

The solver fixes the key and the test passes. Those new events can produce another observation:

Tenant identity was added to the key; the regression now passes.

The memory now contains both the original problem and the later fix.

4. A future solver searches a small index

A new task asks whether tenant isolation is covered. The solver searches for “tenant cache.”

It first receives short results with IDs and titles, not every full note in the database.

5. The solver checks the timeline

Seeing a failure note alone could be misleading. The solver looks at nearby records and notices the later fix.

This gives the result its chronological context.

6. The solver fetches selected details

It requests the full failure and fix observations by ID. If it needs the exact historical test output, it can also request the associated raw tool event.

That raw evidence can be missing or capped; it is not guaranteed lossless storage.

7. The solver uses the remembered evidence

It knows which test covers tenant isolation and can verify the current code before acting.

What persists: the observation database and search index. The future prompt contains only selected material.

Feedback boundary: the observer knows what the captured events supply. It does not independently inspect the code or receive a hidden answer key.

The defining operation is: tool events → observer notes → search → selected details. Event schemas, observer output, and read calls are below.

What you are building

Build a pipeline in which a separate observer model reads captured tool events and turns useful ones into persistent observations. A later solver first searches a small index, then fetches selected details.

The defining separation is:

solver tool execution -> event capture -> observer call -> database/index
future solver         -> search -> choose IDs -> fetch notes/evidence

Claude-Mem is an engineering system. This chapter follows the pinned release; simplified record shapes below are implementation explanations, not a claim that its SQL schema has these exact column names.

Step 1 — Capture an event the observer can actually see

Register the tool-event hook. After a permitted tool execution, capture its identity, session/project metadata, input, and result. Hand the event to the worker rather than asking the solver to write a note manually.

A normalized example:

{
  "project": "cache-service",
  "session_id": "session_A",
  "tool_use_id": "tool_17",
  "tool_name": "test",
  "tool_input": {"target": "test_two_tenants"},
  "tool_response": "FAILED: tenant A and tenant B produced the same key"
}

The observer does not automatically receive every thought, every file on disk, or a hidden evaluator score. What is not captured and supplied is not evidence it can inspect.

The release filters events and retains raw I/O on a best-effort basis. Each captured input/result field has a 64-KiB cap at the inspected pin. Treat raw storage as useful evidence with known limits, not a lossless archive of all agent activity.

Step 2 — Run the observer with a fixed output contract

The code-mode prompt asks for meaningful findings such as discoveries, changes, and fixes, and permits skipping routine events. It emits structured XML observations.

A schema-shaped invented output:

<observation>
  <type>discovery</type>
  <title>Cache keys collide across tenants</title>
  <subtitle>Tenant identity is missing from the key</subtitle>
  <facts>
    <fact>The two-tenant regression returned identical keys.</fact>
  </facts>
  <narrative>The observed failure motivates checking tenant scope in key construction.</narrative>
  <concepts><concept>gotcha</concept></concepts>
  <files_read><file>src/cache.py</file></files_read>
  <files_modified></files_modified>
</observation>

The files field is warranted only if the supplied event stream establishes the file. Our single test event above does not by itself prove the implementation file was read; add the preceding captured read event before producing this complete example. This is precisely why writer inputs matter.

The observer is not an autonomous investigator. It should not fill missing evidence by imagining a code inspection. A later successful test and edit can support a separate bugfix observation.

Step 3 — Parse and persist; distinguish acceptance from completion

The response processor turns model output into stored records. Search indexing follows asynchronously.

In your implementation, distinguish these states:

event received
event queued
observer output produced
observation parsed and stored
observation indexed for search

These labels describe the stages, not literal release status-enum values. An HTTP acknowledgment at the first stage does not establish the last one.

For a simplified implementation, keep raw event records, observation records, and index entries as distinct objects. Associate observations with their source event identities so a reader can recover evidence later. A malformed observer output or a skipped routine event need not produce an observation.

If you add a barrier before deliberately resetting a solver, wait for the required records to become retrievable. Such a guaranteed barrier is an engineering addition to test explicitly, not something implied by asynchronous ingestion.

Step 4 — Produce the initial context for a future solver

At session start, provide a bounded selection of recent memory context plus access to search. Do not paste the whole database into the prompt. Context injection is an initial reading convenience; it is not equivalent to replacing the complete active conversation.

The observer's session summary is a separate artifact from individual observations. Summary fields cover the request, investigation, learning, completed work, next steps, and notes. The same mode configuration specifies both contracts.

Step 5 — Implement the actual three-stage reader

The search skill prescribes staged disclosure. The solver chooses the query and filters IDs based on results.

First, obtain short index results:

search(query="tenant cache", limit=20, project="cache-service")

Suppose the response includes observation 41, “Cache keys collide across tenants,” and observation 55, “Tenant identity added to cache key.” Reading only the first title could leave the solver believing the bug is still present.

Second, inspect neighboring records:

timeline(anchor=55, depth_before=3, depth_after=3, project="cache-service")

Third, fetch selected full observations:

get_observations(ids=[41, 55], project="cache-service")

Now the solver receives detailed facts and narrative about the failure and subsequent fix. The first call returns an index, the second provides chronology, and the third provides full selected content. They solve different reading problems.

The search orchestrator is the source to port for actual routing. Replacing its search behavior with a home-built embedding search changes the implementation condition.

Step 6 — Fetch raw evidence only when needed

If the stored note omits the exact failing output, use the associated tool identity:

get_tool_uses(ids=["tool_17"], project="cache-service")

Observation IDs and tool-use IDs are different namespaces. Do not pass observation 41 as though it necessarily identifies the raw test event.

Raw retrieval can return truncated or missing information. The solver must inspect that status before claiming an exact historical result. It may need to rerun a permitted test against the current repository.

Trace the whole example

Session A reads src/cache.py, runs the failing test, edits the key, and runs a passing test. Captured events let the observer write the discovery and fix records. The worker stores them and the search index catches up.

Session B asks whether tenant isolation is covered. Its initial prompt need not contain the whole prior session. It searches, sees both records, examines their timeline, fetches selected details, and—if exact output matters—fetches the raw test evidence. It can then verify the current implementation.

The observer's write was based on visible event evidence. Session B's useful context was selected by its reader. Neither operation changes the model weights.

Tests and implementation boundaries

Use recorded fake events to test skipped routine activity, malformed XML, multiple observations, database persistence, project filtering, timeline ordering, and raw-ID lookup. Separately test delayed indexing: an accepted event must not be reported as searchable before it is.

These are recommended conformance checks, not benchmark results. The persistent database survives sessions; the active solver prompt still needs its own context-management policy. Pairing Claude-Mem with a compactor is possible, but is a combined system.
