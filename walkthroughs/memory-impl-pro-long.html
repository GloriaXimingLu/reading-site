PRO-LONG: ask a program to read the long history

The idea: keep the raw interaction history in files and let a coding agent write small programs to inspect the parts it needs.

Follow an invented grid-game investigation. This walkthrough uses the ARC-AGI-3 implementation.

1. The runner records what happened

The environment runner executes action 18 and writes the action and resulting board into a log.

The write is ordinary logging. No LLM has to decide how to summarize the board.

2. The coding agent receives access to the workspace

Its instructions identify the log, legal actions, and the file where it should put its next action batch.

The entire log does not have to fit in the prompt.

3. The agent asks a precise question of the log

It wants to know what action 18 changed. It writes or runs a helper that reads the settled board before and after that action and compares their cells.

The distinction between an animation frame and the settled result matters.

4. The helper returns a small result

Instead of two full grids, the agent sees:

The marked piece moved from column 1 to column 0. No other cells changed.

The comparison is computed by code. “This action moves that piece left” is the agent's hypothesis about the result.

5. The agent proposes a short test

It writes a small action batch to the action file.

The runner parses it, enforces the batch limit, executes it, and records the next observations. The coding agent does not replace the environment runner.

6. Later, the agent compares distant observations

At action 70, a similar pattern appears. It searches the old log and reuses its helper to compare the two situations.

It can use evidence from action 18 without carrying all intervening boards in its active conversation.

What persists: logs, helper programs, and any agent-written notes within the run. The selected backend can also resume an agent session.

Feedback boundary: logs contain environmental observations and available progress signals, not an unseen correct action sequence.

The defining operation is: a small program turns a large stored history into a small useful observation. Log formats, action parsing, and backend settings are below.

What you are building

Build an environment runner that records interactions in a persistent filesystem and asks a coding agent to analyze those records with tools and code. The coding agent outputs an action batch; the runner executes it and records the results.

Unlike a learned summary writer, the primary memory write is ordinary logging. The intelligence lies partly in how the agent interrogates that log.

We follow the ARC-AGI-3 research implementation, not every feature of the repository's general-purpose CLI.

Step 1 — Separate the world runner from the coding agent

The runner owns the environment state and action execution. The coding agent receives a workspace, log location, legal-action descriptions, and file/code tools. It should not need to load the game engine directly into its reasoning prompt.

Keep these objects:

Environment:
  current board, score/progress, legal actions, termination state

Persistent workspace:
  logs.txt
  actions.json          replaced per agent call
  optional notes and helper programs

Agent backend:
  model/session configuration
  session identity, if that backend resumes sessions

The directory persists across calls within the run. The action file is cleared before the next request so a stale action batch is not executed again.

Step 2 — Record observations without asking an LLM to summarize them

Append the initial board, actions, resulting boards, and available progress information. Preserve step ordering and distinguish animation frames from the committed state.

The game-state renderer marks intermediate animation frames and the settled board. An analysis using an intermediate frame as the final state can infer a false game mechanic.

The log markers described in the agent prompt include initial and post-action board states. Use that actual format when porting its parser-facing interface.

A normalized teaching record might be:

record = {
    "action_number": 18,
    "action": "ACTION1",
    "before": [[0, 1], [0, 0]],
    "after": [[1, 0], [0, 0]],
    "score_before": 0,
    "score_after": 0
}

This tiny grid and dictionary are an explanatory representation, not the release's textual log schema.

Step 3 — Give the agent a task that points to evidence

On the first call, tell the agent to inspect the log and write its first action batch. On later calls, point it to new records and any files it saved earlier.

The prompt supplies action semantics and recommends programmatic analysis of large grids. The model can use Read, Write, Edit, Bash, Grep, and Glob-style tools, rather than receiving all 64×64 boards as one giant prompt.

The agent may create a helper to parse board blocks, compute connected components, track objects, or compare distant states. Those helper files are derived memory. The original record remains the evidence against which they can be checked.

Step 4 — Implement one concrete programmatic read

Suppose the agent wants to know what action 18 changed. After parsing the two settled grids from the log, a deterministic comparison is:

def changed_cells(before, after):
    if len(before) != len(after):
        raise ValueError("grid heights differ")
    differences = []
    for row_index, (a, b) in enumerate(zip(before, after)):
        if len(a) != len(b):
            raise ValueError("grid widths differ")
        for col_index, (old, new) in enumerate(zip(a, b)):
            if old != new:
                differences.append((row_index, col_index, old, new))
    return differences

For the toy record, this yields:

(row=0, col=0): 0 -> 1
(row=0, col=1): 1 -> 0

The agent sees a small computed result instead of re-reading two complete boards. It may infer that an object moved left, then test that hypothesis with a short action batch. The computation is exact; the interpretation remains a hypothesis.

This is why raw-log memory need not imply raw-log prompt length: a program can turn a large persistent record into a small, task-specific observation.

Step 5 — Parse and execute the proposed actions

The inspected prompt asks for a file shaped like:

{"actions": ["ACTION1", "ACTION6(30,40)"]}

The values are illustrative. The runner parses recognized action names and arguments, respects the configured batch cap, then invokes environment steps in order. Entries beyond the cap are not an invitation to perform unbounded actions. The base agent parser accepts supported string/object forms.

For a new hypothesis, one or two actions make its effect easier to observe. A proven sequence may justify a larger batch. That choice belongs to the agent's planning policy and available action budget.

After executing, append the observations before invoking the agent again. If an action changes the score or ends a level, that visible outcome becomes available evidence.

Step 6 — Keep the backend and log mode explicit

The source has full-log, truncated-log, and current-board-in-prompt modes. Full-log synchronization appends newly recorded bytes; a windowed setting supplies only the configured recent history.

The Codex backend resumes a prior session when available. Therefore the method should not be described as obligatorily resetting the model context at every action batch.

An external log, an agent session, and the environment's lifetime are three different things. Report all three when implementing a comparison.

Follow a complete cycle

At action 18, moving a piece exposes a switch. The log records both boards. The agent saves a helper that extracts that switch's neighborhood.

At action 70, a similar structure appears. The agent searches its history, invokes the helper on old and current boards, and observes the same relative geometry. It writes a two-action plan, which the runner executes. New observations confirm or refute the analogy.

The archive is now longer by two records. A helper or note may also have changed. There was no mandatory call to a memory summarizer, and the old evidence was not overwritten just to improve retrieval.

Feedback, reset, and tests

The logger sees environmental observations and available score/progress information. It does not reveal an unseen correct action sequence. The coding agent's notes inherit only the evidence it inspected.

The workspace persists within the run. Cross-game or cross-task reuse is a separate protocol choice, not established merely by a persistent directory.

Test action-file clearing, parser validation, batch caps, log ordering, settled-frame extraction, and byte synchronization. Then test a task that requires comparing distant observations. Measure the code/tool calls and tokens used by that read policy as well as task success.

The paper motivates programmatic memory; the implementation above makes clear which component logs, which reasons, and which executes.
