ShadowFrog: leave notes beside the code

2 min · 1 worked example · 2026-09-21

All methods

The idea: the coding agent writes discoveries at addresses matching the source files. A future agent working on those files finds the notes.

This is an engineering system. Follow an invented cache bug.

1. The agent checks existing notes

Before investigating src/cache.py, it reads relevant project notes and that file's existing “shadow” notes.

Those notes are evidence to check against the current code, not automatically trusted facts.

2. The agent discovers a behavior

It reads the key-building function and runs a test with two tenants.

The test shows that both tenants get the same cache key. The agent now has evidence worth preserving.

3. The same agent writes a discovery

It writes under the key-building function's heading in .shadow/src/cache.py.md:

Tenant identity is absent from the key. The two-tenant test demonstrated a collision.

The note also records how the finding was verified, where it came from, and which test demonstrates it. No separate observer model is needed.

4. The conversation ends; the file remains

The note is on disk. A later session need not receive the old conversation.

Saving this note does not itself shorten or reset the active conversation.

5. A later task leads back to the note

The new task touches src/cache.py. The file-aware hook surfaces a bounded reminder, and the agent opens the full note.

It now knows which behavior and test to examine before editing.

6. The agent verifies, fixes, and refreshes

It checks whether the collision still exists. After fixing it and rerunning the test, it updates the discovery so an old bug report does not masquerade as current behavior.

What persists: source-addressed Markdown discoveries and their links.

Feedback boundary: the writer sees its code reads, tests, and other supplied evidence—not a hidden solution.

The defining operation is: put a verified finding where work on that source file will uncover it. Exact file layout, heading syntax, and cross-file rules are below.

What you are building

Build a repository notebook organized at the same addresses as source code. The task-solving agent writes discoveries; no separate observer is required. Later sessions find those discoveries by file/symbol, project-wide preferences, cross-references, or search.

This is an engineering system, not a trained memory policy. The pinned ShadowFrog instructions define the storage and behavior below. Hook reminders and the writer's instructions must both be installed; a folder alone does not produce this behavior.

Step 1 — Create the addresses before writing findings

For a source file src/cache.py, use .shadow/src/cache.py.md. A top-level function has a level-two Markdown heading with its name in backticks. A class method has a level-three heading. The viewer depends on that formatting.

.shadow/
  _index.md
  _prefs.md
  _cross/
  _meta/state.json
  _dreams/_index.md
  src/cache.py.md

An initialized file can contain symbol headings but no discoveries. Initialization inventories code; it does not prove behavioral claims.

The path mapping itself is simple:

from pathlib import PurePosixPath

def shadow_path(source_path):
    p = PurePosixPath(source_path)
    if p.is_absolute() or ".." in p.parts:
        raise ValueError("expected repository-relative source path")
    return ".shadow/" + p.as_posix() + ".md"

The validation is a recommended containment check. It is not an additional learned component.

Step 2 — Implement the pre-work reader

Before investigating or editing, provide the solver with these actions in order:

  1. Read _prefs.md for repository-wide conventions.
  2. List _cross/ and open findings relevant to the affected area.
  3. Check the dreams index for relevant experiment reports.
  4. Open the shadow of the specific file being investigated.
  5. Read current source code to establish whether stored claims still apply.

The agent chooses relevant notes based on the task and file. This is not vector search over all previous conversations. The index can be stale, so the instructions require direct checking of per-file and cross-cutting notes.

A pre-edit integration can make the target file mechanically available:

incoming edit request: src/cache.py
hook maps it to:      .shadow/src/cache.py.md
hook response:        bounded discoveries + reminder to inspect full notes
solver:               reads the note, then performs the requested edit

The pre-tool hook has a bounded snippet—at the inspected pin, up to three discoveries and 600 characters. That snippet is not the complete notebook or a guarantee that every relevant finding was shown.

Step 3 — Decide what the solver should write

The writer's evidence is ordinary investigation: code reads, executions, tests, user explanations, and prior notes. The policy should capture a behavioral fact that will change future work, not narrate every tool call.

Suppose make_key omits tenant identity and a regression test demonstrates two tenants collide. Store the behavior, evidence status, provenance, and the other affected symbol:

# Shadow: src/cache.py

## `make_key`

- Tenant identity is omitted from the key; the two-tenant test
  demonstrated a collision.
  _(verified, source: exploration, labels: [bug])_
  Also involves: `tests/test_cache.py::test_two_tenants`

## Cross-References

This is an invented finding using the source's actual format. The status distinguishes verified, uncertain, and refuted claims. Provenance distinguishes exploration, user input, and interaction. A label such as bug is optional.

The canonical address is file::symbol. There is no separate UUID required for each per-file discovery.

Step 4 — Apply the placement and merge rules

Before adding a discovery, read the existing entries under that symbol:

  • Same claim already present: update it rather than duplicate it.
  • New evidence extends a claim: merge the information.
  • Claims conflict: investigate, retain the supported account, and mark the contradicted one refuted.
  • No related claim: append the new discovery.

Do not replace the entire file merely because you learned one fact. Preserve unrelated discoveries and the final Cross-References section.

Placement depends on scope:

Knowledge scope Write destination
General user preference _prefs.md
One source file/symbol Its shadow
Two files Per-file discovery with Also involves
Three or more files _cross/<descriptive-slug>.md plus back-pointers

For a cross-cutting finding, keep both directions: the cross entry lists source-symbol references, and each affected file links back to that entry. These are maintained links, not automatically inferred graph edges.

Step 5 — Verify before marking a discovery verified

For a structural claim, reading the code may suffice. For runtime behavior, construct a test or probe. In the cache example:

hypothesis: tenant A and tenant B can obtain identical cache keys
probe:      same resource ID, different tenant IDs
observed:   equal keys
write:      verified exploration discovery, linked to the test

After changing make_key to include the tenant, rerun the probe. The old “omits tenant” statement is no longer a description of current behavior. Refresh it or mark it refuted and retain relevant historical context only if useful. The update instructions are part of the implementation, not optional housekeeping.

User-provided preferences have their own provenance rules. They are not benchmark-certified facts. A repository notebook should still remain subordinate to the current task's authorized instructions.

Step 6 — Follow the next-session read

On the next cache task, the agent starts with normal task instructions and reminders. The edit target identifies the relevant shadow. Reading it supplies the remembered collision and test location. The solver can rerun that test before editing.

The storage stayed on disk while the conversation changed. Nothing in this step requires the original conversation to remain in the prompt.

session A:
  read code -> run probe -> write discovery at file::symbol

session B:
  task mentions file -> hook points to shadow -> solver reads finding
  solver verifies current code -> uses test/constraint during new work

What is not provided by this mechanism

The notebook does not automatically summarize and evict the active conversation. A “write notes, reset context, resume” controller would need its own trigger, write-completion check, and next-prompt construction. Label that as a combined design.

Optional dream experiments produce additional evidence through extra work; they are not free memory writes. Do not include their benefits without counting that investigation budget.

Before running a comparison

Test the exact path mapping and symbol-heading syntax; ensure an edit hook finds the intended file; test that a duplicate claim updates rather than multiplies; and check cross-reference consistency. The viewer's static invariant checker covers only some structural checks, not semantic correctness of every discovery.

A useful end-to-end test is to give session A a fact obtainable through a probe, close its conversation, and ask session B a task requiring it. Check separately whether the fact was written, surfaced, read, and applied. A failure at any one of those stages is different from “memory does not work.”
