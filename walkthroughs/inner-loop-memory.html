Inner-Loop Memory: ShadowFrog, Claude-Mem, and Codex Compaction

16 min · 5 approaches · 2026-09-18

A focused companion to the broader methods survey. Source/code check: 18 September 2026. This explains existing mechanisms first, then proposes a small initial experiment. No implementation or experiment has been run. Repository-specific integration notes stay private.

The decision in one minute

Start with three portable versions: a rolling checkpoint; that checkpoint plus solver-written notes; and that checkpoint plus observer-written notes. Add exact-evidence recovery as a separate fourth version. These isolate the useful ideas from Codex, ShadowFrog, Claude-Mem, and Memex without requiring three complete product integrations.

One important correction: notes + grep does not shrink the active conversation. Notes solve persistence and selective access; a compaction policy decides what leaves the next model input. An agent that keeps appending all messages can still overflow while its note directory works perfectly.

Mechanism Who writes? What persists? How the solver gets it back
ShadowFrog The solving agent, following skills Source-addressed Markdown discoveries File-aware reminders, read/grep, viewer search
Claude-Mem A separate observer of tool activity Structured observations, summaries, and some raw tool I/O Recent-memory injection, then index → context → details → evidence
Codex compaction A compaction model call or provider service A replacement active context Included in subsequent model inputs; no note search is required
Memex-style recovery Agent writes an indexed summary; evidence is archived Short working state plus referenced blocks Explicit fetch by stable ID
PRO-LONG-style control Harness logs experience; agent can add notes Action/history archive Search and programmatic analysis

Inner loop means the task-solving agent, not an outer system revising its harness. We will first explain continuity inside one task. The same note-writing mechanisms can later carry experience across tasks, but that requires a different reset/feedback protocol. Keep the two settings distinct.

Reading route: ShadowFrog → Claude-Mem → Codex → a useful hybrid → initial versions → design decisions.

One example to follow through every method

Illustrative example—not a reported experiment. An agent is fixing a cache bug. It has learned that a cache key omits the tenant ID; a proposed fix passes a single-tenant test but has not passed the two-tenant regression. Later, after many unrelated tool calls, its context must shrink.

What must survive? The concrete finding, its evidence, the unsuccessful/partial attempt, the unresolved regression, and where to continue. “Investigated caching and improved tests” is a fluent summary but an inadequate working memory. For a research task, substitute a paper/dataset for a source file, an experimental result for a test, and an unresolved confound for the regression.

1. ShadowFrog: the solver writes notes at predictable addresses

Mental model: keep code knowledge beside the code's directory structure. This is a note organization and retrieval design, not a compaction algorithm. The released implementation checked here is commit 6ae4fc8.

Step by step

  1. Initialize addresses. The initializer scans source files and symbols, creating corresponding files under .shadow/. src/cache.py gets .shadow/src/cache.py.md, with symbol headings. Scaffolding creates places to store knowledge; it does not discover the knowledge itself. Initializer
  2. Learn something while solving. The solver reads, edits, tests, or receives information from the user. Its instructions ask it to record useful behavioral discoveries, with provenance and status. This is selective, model-written distillation—not “save every token.” Writing rules
  3. Put the discovery where a future reader will look. One-file knowledge belongs in that file's shadow. Two-file findings use Also involves: references; findings spanning three or more files get _cross/ entries with back-pointers. Placement rules
  4. Remind the agent before it acts. Session start advertises the store. Before an edit, a hook uses the target filename to surface relevant bug/security notes and a pointer to the full shadow. At this pin the rich snippet is capped at three discoveries and 600 characters; repeat delivery is limited per file/process. The solver can read or grep further. Edit hook
  5. Maintain, rather than trust forever. Update checks changed code and refreshes affected discoveries; consolidation can merge duplicates or investigate conflicts. The hook only warns about staleness; the agent must update the notes. An old note remains a claim to check against current code, not an instruction to obey. Update

Example note, our simplified schema:

File: .shadow/src/cache.py.md
Symbol: make_key
Finding: key contains resource_id but not tenant_id.
Evidence: inspected make_key; two-tenant regression still fails.
Attempt: added tenant_id at one caller; single-tenant test passes.
Unresolved: check other callers before claiming the bug is fixed.

After reset, a solver about to edit cache.py can locate this without reconstructing the whole debugging session. If it only knows “cross-tenant leakage,” lexical search and cross-file links matter more than direct path lookup.

What we must add for an inner-loop version

The released hooks register session start and edit-tool pre-use, not a universal post-tool writer or pre-compaction checkpoint. It does not implement “context nearly full → flush notes → replace history → resume.” That controller would be our addition. The ordinary note store is also not a guaranteed raw tool-output archive. Optional dream mode performs additional exploration; exclude it initially so extra experiments do not confound memory quality. Hook configuration, project overview

Evidence boundary: 97.6% versus 36.2% is planted-fact retrieval recall in the highlighted Django condition: about 2,500 facts, the relevant path supplied, eight tool calls. The giant-file condition contains the same planted facts; the difference is layout under a search budget. It does not measure the writer's accuracy or downstream task success. Predictable addressing is especially helpful when the query already contains the address. Study

Borrow first: solver-written, scoped notes plus path/topic lookup. For research, mirror source IDs, datasets, or entities rather than forcing everything into code-file paths.

2. Claude-Mem: an observer builds searchable memory for the solver

Mental model: the solver acts; a second model watches the observable work and writes its memory. The checked local-worker implementation, d8bc975, has more moving parts than notes + grep. Hosted modes are outside this review.

Step by step

  1. Capture a completed tool event. A PostToolUse hook sends the tool name, input/result, session/project information, and tool-use ID to a worker. This does not require the solver to decide to write a note. Filters exclude some calls/content. Capture handler
  2. Save evidence and queue interpretation. The worker best-effort stores raw I/O for calls with stable IDs, then queues an observer message. At this revision the cap is 64 KiB per input/result field, not 64 KiB for the entire row. Missing IDs, exclusions, truncation, or write failures can prevent complete evidence retention. Dual write, storage cap
  3. Observer writes a discovery. A separate model, instructed not to investigate independently, converts activity into observations: title, type, facts, narrative, concepts, and files read/modified. It may skip routine activity. A stop hook also requests a progress summary, including completed and next steps. Observer prompt
  4. Commit notes and update search. Parsed observations enter SQLite; vector-index synchronization happens asynchronously. At resume, a bounded recent-memory view is injected. The session-start hook includes compact, so this can support a continuing task—not only a later task. Persistence, asynchronous indexing, resume triggers
  5. Solver selects how deeply to read. Search returns a compact index; timeline supplies neighboring events; selected observations supply details; get_tool_uses can recover original I/O. Timeline helps distinguish “tried a fix” from “later proved it wrong.” Both writing and retrieval are guided by prompts, not evidence here of a separately RL-trained policy. Retrieval instructions

In our example, the observer could write “tenant omitted from cache key; one caller patched; two-tenant regression unresolved.” After compaction, the solver searches for tenant cache, reads nearby events, fetches that observation, and requests the exact failing assertion only if needed. This is an illustration, not a claim that the implementation always extracts the correct lesson.

Two details that matter when adapting it

A queued write is not a completed memory. The inspected path acknowledges ingestion before the observer finishes; search indexing can lag behind storage. For a controlled first version, use synchronous checkpoint writing or wait until every event through checkpoint N has been processed or explicitly skipped, and all selected notes are committed and searchable, before resetting context. Otherwise apparent forgetting may be a scheduling race. Queue acknowledgements

A keyword-only clone is an adaptation. Although the docs discuss FTS5, the checked query-bearing search path uses Chroma; simply disabling it is not equivalent to obtaining a working lexical baseline. Implement rg/FTS explicitly if that is the intended experiment. Also, the source-call link can point to the first observation of a batch—not a precise one-note/one-event attribution. Preserve explicit evidence IDs in our own schema. Search routing, source linkage

Borrow first: a separate observer, explicit readiness before reset, and small search results followed by selective fetch. A files/FTS implementation can test this idea without adopting the whole daemon/plugin stack. Count the observer's cost. The documentation's token-saving examples are not a matched-quality long-task success evaluation. Search documentation

3. Codex compaction: replace the working context

Mental model: produce a smaller continuation state and make it the model's next input. This is not inherently a notebook or retrieval system. There are distinct text-summary and provider-native paths; treating both as “a Markdown summary” would hide an important implementation difference.

A. Readable-summary path: the portable idea

In the public Codex source at 7498521, local compaction asks the configured model for a handoff summary, then replaces active history with selected recent real-user messages and the summary; initial context can be refreshed. It is not generically “keep a recent raw tool-output tail.” “Local” means client-orchestrated, not necessarily an on-device model. The summary needs to preserve enough state to continue, and successive summaries may lose detail. Compaction implementation, handoff prompt

The portable mechanism is straightforward:

  1. Observe that active context is approaching a declared limit; leave space for the compaction request and output. Codex exposes a compaction token limit; it can trigger before a turn or during continuing work. Configuration reference
  2. Ask for a task-specific handoff: goal, constraints, verified progress, unresolved questions, failed attempts, current artifacts, and next actions.
  3. Build a smaller next context according to an explicit preservation policy.
  4. Continue the same task and environment; repeat when needed.

For our example, the checkpoint must say that the two-tenant regression remains unresolved. If that distinction disappears, the resumed agent can incorrectly conclude that the task is finished. Nothing about a readable summary automatically makes omitted old tool output searchable.

Our baseline is an adaptation: keep system/task instructions, a bounded checkpoint, and a bounded set of complete recent tool exchanges. This tail policy is our control, not a claim about Codex's exact algorithm. A separate evidence store can later be added.

B. Provider-native compaction: useful reference, different portability

OpenAI's standalone /responses/compact accepts a context that still fits the model window and returns a replacement window. It includes an opaque encrypted compaction item and may retain other items; pass the entire returned window onward unchanged. This is not a human-readable note or a representation one can assume works with a different provider/model.

There is also automatic server-side compaction through context_management and compact_threshold. That route emits compaction during the response flow; its input-chaining rules differ from the standalone endpoint. For a controlled experiment, record which route was used. Official compaction guide

Borrow first: an explicit checkpoint-and-replace operation. Treat actual provider-native compaction as an additional reference arm if the serving stack supports it—not as a drop-in implementation for an arbitrary open-weight model. Opaque state is not proof of a particular KV-compression algorithm, exact recall, or cross-model portability.

Version details: what “Codex does” should not hide

At the inspected revision, local compaction caps retained user messages at approximately 20K tokens. A separate remote-v2 implementation retains eligible user/hook and certain developer/inter-agent messages under a 64K budget, then adds the opaque compaction item; it does not retain ordinary tool traces verbatim. There is also a feature-gated fresh-window reset without summarization. These are distinct paths, not one universal retention guarantee. Remote-v2 source · Reset path.

Background persistent memories generated from prior eligible chats are another mechanism entirely. They are not the same as compacting an active task. Official local-memory documentation.

4. The most useful addition: a checkpoint that can recover evidence

Memex suggests a clean extension: keep a concise indexed summary in the active context while retaining referenced experience blocks outside it. Its CompressExperience operation archives blocks and replaces working history; ReadExperience(index) restores selected evidence. MemexRL trains these decisions, but a prompted version can test the interface before RL. Paper, algorithm and mechanism

In our example, a summary can contain: “two-tenant failure unresolved; exact assertion at event E17.” Later, fetching E17 recovers the concrete result rather than asking the solver to guess what “unresolved” meant. Our implementation proposal is to have the harness copy observed evidence under immutable IDs; the model writes references, not reconstructed copies of supposedly raw evidence.

This is a promising first extension because it isolates a specific failure: the note was useful but insufficiently detailed. Keep the checkpoint text identical and toggle evidence access for paired restart tests. It will not fix a writer that omits both the fact and every route to finding it; test broader archive search separately. Published Memex gains under its modified ALFWorld protocol are not a forecast of gains on our tasks.

PRO-LONG supplies the complementary control: retain an action/history archive and let the solver search or compute over it, without requiring high-quality distilled notes. Its lesson is that a reader may need to compare states or aggregate events, not just retrieve a matching sentence. Start with lexical search; add Python/programmatic analysis as a separate reader enhancement. Its reported experiments start fresh per game, not with cross-game learned memory. Paper

5. A few initial versions to decide on today

These are proposed mechanism-controlled adaptations, not exact reproductions or measured winners. Use the same solver model, task inputs, allowed environment state, context cap, recent-tail policy, and total budget. Keep provider-native Codex as a separately labeled reference because it changes the available representation/service.

Version What changes Question it answers
V0 — checkpoint only At the boundary, write a short handoff and replace old history; no searchable prior notes How far does ordinary text compaction get us?
V1 — solver notes V0 plus task-scoped notes written by the solver and searched with rg/bounded reads Does selective external memory beat one running summary?
V2 — observer notes V0 plus the same note schema/read interface, but a separate observer writes from captured events Does separating writing from solving improve useful memory per unit cost?
V3 — recoverable memory Same notes/checkpoint and preassigned evidence IDs as V2; additionally allow bounded fetch-by-ID How much does evidence recovery repair summary omissions?

Also retain the existing harness unchanged as a reference. It is not V0 if it never compacts. A raw-archive + search arm is valuable next, particularly if V1/V2 struggle to write the right notes. Full-history inference is an upper-context reference only where it actually fits.

For the first paired comparison, give V1 and V2 the same explicit checkpoint schedule and note budget; permit ordinary reads during continuation. Control the writer's input too: a solver with the full conversation and an observer with tool events differ in information access, not only role. A writer-isolation test supplies the same serialized task, prior memory, and permitted event bundle; otherwise report an actor-context versus observer-context comparison. Later compare opportunistic writing against continuous asynchronous observation. Equal budgets do not mean equal realized cost: report both.

For V2/V3 paired continuations, archive and assign event IDs for both, but deny V2 access; keep notes/checkpoint identical. The host's inaccessible diagnostic archive is not solver memory. Use the same checkpoint writer/input policy in every arm, and generate that checkpoint from the pre-note-writing snapshot so incidental note-writing conversation does not become an extra memory channel. Complete closed-loop runs can then let trajectories and notes diverge.

One generic loop, with the method-specific pieces visible

create fresh task-local memory and start the solver
while objective unfinished and total budget remains:
    run a solver action and collect its allowed observation
    record allowed evidence under IDs; restrict access by arm
    finish the complete tool-call/result exchange
    if a declared checkpoint is due:
        save the common pre-note-writing snapshot
        V1: solver updates scoped notes
        V2/V3: observer updates scoped notes
        wait for notes and search index to become ready
        write a bounded checkpoint from that saved snapshot
        replace active context using the common retention policy
        resume with task, checkpoint, and memory-tool instructions
    solver searches/reads memory when it chooses
score only the final task outcome with the protected evaluator
discard this task's memory before a new independent task

The default here tests within-task continuity. For across-task reuse, preserve only the permitted store between separately scored tasks and replace the unfinished-task checkpoint with a new task's objective. That is the separate cross-task protocol, not an unannounced extension of this loop.

6. What to lock down after reading—not silently assume

  1. Boundary: a fixed token threshold, declared checkpoints, or both? Use enough headroom to write the checkpoint before overflow. Never discard half of a tool-call/result pair.
  2. Memory permissions: notes only, exact-event dereference, or full archive search? A diagnostic transcript on the host is not automatically solver-accessible memory.
  3. Writer: same model in an explicit note-writing phase, or separately invoked observer? The observer sees only permitted observations—not hidden grading answers or future events. Give it a separate inference stream and account for its tokens.
  4. Read interface: match index size, returned-token caps, query budget, and fetching behavior between V1/V2. A writer comparison should not secretly be grep versus semantic retrieval.
  5. Commit rule: every event through watermark N must be processed or explicitly skipped; selected notes must be durably committed and searchable. This does not require storing every event as a note. If writing fails, keep the old context or record a failed checkpoint; do not silently reset with missing memory.
  6. Evaluation: final success/quality, total solver + writer + retrieval cost, wall time, repeated investigations, lost constraints, and harmful/stale-note use. A smaller prompt is not itself a success metric.

Use both paired checkpoint continuations and complete closed-loop trajectories. The former isolate restart quality from identical state; the latter expose accumulated errors and the cost of maintaining memory. Include dependencies that become relevant only after several compactions, not just facts immediately queried after being written.

My suggested order: get V0 and V1 working first; add V2 with synchronous checkpoint writes; then test V3's evidence recovery. These are candidate choices for discussion, not a locked repository design. Train writing/search only after the frozen-model versions reveal which failure actually limits performance.

If you remember three things

  • Persisting information and shrinking the prompt are separate operations. Notes without a context policy can still overflow.
  • Writer, reader, and evidence access are separate experimental variables. Copying whole products obscures which one helped.
  • A note should say what remains uncertain and how to verify it. Fluency and compactness do not guarantee that the next continuation can finish the task.
