NOOA: Native Python Object-Oriented Agents (NVIDIA)

10 min read · arXiv:2607.20709 · arXiv · GitHub · X post · Tools & Infrastructure

TL;DR

  • NVIDIA's NOOA ("double-O Agents", arXiv 2607.20709; Furgale, Klingler, et al.) makes an agent a single Python class: methods are actions, fields are state, docstrings are prompts, type annotations are output contracts. A method whose body is ... becomes an LLM-driven loop; a method with real code stays deterministic Python — the boundary is one line wide and visible in source.
  • The load-bearing idea is pass-by-reference: a CodeAct method receives arguments as live Python objects, and the model sees only a bounded preview (type, true length, head/tail sample). The full object stays bound in an execution session the model writes code against, so an agent can process a million-row table while the prompt carries a ten-item preview — the limit becomes the machine, not the context window.
  • A 253-line benchmark-agnostic agent hits 82.2% on SWE-bench Verified with GPT-5.5 (xhigh) at ~28 model calls / 1.1M tokens per task, vs OpenCode's 78.6% and PI's 78.2% at 66 calls / 2.2M tokens — defining most of the accuracy–cost frontier. Across 10 models, the interface itself passes 97.9% of 4,400 capability-test records zero-shot.

Why this matters

This tracker keeps circling one theme: for a frozen model, the harness is where capability, cost, and reliability are decided — the long-horizon survey calls long-horizon ability a property of the Model × Harness system, and the harness-handbook argues scaffolds should be readable, navigable, editable. NOOA is a concrete bet on what the harness's interface should be. Today an agent is scattered across prompt templates, JSON tool schemas, callback code, and a workflow graph — four representations of one behavior, none of them ordinary code. NOOA's claim is that Python already has the right abstractions (classes, methods, types, asyncio, control flow), they're mature, and — crucially — they're dense in LLM training data, so both the human and the model already know the interface.

The second reason it matters is measured, not aesthetic. Because tool outputs stay live as typed Python values instead of being re-serialized into the transcript every turn, NOOA hits frontier accuracy at roughly half the tokens and half the model calls of comparable open harnesses, and it does so without lossy transcript compaction. That's the same insight as PRO-LONG's programmatic memory ("keep the full record, query it as a database, don't compress") and coding-agents-as-long-context-processors, but pushed down into the agent's calling convention: data an agent operates on need not pass through the context window at all.

The core idea

An agent is a Python object; agentic methods are the parts you leave to the model.

from nooa import Agent

TicketKind = Literal["refund", "damaged", "other"]

class Ticket(BaseModel):
    kind: TicketKind
    priority: int = Field(ge=1, le=5, description="Urgency 1 (low) to 5 (high).")
    summary: str = Field(description="Customer-visible summary of the issue.")

class SupportAgent(Agent):
    """You are a support agent for a customer service system."""
    order_db: OrderDB                        # object state: model-visible, by reference

    def is_refund_eligible(self, order: Order) -> bool:   # real body → deterministic
        """Return whether an order is eligible for a refund."""
        return order.delivered and order.days_since_delivery <= 30

    @strategy(PredictStrategy())             # "..." body → single typed LLM call
    async def classify(self, message: str) -> TicketKind:
        """Classify the customer message into the best ticket kind."""
        ...

    @strategy(CodeActStrategy())             # "..." body → iterative code-writing loop
    async def triage(self, message: str, photo: Image | None,
                     order: Order | None) -> Ticket:
        """Triage a customer message and create a support ticket."""
        ...

The class is simultaneously source code, prompt surface, type contract, tool interface, and state boundary. Five design principles drive it: (P1) reuse Python abstractions rather than inventing a DSL; (P2) reframe an agentic loop as a typed method call with pass-by-reference arguments; (P3) move deterministic work (arithmetic, parsing, exact rules) out of the model loop into normal method bodies; (P4) unlock the model's existing Python knowledge by letting it act via code; (P5) expose harness internals (context blocks, event history) as Python APIs the model itself can call. The paper claims NOOA is the first kit to combine six model-facing capabilities on one surface — typed I/O, pass-by-reference, code-as-action, programmable loop engineering, explicit object state, and model-callable harness APIs — and surveys 14 frameworks to show the field converging on subsets of them.

How it works

Figure 5 from the paper: the optional long-term memory subsystem. MemoryManager.install(agent) attaches memory to an unmodified agent; the agent curates its own store via seven tools (write / recall / search / update / forget / associate / deref); a BeforeTurn hook injects associated memories; asynchronous reflection consolidates the store. All state lives in one inspectable SQLite file.

The agentic loop. A @strategy-decorated method with a ... body runs as a loop: render context → call LLM → (if it writes code) execute Python in a restricted Jupyter-like session → append typed events and update state → repeat until the model calls return_result(...) with a value that passes return-type validation. Two built-in strategies: PredictStrategy (one typed LLM call, local retry on validation failure — for classification/extraction) and CodeActStrategy (an iterative REPL where the model calls execute_python(...)). Strategies are per-method and override model/truncation/context, so a small fast model can serve classify while a frontier model serves triage.

Pass-by-reference — the key mechanism. Rendering context does not mean serializing state into the prompt. A list of 100 integers renders as:

records = list(len=100, [:5]=[42, 17, 89, 33, 8], [-5:]=[56, 71, 12, 45, 28])

The preview shows the concrete type, true length, and a head/tail sample. But records is the full 100-element list, bound as a local in the execution environment — the model can for r in records: ... over all of it though only ten elements ever enter context. The amount of data an agent can process is bounded by the execution environment, not the prompt: a method can accept a multi-million-row table and the model works on the whole thing by writing code. This is code-as-action + pass-by-reference together — the model spills results to typed live variables (not untyped text on disk, the bash pattern models already improvise) that persist cell to cell.

Context in three regions, engineered for the KV cache. A cacheable static prefix (system prompt + strategy instructions + doc(self)), an append-only event history of typed events (queryable, collapsible into summaries à la MemGPT), and a dynamic suffix re-rendered each turn (pprint(self), live state). Static prefix never changes, history only appends, volatile state sits at the tail — so live-state updates don't invalidate the cached prefix. Both developer and model manipulate context through the same Pythonic API (self.context[...], self.events.query(...), self.events.collapse(...)).

Safety by construction. eval/exec/compile/input and blocking event-loop calls are rejected; tracebacks come back in IPython format so the next turn can repair code like a notebook cell. Termination is a validated action: the model must return a typed result (e.g. a TaskResult with root cause + evidence + verification command), not just stop talking.

Results

  • Capability tests (does the model even understand the interface?): 88 tests × 5 runs × 10 models = 4,400 records, 97.9% pass zero-shot. Frontier models (Opus 4.8, GPT-5.5, Gemini 3.1 Pro, GLM-5.2, Kimi K2.6, Nemotron 3 Ultra) 99.2%; small models 96.0%. GPT-5.5 is perfect. The residual failures concentrate in six "stress" families (batch bookkeeping, error recovery, multi-step REPL) — 84.7% — which the authors read as long-horizon reliability frontiers, not interface-comprehension gaps.
  • SWE-bench Verified: NOOA leads every open harness in every config. GPT-5.5: 67.2 / 78.8 / 82.2% (off/high/xhigh); Opus 4.6: 79.8%. vs OpenCode 78.6% and PI 78.2% at xhigh. Narrows the gap to closed systems (Codex 88.7%, Claude Code 80.8%) with a 253-line agent.
  • Cost: 82.2% at ~28 calls / 1.1M tokens vs PI's 78.2% at 66 calls / 2.2M — roughly half the calls and tokens for higher accuracy. NOOA defines most of the score–cost Pareto frontier (Figure 6).
  • Terminal-Bench 2.0: bigger margin — 73.0% (GPT-5.5 high) vs OpenCode 60.7%; the interface helps most when the model supplies less planning discipline of its own.
  • CyberGym L1 (vulnerability discovery): 86.8% with GPT-5.5 (network blocked), top open-source agent, beating most closed solutions — validated by an 18-pass red-team cheat-check audit.
  • ARC-AGI-3: the sharpest demonstration — NVIDIA's prior 6-agent DreamTeam world-model system (1,821 lines of role prompts + a 4,690-line retrodiction engine) collapses into one NOOA agent + a 50-line skill, with the CodeAct REPL as simulator and the memory subsystem as carry-forward ledger. Reaches 50.2% RHAE on GPT-5.5 and 85.1% on GPT-5.6-sol (vs 13.3% for raw GPT-5.6-sol — a 6.4× harness effect), under $20/game, with a +11.8-point lift over the same skill using markdown files instead of the memory subsystem.

Figure 7 from the paper: RHAE (action-efficiency score vs per-level human baselines) over the two-hour fleet cap. The dashed line is ARC Prize's evaluation of raw GPT-5.6-sol (13.3%); dots mark each $4 of per-game spend.

How it connects

  • OpenHarness: Claude Code Reimplemented in Python and Harness Handbook — same thesis (harnesses should be ordinary, inspectable code); NOOA pushes it into the model-facing calling convention, not just the developer-facing implementation.
  • PRO-LONG: Programmatic Memory and Coding Agents Are Effective Long-Context Processors — pass-by-reference is the calling-convention version of "keep the full record live and query it with code" rather than stuffing it into the prompt.
  • Training Agents Inside Their Harnesses and The Agent Is Its Own Best Speculator — NOOA is the substrate such harness-native training/latency work would run on; its KV-cache-friendly three-region context is the same prefix-stability concern.
  • NVIDIA's DreamTeam / workspace optimization (cited as companion work sarafian2026workspace) — NOOA's long-term memory targets the transfer problem that workspace optimization leaves open (the workspace is discarded at each task boundary).
  • wGraph and NOOA are two answers to "how should agent workflows be expressed" — graph serving engine vs plain Python objects; a useful contrast for the multi-agent-orchestration debate in this tracker.

Critical take

The strongest evidence is the ARC-AGI-3 collapse and the token-efficiency numbers; the weakest is the framing that this is fundamentally new. Pass-by-reference over a live REPL is essentially what CodeAct/OpenHands and Pydantic's CodeMode already do, and the paper's own Table 7 admits Microsoft's harness providers, OpenAI's sandbox agents, and Codex's code mode all shipped these ideas during the evaluation window — so "first to combine all six" is a real but narrow claim, and several competitors are marked experimental/flag-gated in ways that flatter NOOA. The benchmark comparisons also mix backends and reasoning efforts (GPT-5.5 xhigh for the headline SWE-bench number, Opus 4.6 elsewhere), and NOOA doesn't win everywhere — PI edges it on Terminal-Bench GPT-5.5 xhigh. The deeper open question is the one the stress tests expose: the interface is trivially learnable (97.9%), but disciplined multi-step use of it — batching, recovery, decomposition — is still a capability frontier that scales with model quality, so how much of NOOA's win is the interface vs the frontier model driving it remains partly confounded (the margins shrink as reasoning effort rises, which the authors honestly note). Still: a 253-line agent competitive with Claude Code, at half the tokens, on an interface models use zero-shot, is a strong argument that a lot of agent-framework complexity is incidental.

If you remember three things

  1. The ... body is the whole idea: one line marks the boundary between deterministic Python and an LLM loop, so an agent is testable, traceable, refactorable software instead of a scatter of prompts, schemas, and callbacks.
  2. Pass-by-reference breaks the context-window ceiling: the model sees a bounded preview while the full typed object stays live in the execution session — so data volume is bounded by the machine, and you get ~2× token/call efficiency for free by never re-serializing tool outputs.
  3. Harness > model, quantified: the same GPT-5.6-sol goes from 13.3% raw to 85.1% inside NOOA on ARC-AGI-3, and a 6-agent 6,500-line system compresses to one agent + a 50-line skill — the strongest single data point in this tracker for "the scaffold is where the capability lives."
