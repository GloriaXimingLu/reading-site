Living-Harness: Post-Episode Harness Evolution via Episodic Memory + State Graphs

18 min read · arXiv:2607.26598 · arXiv · GitHub · X post · Self-Improving Agents & Harnesses

TL;DR

  • "Living-Harness Is an Interactive-Agent Evolver" (arXiv 2607.26598; Yuetian Du, Yucheng Wang, He Xu, Jiexu Xu, Shanwen Tan, Bing Zhao, Boyu Yang, Zhijie Xu, Ming Kong, Hu Wei, Jie Liu, Qiang Zhu) makes the harness the object of self-improvement: after each evaluated episode a fixed domain-level Evolution-SOP converts trajectory + evaluator signals into posterior evidence and commits bounded updates to two persistent stores — episodic memory (trigger conditions, failure patterns, recovery actions) and a state graph (state nodes, repair edges, transition rules) — while tools, base context, and weights stay frozen.
  • With GPT-5.2-medium as the actor it reaches 83.09 average Pass@1 on τ²-Bench (+10.07pp over Reflexion, above Gemini 3 Pro's 82.92) and 65.50 on MultiWOZ-2.4 (+9.91pp over ReasoningBank). The evolved state transfers retrieval-only: frozen, it improves every reported domain for Gemini 3 Pro, GLM-5, Qwen3-max, and Kimi-k2 — MultiWOZ Taxi goes 0.00 → 43–45.
  • The distinctive engineering is commit discipline: candidate repairs must pass schema, scope, evidence, constraint, and merge gates before touching persistent state, and an episode's evidence is never available when that episode is scored. Ablating the Evolution-SOP (keeping both containers) costs 9.7 points — the win is structured bounded evolution, not bolted-on memory.

Why this matters

The recurring disease of interactive agents is that they recover without learning: Reflexion-style retries fix the current instance, the correction evaporates with the episode, and the same tool-call omission reappears next week. The paper's case study is the perfect specimen — the agent repeatedly concludes "this user should be transferred to a human" and repeatedly fails to call transfer_to_human_agents(), because a textual lesson is not an executable repair.

Living-Harness is the most disciplined version of that argument so far. It draws the update boundary tightly — only the harness state evolves; tools, base context, domain rules, and the Evolution-SOP itself are frozen — and splits procedural knowledge into two representations: memory for why/when a repair applies, a graph for where it changes the workflow. That the resulting state is model-agnostic (frozen, it lifts four other backbones purely via retrieval, including a stronger one) is the headline evidence that harness-level learning is real capital, not prompt-tuning residue: a concrete existence proof that post-deployment procedural repair accumulates without touching weights.

The paper's Table 6 scores related systems on four axes: what object is updated, whether it persists, whether the external procedure is revised, and whether commits are bounded by explicit gates. ReAct keeps nothing; Reflexion keeps verbal memories without revising procedure; AWM revises workflows "partially"; ReasoningBank persists reasoning strategies; EvoTest rewrites agent configurations; Meta-Harness rewrites harness code. By the authors' accounting, none of those rows has bounded gates. That fourth column is the actual claim to novelty, and the ablations defend it.

The core idea

Separate fixed execution resources from an evolving procedural state. In domain \(d\) at episode \(n\), the harness is

\[H_{d}^{(n)}=\left(C_{d}^{\mathrm{act}},\psi_{d},S_{d}^{(n)}\right),\qquad S_{d}^{(n)}=\left(\mathcal{R}_{d}^{(n)},G_{d}^{(n)}\right),\]

where \(C_{d}^{\mathrm{act}}\) is the frozen actor context (tools, base context, domain rules), \(\psi_{d}\) the frozen domain-level Evolution-SOP — the hand-written document that says how to turn a finished episode into an update — and \(S_{d}^{(n)}\) the only evolving part: episodic memory \(\mathcal{R}_{d}^{(n)}\) plus state graph \(G_{d}^{(n)}\), both as they stand at the start of episode \(n\). Memory holds why and when a repair applies; the graph holds where in the workflow it belongs. Initialization is empty memory and a coarse scaffold, \(S_{d}^{(0)}=(\emptyset, G_{d,\mathrm{scaf}})\), supplying only domain roots and task-family structure — every fine-grained repair is induced from evaluated experience.

Figure 1 from the paper: a static harness is fixed after deployment; Living-Harness evolves exactly two components — episodic memory (trigger conditions, failure patterns, recovery actions) and the state graph (state nodes, repair edges, transition rules) — under Evolution-SOP guidance.

How it works

The loop in one sentence. Every episode Living-Harness does the same five things: run the task with what it has already learned, score the run, turn the run into one candidate memory entry and one candidate workflow repair, screen those candidates through five gates, and commit whatever survives. Everything else is detail about what a candidate contains and what the gates throw out.

Figure 2 from the paper: the rollout–evaluate–update loop. Memory and state graph evolve (flame icons); tools and context are frozen (snowflake icons). Over cycles the state goes from sparse/incomplete to structured/well-connected.

One episode, start to finish

The paper's Figure 4 case study, in the Telecom domain of τ²-Bench. A user reports "Phone shows No Service." The hidden cause is a contract-end suspension, which the domain's policy says must be escalated to a human agent — the agent has to actually execute the transfer, not announce it.

Step 1 — Retrieve what earlier episodes learned. Before the agent starts, a briefing is assembled. A query is built from the task and its task family, and the top three entries are pulled from memory and the top three fragments from the state graph — same-family evidence first, other families only when same-family evidence is thin, ranked by semantic relevance, family compatibility, and accumulated confidence. Those are rendered into the actor's context, and the frozen domain rules always take precedence over anything retrieved. On the very first episode there is nothing to retrieve.

Step 2 — Run the task. The agent works with frozen tools, frozen base context, and frozen domain rules, plus that briefing. It may retry inside the episode — up to three trials, matching Reflexion's budget — but the scratch notes from those retries are quarantined and never reach either store. This is exactly where the baseline fails: the Reflexion-only agent spends all three attempts for reward 0, escalating its own hints ("call transfer tool" → "do not only announce transfer" → "execute formal transfer action") and never firing the tool.

Step 3 — Score it, before anything is learned from it. The evaluator scores the finished episode. Nothing extracted from this episode was available while it ran, and nothing extracted from it is available while it is scored — so every reported number belongs to a harness state built entirely out of earlier episodes.

Step 4 — Turn the episode into a proposal. Only now does the domain's Evolution-SOP run — the frozen, hand-written recipe for turning a finished episode into an update. First it abstracts the episode down to its reusable content: objective, verified facts, outcome, and the critical failure-or-recovery point. Then two extractors split that abstraction into two candidates — something to remember, and something to change in the workflow. Under the SOP's instruction "Extract executable missing repair, not vague advice," the Telecom failure produces a memory entry (for terminal-suspension cases, the missing step was that the transfer tool was never executed; the recovery action is to call it once suspension is confirmed) and one repair edge: confirm the terminal suspension, then call the transfer tool — guarded by the condition "only if contract-end suspension is confirmed."

Step 5 — Screen the proposal through five gates. A candidate is not a commit. Five checks run before anything is written, and each throws out a different kind of bad update:

Gate Rejects What that stops here
Schema malformed extractor output a truncated entry — one repair pass is allowed, then it is discarded
Scope over-generalization a Retail refund lesson leaking into Airline retrieval
Evidence ungrounded self-critique a plausible-sounding lesson with no evaluator signal, trajectory evidence, or repeated failure behind it
Constraint repairs that relax policy an edge that would skip a tool precondition or override a frozen domain rule
Merge near-duplicates a fifth phrasing of an edge already stored — folded into it, not inserted

The guard clause on the Telecom edge is scope and constraint doing their job: without it, the repair would escalate every telecom complaint.

Step 6 — Commit the survivors. Accepted memory entries are written or strengthened; accepted graph updates add repair edges or raise confidence in existing ones. Nothing else in the harness moves. In the next cycle the same complaint retrieves that entry and that edge, and the run goes: retrieve the account, confirm the suspension, fire the transfer tool — one attempt, reward 1.

The machinery behind steps 1, 4, and 6

Step 1, what retrieval hands the actor. Retrieval builds a task-conditioned query \(q_n = Q(x_n, f_n)\), where \(x_n\) is episode \(n\)'s task and \(f_n\) its task family. The two stores are queried separately and the results rendered into one block of context:

\[\kappa_{n}=\operatorname{Render}\!\left(\operatorname{Retrieve}_{\mathcal{R}}(\mathcal{R}^{(n)},q_{n}),\operatorname{Retrieve}_{G}(G^{(n)},q_{n})\right),\qquad \tau_{n}\sim p_{M}\!\left(\tau\mid x_{n},C_{d}^{\mathrm{act}},\kappa_{n}\right)\]

Here \(\operatorname{Retrieve}_{\mathcal{R}}\) and \(\operatorname{Retrieve}_{G}\) each return the top \(k{=}3\) items from memory \(\mathcal{R}^{(n)}\) and graph \(G^{(n)}\) as they stand at the start of the episode; \(\operatorname{Render}\) formats them into the actor-facing string \(\kappa_n\); \(p_M\) is the actor model \(M\)'s distribution over trajectories; and \(\tau_n\) is the trajectory it samples given the task, the frozen context \(C_d^{\mathrm{act}}\), and \(\kappa_n\). The state is frozen for the entire rollout.

Why conditioning on retrieved procedure helps at all. The paper frames this as a program-state POMDP: the environment state is augmented with an episode-level program state \(z^{(n)}\) induced by \(S^{(n)}\), constant within an episode and changed only by post-episode updates. Proposition 1 then says retrieval provably cannot hurt in the ideal case:

\[\mathcal{B}(\mathcal{I}_{s,z})=\mathcal{B}(\mathcal{I}_{s})-\Gamma_{z}\leq\mathcal{B}(\mathcal{I}_{s}),\qquad \Gamma_{z}=\mathbb{E}\!\left[\operatorname{Var}\!\left(\mathbb{E}[\xi\mid\mathcal{I}_{s,z}]\mid\mathcal{I}_{s}\right)\right]\geq 0\]

Symbol by symbol: \(\xi\) is an execution-relevant latent — the thing the agent needs to infer but cannot see, such as "this account is suspended at contract end"; \(\mathcal{I}_{s}\) is the information available from the interaction history \(h_t\) alone, and \(\mathcal{I}_{s,z}\) that same history plus the program state; \(\mathcal{B}(\mathcal{I})=\mathbb{E}[\operatorname{Var}(\xi\mid\mathcal{I})]\) is the Bayes error bound — the irreducible uncertainty about \(\xi\) given information \(\mathcal{I}\); and \(\Gamma_{z}\ge 0\) is how much of that uncertainty the program state resolves, written as the variance of the improved estimate. So the bound is tightened by \(\Gamma_z\) and never loosened. The approximate version adds an extraction-error term \(\epsilon_z\): retrieval helps only when the information gained exceeds the noise of extracting and using it — which is precisely the job the commit gates are hired to do.

Step 4, from trajectory to candidate. After the evaluator emits signals \(y_n\), the SOP runs a posterior-then-extract pass:

\[e_{n}=\operatorname{Post}_{M,\psi_{d}}\left(x_{n},\tau_{n},y_{n},C_{d}^{\mathrm{act}}\right),\qquad u_{n}=\left(u_{n}^{\mathcal{R}},u_{n}^{G}\right)=\operatorname{Extract}_{\psi_{d}}(e_{n})\]

\(e_n\) is the episode abstraction — the objective, verified facts, outcome and critical failure/recovery point — produced by model \(M\) under the frozen SOP \(\psi_d\) from the task, the trajectory, the evaluator signals and the frozen context. \(\operatorname{Extract}_{\psi_d}\) then splits \(e_n\) into \(u_n^{\mathcal{R}}\), the memory candidate, and \(u_n^{G}\), the graph candidate.

The extractor prompts (Appendix E) are the real specification of "procedural repair," since they define the JSON that gating is applied to. The τ²-Bench memory extractor returns 0–3 items with seven fields each: title (short, action-oriented), applicability (when to retrieve it), failure_class (the prompt names lookup_failure, missing_precondition, wrong_branch, eligibility_gap, workflow_gap), missing_step, recovery_action, family, and source_type ∈ {failure, failure_informed_success} — the second reserved for successful episodes that are only informative because an earlier failed branch or reflexion signal exposed the lesson. Items must be atomic and reusable within their family; unjustified evidence must return "memory_items": []. The workflow extractor returns at most one fragment: family, precondition, a state_sequence of 3–8 abstract labels (its own examples: resolve_identity, validate_preconditions, prepare_action, execute_task_action, confirm_outcome), critical_checks, a commit_gate — "the last condition that must be true before the irreversible step" — postcondition, tool_hints, status ∈ {candidate, stable}, and repair_origin: true when the fragment came from a corrected path. Insufficient evidence returns {"workflow": null}.

Step 6, the commit and the firewall. Survivors land as \(S^{(n+1)}=\operatorname{Update}_{\psi_{d}}\left(S^{(n)},u_{n};C_{d}^{\mathrm{act}}\right)\) — the next episode's state is the current state updated with the accepted candidate under the frozen SOP and subject to the frozen context; rejected candidates leave \(S^{(n+1)}=S^{(n)}\). The ordering is the load-bearing part: the actor rolls out on \(S^{(n)}\), the evaluator scores, and only then do the posterior generator and the extractors get to look at the trajectory. Evidence generated by an episode is never available when computing that episode's reported score — a system that commits before scoring is effectively reading the answer key. On τ²-Bench the state updates after each scored episode; on MultiWOZ-2.4 updates synchronize every four, so the whole window is rolled out and scored before anything commits. The Evolution-SOPs themselves are run-frozen per-domain documents — eight of them in the appendix — while the posterior–extract–commit machinery is shared across domains.

What the loop cannot tell you

The ablations locate the gain in the hand-written part. Removing the domain Evolution-SOP while keeping both containers drops the τ²-Bench average from 83.09 to 73.38 — the largest single hit, and within 0.4 points of Reflexion's 73.02. Strip the posterior interpretation and the domain-specific gates and a memory-plus-graph harness lands essentially where task-local reflection already was. Removing memory costs less (77.34), removing the state graph less still (79.50). The stores are complementary, but the eight bespoke SOP documents are a real authoring cost and a hidden prior, and the paper explicitly declines to claim zero-shot SOP transfer. "Self-evolving" is doing less work here than "well-specified evolution protocol."

Gates screen, they do not audit. The authors state the ceiling themselves: the gates reduce the chance that noisy or misattributed evaluator signals become persistent state, but "they do not provide full rollback or regression testing." A plausible-but-wrong repair that clears the evidence gate persists and is retrieved forever; nothing re-checks old entries when policy changes, and nothing demotes or expires the status: candidate entries the schema anticipates.

No matched-budget control. The headline averages are the state after three evolution cycles over the benchmark, each cycle spending a scored rollout plus posterior and extractor calls on every task. The paper reports no arm in which Reflexion, ReasoningBank, or the other baselines are given an equivalent budget, so "better per episode" and "more episodes plus more LLM calls" are not separated.

Loop over episodes n = 0, 1, 2, ... in domain d:
  1  q_n ← Q(x_n, f_n)                          # task-conditioned query, family scope f_n
  2  κ_n ← Render(top-3 from R^(n), top-3 from G^(n))   # same-family-first retrieval
  3  τ_n ← rollout under frozen tools/context C_d + κ_n
     (task-local reflexion ≤ 3 trials allowed; its buffer is NEVER written to R or G)
  4  y_n ← Evaluator(x_n, τ_n)                  # score BEFORE any update (no same-episode reuse)
  5  e_n ← Post(x_n, τ_n, y_n, C_d)             # episode abstraction via Evolution-SOP ψ_d
  6  (u_R, u_G) ← Extract_ψd(e_n)               # candidate repair, schema-constrained JSON
  7  gate the candidate:
       schema gate     — valid memory/graph schema (one repair pass, then discard)
       scope gate      — committed to its task family unless transfer is supported
       evidence gate   — grounded in evaluator feedback / trajectory / repeated failure
       constraint gate — must not override frozen policies or tool preconditions
       merge gate      — near-duplicates merged via semantic hash + confidence, not inserted
  8  if accepted: R^(n+1), G^(n+1) ← write/strengthen entries and repair edges
     else:        S^(n+1) ← S^(n)

The line to watch is step 4 sitting above steps 5–8: everything the episode teaches is computed strictly after the number it is scored on.

Results

On τ²-Bench with GPT-5.2-medium, Living-Harness averages 83.09 Pass@1 vs. 73.02 for Reflexion (best interactive baseline; +10.07pp) and 82.92 for Gemini 3 Pro, the best flagship. Per-domain: 85.96 Retail, 88.00 Airline, 78.07 Telecom. On MultiWOZ-2.4 it averages 65.50 vs. 55.59 for ReasoningBank (+9.91pp) and 53.10 for Reflexion; slightly below Reflexion on 1-domain tasks (76.55 vs 77.88) but best on the 2- and 3-domain groups (70.52 and 25.87) — repairs pay off most when procedures compose across domains. AWM (51.08 / 42.80) and EvoTest (50.62 / 37.80) trail badly, both landing below the un-augmented GPT-5.2 backbone on τ²-Bench.

Evolution dynamics (Table 2): Retail climbs 57.02 → 85.96 and Telecom 57.39 → 78.07 over three cycles; MultiWOZ final-cycle gains are +13.96 Restaurant, +24.11 Hotel, +22.83 Train, +25.25 Attraction, +28.71 Taxi. Biggest jumps after cycle 1, refinements later — "repair missing workflow steps first, then polish" — though Airline peaks at 88.00 in cycle 2 and slips to 86.00, one of the "occasional mild fluctuations" the authors acknowledge. State growth is roughly linear (Retail: 198 memory entries, 714 nodes / 1,368 edges after cycle 3; Airline adds exactly +200 edges per cycle).

Ablations (Figure 3). Swapping the domain Evolution-SOP for a generic extractor while keeping both containers costs 9.71 points on the τ²-Bench average — by far the largest hit, and read in full above under What the loop cannot tell you. Disabling memory retrieval and updates costs 5.75; disabling graph retrieval and updates costs 3.59. The full system is best in every domain, so no one domain carries the average.

Retrieval-only cross-model transfer (Table 3) is the most consequential result. The GPT-5.2-evolved MultiWOZ state is frozen and handed to four other backbones, retrieval only, no further global updates. Every reported domain improves for every model. Gemini 3 Pro — the strongest flagship in Table 1 — goes 47.83 → 66.13 Restaurant, 45.18 → 63.71 Hotel, 55.35 → 66.87 Train, 63.64 → 66.67 Attraction, 30.26 → 68.72 Taxi. GLM-5 goes 24.94 → 39.36, 16.50 → 38.83, 18.18 → 38.38, 27.27 → 38.13, 0.00 → 43.08; Qwen3-max and Kimi-k2 show the same shape, both taking Taxi from 0.00 to 45.13. The three 0.00 → 43–45 jumps are the striking part: a domain three backbones fail completely becomes solvable at roughly the same rate for all three once the procedure is supplied, which reads as the harness state rather than the model setting the ceiling there (inferred from the pattern — the paper doesn't decompose it). Portability implication: what was learned is not a GPT-5.2-specific prompt idiom but a procedure any competent actor can execute — evolve it once on your strongest model, ship it to your cheapest.

How it connects

  • Recursive Harness Self-Improvement — the other "the harness is the object" paper, and a near-mirror image: RHI rewrites a prompt-level spec of the whole agent loop from pairwise preferences, with no persistent per-episode state; Living-Harness leaves the spec alone and accumulates state. Neither is recursive in the improver — RHI's optimizer is a fixed external model, Living-Harness's Evolution-SOP is a frozen document.
  • EvoHarness-RL — trains harness usage into the weights; Living-Harness is the complementary weights-frozen path where all learning lives in retrievable state.
  • Harness Handbook — argues for readable/editable harnesses; the schema-constrained JSON memories and explicit repair edges here are what "editable" looks like when the editor is an evaluated pipeline rather than a human.
  • MSCE: Memory into Executable Skills — same diagnosis (textual lessons don't execute), different artifact: MSCE compiles memory into skills, Living-Harness into state-conditioned repair edges.
  • Agentic Context Management — the retrieval-and-render step (top-3, same-family-first, fixed rules take precedence) is a concrete context-management policy for procedural knowledge.
  • Meta-Harness — a row in this paper's own comparison table and the natural contrast: it rewrites harness code with unbounded edits and full-trace evidence; Living-Harness rewrites harness state with bounded, gated commits. Same object, opposite risk posture.
  • It also reads as a working instance of scaffold-level (L2) evolution with evidence-gated commits in the sense of the Reliable Self-Evolving Agents survey — including honest compliance with "score before update."

Critical take

The three limits recorded above under "What the loop cannot tell you" are the load-bearing ones: the largest ablation hit lands on the eight hand-written SOPs, the gates screen without rollback or regression testing, and no arm gives the baselines a matched budget. Two more compound them. The state grows linearly without pruning — +456 edges per cycle in Retail, 951 memory entries in MultiWOZ Restaurant — which top-3 retrieval masks at this scale but will not at 100 cycles; retrieval quality, not storage, is what breaks first, and Airline's −2.00 slip in cycle 3 hints that stale entries already cost something. And the whole loop is downstream of a post-episode evaluator signal: benchmarks hand you one, deployments mostly do not, so the honest scope of this method today is "settings with a scorer." Score-before-update is genuine hygiene, and the authors are careful about what it does not establish — no test of robustness to shuffled stream orders, no measured reduction in failure recurrence, no held-out task families, no policy perturbations. What survives is still the most disciplined post-deployment learning loop in this tracker, and the retrieval-only transfer result is hard to explain away: whatever the SOPs contributed, the product is a procedure four other models can execute.

If you remember three things

  1. Bounded target: only \(S=(\mathcal{R},G)\) evolves — trigger/failure/recovery memories plus state-graph repair edges — under a frozen Evolution-SOP, frozen tools/context, frozen weights; candidates pass schema/scope/evidence/constraint/merge gates, and episodes are scored before their evidence can commit.
  2. It beats the strongest interactive baselines by ~10pp Pass@1 on τ²-Bench (83.09) and MultiWOZ-2.4 (65.50); the SOP ablation (83.09 → 73.38, essentially Reflexion's 73.02) shows structured bounded evolution — not memory per se — is the active ingredient.
  3. The evolved state is portable capital: frozen and reused retrieval-only, it improves four other backbones on every reported domain, taking three separate 0.00 scores to ~45 and Gemini 3 Pro's Taxi from 30.26 to 68.72.
