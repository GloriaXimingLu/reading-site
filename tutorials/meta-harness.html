Meta-Harness: Outer-Loop Search over Harness Code with Full Execution-Trace Access

18 min read · arXiv:2603.28052 · arXiv · X post · yoonholee.com · Self-Improving Agents & Harnesses

TL;DR

  • "Meta-Harness: End-to-End Optimization of Model Harnesses" (arXiv 2603.28052; Yoonho Lee, Roshen Nair, Qizheng Zhang, Kangwook Lee, Omar Khattab, Chelsea Finn — Stanford + KRAFTON + MIT) automates harness engineering with the most minimal outer loop imaginable: a coding-agent proposer (Claude Code with Opus-4.6) gets unrestricted filesystem access to the source code, scores, and raw execution traces of every prior candidate harness, navigated with grep and cat rather than ingested as a prompt.
  • The design bet is feedback bandwidth: prior text optimizers (OPRO, TextGrad, AlphaEvolve, GEPA, TTT-Discover) hand the proposer 0.002–0.026 MTok per iteration; Meta-Harness exposes ~10 MTok — one evaluation can produce up to 10M diagnostic tokens. The ablation says this is the ingredient: full-trace access reaches 50.0 median / 56.7 best search-set accuracy vs 34.6/41.3 for scores-only, and LLM-written summaries don't recover the signal (34.9/38.7).
  • Three domains: +7.7 points over ACE on online text classification with ~4x fewer context tokens (48.6% vs 40.9%); a discovered BM25 retrieval harness lifting 200 IMO-level problems +4.7 points averaged over five models (four never seen during search); and TerminalBench-2 harnesses at 76.4% (Opus 4.6, above hand-engineered Terminus-KIRA's 74.7%) and 37.6% (Haiku 4.5, #1 among reported Haiku agents).

Why this matters

One nuance the thread mangles: the "up to 6x performance gap from the harness alone" is the paper's opening citation (SWE-bench Mobile, Tian et al. 2026), not something this paper proves — it's the motivating fact that harness choice can matter as much as weights. What the paper contributes is an answer to the question this tracker keeps circling: if harness engineering is real engineering, can an agent do it? Every prior attempt inherits machinery from text optimization — mutation operators, parent selection, reflective summaries — all of which compress feedback because raw feedback wouldn't fit in a prompt. The authors are fair about why: that compression is "a pragmatic scalability choice, not evidence that longer-range dependencies are uninformative." But it is exactly what breaks harness search. A harness is a stateful program whose early decision (what to store, when to retrieve) surfaces as a failure many steps later, and a scalar score or paragraph summary destroys the causal chain needed to trace it back. The fix is architectural: stop compressing. Put everything on disk, hand the proposer a terminal, and let a coding agent — the artifact class trained on exactly "navigate a big repo and find the bug" — decide what to read. It's the Bitter Lesson applied to prompt optimization, and the paper says so, citing Sutton.

The core idea

A harness is a stateful program that wraps a frozen model: it builds prompts, the model responds, the harness updates its state, and the cycle repeats until the task ends. Write \(H\) for the harness, \(M\) for the frozen model, \(\mathcal{X}\) for the distribution of task instances it will face, and \(x\) for one instance drawn from it. Running \(H\) with \(M\) on \(x\) yields not a fixed result but a distribution over runs, \(p_M(H,x)\); one run \(\tau\) sampled from it is a trajectory — the full record of prompts, tool calls, model outputs, and state updates — and \(r(\tau,x)\) is the benchmark's reward for it. The objective is the obvious one:

\[H^{*}=\operatorname*{argmax}_{H}\;\mathbb{E}_{x\sim\mathcal{X},\,\tau\sim p_{M}(H,x)}\;r(\tau,x)\]

\(\mathbb{E}\) averages over both sources of randomness — which instance is drawn and which run the harness-plus-model produces on it — and \(H^{*}\) is the harness with the highest average reward, searched over executable programs (here: single-file Python) with \(M\) held fixed throughout. When accuracy and context cost both matter, candidates are kept as a Pareto frontier — the set of harnesses no other candidate beats on both axes at once — instead of collapsing to a single scalar.

Figure 2 from the paper: the whole method. Propose from the filesystem, evaluate against tasks, append all logs back to the filesystem.

What is deliberately absent is the search apparatus prior work considered necessary. Meta-Harness keeps a population and a Pareto frontier but imposes no parent-selection rule, no mutation-operator taxonomy, no archive summarization: the proposer inspects any prior harness and its traces, picks which failure mode to attack, and chooses between a local edit and a full rewrite. Each evaluated candidate contributes one directory to a growing filesystem holding its source code, its scores, and its raw traces — and that filesystem, not a prompt, is the interface between iterations.

How it works

The loop in one sentence. Each iteration a coding agent reads a directory tree containing every harness tried so far — its code, its score, and the complete logs of every run it produced — and writes one or more new harnesses, which are evaluated and appended to the same tree. Everything else is detail about what is in the tree and how much of it the agent chooses to read.

One iteration, start to finish

The setup, from the paper's own search log (Appendix A.2, TerminalBench-2, Opus 4.6, quoted verbatim). This run is ten iterations long and the seventh is the one that turns it around, so the six before it are the setup. Iterations 1 and 2 bundled plausible structural bugfixes with prompt-template rewrites and regressed sharply against the log's 64.4% baseline for Terminus-KIRA, the hand-engineered harness the population was seeded from (58.9%, then 57.8%). Iterations 4–6 kept probing the same subsystem and kept losing. The question iteration 7 answers: after six straight regressions, what does the proposer do differently?

Step 1 — What is on disk when the iteration starts? One directory per evaluated candidate, holding its source code, its scores, and its execution traces — prompts, tool calls, model outputs, state updates, all of it. By iteration 7 that is the hand-built harnesses the population was seeded with plus six iterations of failures, every one with its run logs intact. Nothing has been summarized or discarded.

Step 2 — Read whatever looks relevant. The tree is far larger than any context window, so the proposer works it with terminal tools rather than swallowing it. Here it opens the traces around the completion state machine — the logic deciding when a task counts as finished — that it has attacked since iteration 4, including the trajectories the log cites directly: agents spinning through 30–60 verification steps on configure-git-webserver after effectively solving the task.

Step 3 — Explain the failures rather than counting them. The proposer's earlier reasoning is itself part of the record, and iteration 3 shows what that buys. Having seen two bundled changes regress, it concluded that "the structural bugfixes were confounded with harmful prompt changes," reverted only the prompt, re-tested the structural fix in isolation, and lost 1.1 points instead of five to seven (63.3%) — confirming the confound and rescuing the part that was fine. By iteration 7 the diagnosis is blunter: every edit to the completion state machine, confounded or not, has cost points.

Step 4 — Decide what kind of change to write. The system imposes no menu here; these are behaviours visible in the log rather than operators the harness offers.

Move When the proposer reaches for it In this log
Local edit a failure localises to a specific mechanism iterations 1–6, all on the completion state machine
Full rewrite the design itself looks wrong none described
Compose two candidates two prior harnesses each hold part of the answer iteration 8, folding the winner into an earlier structural fix
Purely additive edits to a subsystem keep regressing, so stop editing it iteration 7 — the pivot that wins

Iteration 7 takes the last of these: leave the existing control flow entirely alone and gather an environment snapshot in one shell command before the first model turn.

Step 5 — Cheap check first, expensive check second. A new harness passes an interface-validation smoke test before anything is spent evaluating it — enough to catch duds that do not even run. Survivors are then evaluated on the search set, the only tasks the loop may optimize against. This one wins: it is the first candidate in the run to beat its seed.

Step 6 — Everything goes back on disk. Code, scores, and traces are appended as a new directory, and the candidate joins the Pareto frontier over accuracy and context cost. The history keeps paying out afterwards: iteration 8 composes this winner with an earlier structural fix, and iteration 10 cites a lesson learned in a separate earlier search run. Throughout, the proposer never sees test-set results — the search set and its traces are its only signal.

The final artifact is Terminus-KIRA plus roughly 80 lines of bootstrap: working directory, an /app listing truncated to 20 entries, language and package-manager versions, memory, all guarded by a silent 15-second timeout. It eliminates the two-to-four turns agents waste probing the sandbox, and it gains on 7 of 89 tasks (largest: protein-assembly, path-tracing) — all tasks needing domain tooling whose availability cannot be assumed. This is credit assignment over program history, which is exactly what scalar- or summary-fed optimizers cannot do.

The machinery behind steps 1 and 2

How much the proposer can see. Table 1 is the paper's framing device: the authors' best estimate of context available per optimization step in each method's largest reported setting.

Method History Log content MTok/iter
OPRO window past (solution, score) pairs 0.002
GEPA summary reflective feedback from rollout traces 0.008
Feedback Descent summary comparison + textual feedback 0.012
TextGrad last textual feedback on current artifact 0.015
AlphaEvolve window program database + eval scores 0.022
TTT-Discover window previous solution fragment 0.026
Meta-Harness full all logs and scores 10.0

Roughly three orders of magnitude, and a single evaluation can produce up to 10M diagnostic tokens.

How much it actually reads. Instrumentation from the same TerminalBench-2 run records a median of 82 files read per iteration (range 69–99), split 41% prior source code, 40% execution traces, 6% score and summary files, 13% other, referencing more than 20 prior candidates per step. The access pattern is, as the authors put it, non-Markovian: the proposer re-reads the majority of available history rather than conditioning on its most recent parent. That is why the proposer has to be a coding agent rather than a raw model — something must decide what to open and validate its edits against the codebase — and why its outputs, not its diagnosis, are the only thing constrained: a single minimal "skill" file states where to write harnesses and what it may not modify. The paper is upfront that this only became practical with early-2026 coding agents; the loop's simplicity is a bet that the method improves for free as coding agents do.

Whether the bandwidth is load-bearing. The interface ablation (Table 3) holds everything else fixed and varies only what a candidate's directory may contain; the numbers are search-set accuracy.

What the proposer may read Median candidate Best candidate Runs above zero-shot
code + scores 34.6 41.3 26
code + scores + LLM-generated summaries 34.9 38.7 23
code + scores + raw traces 50.0 56.7 39

The median full-interface candidate beats the best candidate under either ablation. More pointedly, summaries do not merely fail to help — they lower both best accuracy and the above-baseline count relative to scores alone, and the authors note they "may even hurt by compressing away diagnostically useful details." Summarizing feedback for the optimizer is not neutral compression; it deletes the causal chain.

The other two discovered harnesses are similarly legible. For classification the search converged on a label-primed query program — a label primer, one coverage example per class, and TF-IDF query-anchored contrastive pairs. For math it produced a four-route lexical router (combinatorics, geometry, number theory, default) over math-aware BM25, autonomously merged from two successful lineages.

What the demonstration does not cover

Three limits are structural rather than incidental, and they bound what the TerminalBench-2 headline can mean.

The search set and the test set are the same 89 tasks. The authors defend this openly as a "discovery problem": public writeups already describe repeated benchmark-specific harness iteration on TerminalBench, and the benchmark is small and expensive enough that carving out a split "would materially weaken the search signal." Fair — but it leaves the number same-distribution, guarded by manual inspection and regex leakage audits rather than by held-out data.

Search starts one edit from the frontier. The population is seeded with Terminus 2 (62.9%) and Terminus-KIRA (74.7%), and the winner is 80 additive lines on someone else's harness. Cheap, safe, composable — and a demonstration of automated refinement at the frontier rather than invention. (The appendix log also measures its Terminus-KIRA baseline at 64.4% while the main table reports 74.7%; the paper does not reconcile the two, which is worth knowing before reading per-iteration deltas as absolute standings.)

Out-of-distribution margins are a fraction of in-search ones. On nine unseen classification datasets the discovered harness beats ACE by +2.9 rather than the in-search +7.7, and ACE still wins 3 of the 9; on retrieval-augmented math the gain over plain BM25 is +1.3. Both are detailed in the results below, and both are the honest size of the claim.

# Meta-Harness outer loop (Algorithm 1, plus Sec. 3 practical details)
Input: tasks X (search set only), frozen LLM M, coding-agent proposer P, iterations N
H <- initial population (strong hand-built baselines, e.g. zero-shot / few-shot / ACE)
D <- empty filesystem                       # one directory per candidate
for H_i in H:  D <- D + {code, scores, traces of Evaluate(H_i, M, X)}
for t = 1..N:                               # typical run: ~60 harnesses over 20 iters
    P queries D with grep/cat/ls            # median 82 files/iter; code + raw traces
    P forms failure hypotheses              #   "which earlier design choice caused this?"
    P writes k new single-file harnesses    # local edit, rewrite, or compose — its choice
    for H_new in proposals:
        if H_new passes interface validation:      # cheap smoke test, catches duds
            D <- D + {code, scores, traces of Evaluate(H_new, M, X)}
return Pareto frontier of D                 # test set evaluated once, at the very end

Results

Compute-matched controls (Table 4, search set). All methods use the same proposer configuration (Opus-4.6 at max reasoning), select candidates solely on search-set performance, and get the same budget of harness evaluations. GEPA 32.6/40.2; Best-of-N 34.0/44.2 — independent samples from the seed with no search structure at all, the control for whether search matters; OpenEvolve 39.1/43.3; TTT-Discover 34.1/45.6; Meta-Harness 50.0/56.7. The uncomfortable detail is that Best-of-N's best candidate (44.2) beats GEPA's and OpenEvolve's and sits within 1.4 of TTT-Discover's: three of the four structured optimizers barely improve on unstructured sampling here. Only Meta-Harness clears the control decisively (+12.5 best, +16.0 median), matching the strongest prior optimizer's final accuracy within its first 4 evaluations — roughly 10x fewer.

Online text classification (GPT-OSS-120B; LawBench 215 classes, Symptom2Disease 22, USPTO-50k 180): best discovered harness 48.6% avg vs ACE 40.9% and MCE 40.0%, on 11.4K context tokens vs ACE's 50.8K and MCE's 28.5K. Because the objective is a Pareto preference rather than a scalar, the search yields a smooth accuracy–context frontier instead of one operating point.

Transfer — and the honest size of it. On nine unseen classification datasets the discovered harness averages 73.1% vs ACE's 70.2%, winning 6 of 9 on 7.3K context tokens vs ACE's 11.7K. That margin is +2.9, not the in-search +7.7, and it isn't uniform: ACE still beats it on FiNER (74.0 vs 67.0), FPB (96.7 vs 94.0), and Bank77 (83.3 vs 82.7); the big win is SciC (53.3 vs 40.7). On retrieval-augmented math, one harness searched with GPT-OSS-20B (109 candidates, 40 iterations, 250-problem search set) is evaluated on 200 IMO-level problems across five models: +4.7 over no retrieval, but only +1.3 over plain BM25, and dense retrieval at \(k{=}5\) reaches 38.1 against Meta-Harness's 38.8. The real advantage is consistency, not peak: dense retrieval and random few-shot each regress on multiple models (random few-shot averages −1.9), while Meta-Harness improves every model over no-retrieval — though it loses to plain BM25 on one of the five (Gemini-3-Flash, 46.3 vs 46.6).

The decontamination work is real. The 535,356-problem corpus comes from eight sources with filtering: NuminaMath-1.5 restricted to competition-math subsets; OpenMathReasoning deduplicated to one solution per problem (highest pass rate on an independent verifier), with any problem whose source matched an evaluation family (IMO, AIME, HMMT, SMT, USAMO, Putnam) removed before dedup; then the whole corpus decontaminated against every evaluation benchmark and the search set by exact prefix matching followed by fuzzy Jaccard at threshold 0.8, discarding either-way matches; then manual inspection of top BM25 retrievals for held-out examples. On TerminalBench-2 the analogous check is manual inspection plus regex audits for task-specific string leakage into evolved harnesses.

TerminalBench-2 (89 tasks): Opus 4.6 76.4% — #2 overall, above every hand-engineered agent the authors could reproduce (ForgeCode's 81.8% wasn't reproducible from public code); Haiku 4.5 37.6% vs Goose's 35.5%, #1 among reported Haiku agents. The only fully-automatic entries in the table.

Figure 7 from the paper: discovered strategies (pink) largely track the diagonal — search-set gains carry to the test set rather than being search-set mirages.

How it connects

  • AutoDesign: Meta-Harness Optimization for Long-Horizon Agentic Design — the same thesis five months later in the design domain: a meta-level optimizer reads rollout feedback and directs a code agent to rewrite the harness. Meta-Harness is the cleaner ablation of why it works; AutoDesign adds cross-model scaffold-transfer evidence.
  • Mendel Gödel Machine — same enemy, opposite philosophy of evidence. MGM curates it per self-edit (two-trajectory controlled comparisons); Meta-Harness un-curates it (everything on disk, agent chooses) — reconcilable, since agent-directed selective reading is compression at read time rather than write time.
  • Rethinking the Evaluation of Harness Evolution — the standing null hypothesis (gains = repeated sampling + eval-set adaptation). Meta-Harness answers better than most: Best-of-N is the compute-matched sampling control (44.2 vs 56.7 best), and the OOD-classification and held-out-model math tables are the transfer evidence that critique demands. The TB2 experiment sits squarely inside the regime it targets.
  • HarnessCompass — manages blind harness evolution with admissibility gates on what edits may contain; Meta-Harness manages it with richer evidence about what to edit, noting code-space overfitting is at least inspectable (brittle if-chains are visible in a way weight overfitting isn't).
  • Living-Harness — the bounded counterpart, which lists Meta-Harness in its own table as the "harness code, no bounded gates" row: gated state updates versus unrestricted code rewrites, this paper betting on evidence richness where Living-Harness bets on commit discipline.
  • Recursive Harness Self-Improvement — one level up: there the improver improves itself; Meta-Harness keeps its outer loop frozen. The authors' next step is co-evolving harness and weights, not the loop.
  • No Universally Best Harness — if harness rankings flip across tasks, per-domain automated search is the natural consequence; Meta-Harness shows an agent can run it in hours rather than a team over a quarter.

Critical take

The honest core result is the interface ablation — traces beat summaries beat scores, by a lot — and it's the result most likely to generalize, because it is the one thing the paper varies while holding everything else fixed. The headline benchmarks need the sorting given above under "What the demonstration does not cover": search-on-eval for TerminalBench-2, near-SOTA seeding, and transfer margins a fraction of the in-search ones. Together those bound the claim to automated harness refinement at the frontier of hand-engineering; invention remains open. Two smaller flags. The thread's "five completely held-out frontier models" is wrong — GPT-OSS-20B was the search model, so four are held out. And everything runs on Claude Code + Opus-4.6, which the authors note; "the loop improves as coding agents improve" is a forecast, not a finding, and nothing here tests a weaker proposer. Costs appear in wall-clock ("a few hours") but never in tokens — and a method whose central claim is "spend more bandwidth" ought to report what the bandwidth costs.

If you remember three things

  1. Feedback bandwidth is the variable that matters: prior text optimizers give the proposer ≤0.03 MTok/iteration; Meta-Harness exposes ~10 MTok via a filesystem, and the ablation is unambiguous — raw traces 50.0/56.7 vs summaries 34.9/38.7 vs scores 34.6/41.3, summaries losing even to scores on above-baseline runs (23 vs 26). Summarizing feedback for the optimizer is where the signal dies.
  2. Minimal loop, maximal access: no parent selection, no mutation operators — propose/evaluate/log, with a coding agent reading a median 82 files per iteration across 20+ prior candidates and doing explicit causal credit assignment over program history, including reverting a confound to test a fix in isolation.
  3. Weigh the transfer numbers, not the headlines: +2.9 OOD over ACE, +1.3 over BM25 on math, TB2 #1-among-Haiku with search-on-eval and near-SOTA seeding — enough to show agent-run harness search works at the frontier of hand-engineering, not that it replaces it.
