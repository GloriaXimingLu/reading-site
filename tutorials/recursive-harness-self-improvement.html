Recursive Harness Self-Improvement (Sakana/Berkeley)

14 min read · arXiv:2607.15524 · arXiv · X post · Self-Improving Agents & Harnesses

TL;DR

  • Recursive Harness Self-Improvement (RHI) (Lee, Xu, Seely, Lee, Zaharia, Tang — Sakana AI & UC Berkeley, arXiv 2607.15524) represents the agent harness as a prompt-level specification of the agent loop — roles, instructions, inter-agent contracts, workflow hops — and refines it using pairwise preferences over its own revision history. No gradients, no scaffold code edits.
  • On 30 synthetic ML-research tasks, one to two iterations lift a high-reasoning agent past the same model at max and ultracode reasoning, at up to 60% lower inference cost. Despite the name, the optimizer is a fixed external model: the recursion runs over revision history, not over the editor.
  • The mechanism, per the authors, is task-specific context management — contracts as a learned sparsity pattern on inter-agent communication — evidenced by flat output-token counts alongside 32–64% drops in KV-cache traffic.

Why this matters

The dominant framing of harnesses has been inference-time scaffolding around a frozen model. This paper adopts the newer model–harness co-evolution view: harnesses are also data-generating components, because their execution traces feed the training corpora of future models. A harness therefore has two objectives — task performance and trace quality. RHI addresses "the first half" of that loop.

The practical gap: provider-built scaffolds are expensive to update continually, and most users cannot modify them anyway. So the question becomes whether user-constructed, task-specific harnesses can be optimized cheaply — lightweight, a few iterations — a far more accessible regime than end-to-end RL, and complementary to it. Within this list, RHI is the "optimize the harness automatically, per task, at inference time" corner of the space the Harness Handbook, the harness-generalization paper, and the long-horizon-agents survey map out.

The core idea

The key insight: if the harness is expressed as text, harness optimization becomes a text-refinement problem. RHI writes the whole agent loop as a prompt-level specification, then improves it by running it, comparing the result against the previous revision's output, and rewriting. The signal is relative — this revision beat that one — which avoids needing calibrated absolute scores of harness quality.

Figure from the paper: at iteration \(i\) the agent solves the task with harness \(H^{(i)}\); an LLM evaluator compares output[i] with output[i-1]; the preference is stored in the self-comparison history; an LLM harness optimizer updates \(H^{(i)} \to H^{(i+1)}\).

What "recursive" means here — and what it does not. Nothing in RHI edits the thing doing the editing. The update rule is \(H^{(i+1)} = \mathcal{L}_{\mathrm{harness}}(H^{(i)}, \mathcal{D}_x^{(i)})\), and \(\mathcal{L}_{\mathrm{harness}}\) is a fixed external model with a fixed system prompt, sitting outside the object it rewrites. The edit set is the harness text alone; optimizer, evaluator, evaluation prompt, agent, and weights are all constant. The recursion runs over the revision history — iteration \(i{+}1\) is a function of iteration \(i\) plus the record of how earlier revisions fared — not over the improver, in the Gödel-machine sense where the self-modifying code includes the code performing the modification. That puts RHI in the GEPA / reflective-text-optimization family, not the Darwin Gödel Machine family. The paper is not misleading (Equation 5 says exactly this, and §6.3 treats the optimizer's own biases as a fixed internal factor of the method), but the title invites the stronger reading. Read "recursive" as iterated with memory.

The second, less obvious part of the idea is what gets optimized: improved task-specific context management — the revisions restructure which information reaches which part of the loop — rather than longer chains of thought.

How it works

The pipeline, per task \(x\):

  1. Harness-as-prompt. Author the agent loop as a specification \(H^{(0)}_x\). The only change to the base agent is that its input becomes \(x \cup H^{(i)}_x\).
  2. Execute. Run the current revision, producing an entire code repository \(y^{(i)}_x\).
  3. Compare against the immediate predecessor. An LLM judge, conditioned on a fixed evaluation prompt \(x_{\mathrm{eval}}\), returns preferred / tie / reverse on \((y^{(i)}, y^{(i-1)})\). One comparison, one predecessor — not the whole history, not a population.
  4. Refine. An LLM harness optimizer rewrites the specification from the accumulated preference history.
  5. Recurse or stop. Continue while revisions keep winning; 1–4 iterations do the work.

The objective. The ideal harness-optimization objective is the expected pairwise win rate against a reference population of competing harnesses:

\[f_x(H)=\mathbb{E}_{H'\sim\mu,\; y\sim\mathcal{A}(H,x),\; y'\sim\mathcal{A}(H',x)}\big[\mathbf{1}\{\mathcal{L}_{\mathrm{eval}}(y,y';x_{\mathrm{eval}})=y\succ y'\}\big],\qquad H_x^{*}\in\arg\max_{H\in\mathcal{H}} f_x(H)\]

where \(\mathcal{A}(H,x)\) is the agent running harness \(H\) on task \(x\), \(y\) the produced repository, \(\mathcal{L}_{\mathrm{eval}}\) an LLM judge, and \(\mu\) a distribution over competitors. RHI replaces \(\mu\) with a point mass on the previous revision — a trajectory-local relaxation:

\[\widetilde f_x^{(i)}(H)=\mathbb{E}_{y\sim\mathcal{A}(H,x),\; y^{-}\sim\mathcal{A}(H_x^{(i-1)},x)}\big[\mathbf{1}\{\mathcal{L}_{\mathrm{eval}}(y,y^{-};x_{\mathrm{eval}})=y\succ y^{-}\}\big]\]

The cost argument, precisely. Per-iteration cost is \(C=N_{\mathrm{trace}}+N_{\mathrm{pair}}\): agent executions plus judge calls, outputs cached so each harness runs once. Table 1: the ideal objective needs \(M\) traces and \(\binom{M}{2}\) comparisons, \(\Theta(M^2)\); finite-population search (AlphaEvolve, ADAS, AFlow, GEPA, Meta-Harness) shrinks the population to \(m\ll M\) but still pays \(\Theta(m^2)\); RHI pays exactly one trace and one comparison, \(\Theta(1)\). This matters because an "evaluation" here is not a scalar but a black-box agent run producing a whole repository — every extra population member is another repository generated and judged.

Why the relaxation is not fatal. Under a Bradley–Terry-style model with latent utility \(u_x\) and link \(\sigma\) (\(\sigma(0)=\tfrac12\)), both \(f_x(H)=\mathbb{E}_{H'\sim\mu}[\sigma(u_x(H)-u_x(H'))]\) and \(\widetilde f_x^{(i)}(H)=\sigma(u_x(H)-u_x(H^{(i-1)}_x))\) are monotone in the same utility, so any revision that truly beats its predecessor with probability \(>\tfrac12\) also raises the ideal objective. The comparison is a noisy local ascent signal, not an unbiased estimator: the relaxation changes the problem from "beat arbitrary harnesses" to "beat your own last version".

The self-comparison history. One comparison per iteration is thin, so the update conditions on all of them:

\[\mathcal{D}_x^{(i)}=\big\{\mathcal{L}_{\mathrm{eval}}(y_x^{(k)},y_x^{(k-1)};x_{\mathrm{eval}})\big\}_{k=1}^{i},\qquad H_x^{(i+1)}=\mathcal{L}_{\mathrm{harness}}\big(H_x^{(i)},\mathcal{D}_x^{(i)}\big)\]

Two consequences. First, earlier history is not discarded — the paper's Q&A appendix answers the obvious worry (a good edit at \(\mathcal{H}[i{-}2]\) reverted by noise in the next transition) by noting \(\mathcal{D}_x^{(i)}\) retains all prior judgments in compressed form and acts as a momentum signal. Their stability evidence: consecutive-harness cosine similarity climbs 0.82 → 0.97 → 0.98 → 0.99, so the first update is the big jump and later ones refine rather than oscillate. Second, \(\mathcal{L}_{\mathrm{harness}}\) never sees \(x_{\mathrm{eval}}\) — the six criteria (deliverable coverage, empirical rigor, reproducibility, presentation, engineering quality, task alignment) reach it only through which revisions won. RHI optimizes an implicit preference, not a stated rubric.

The stopping rule. After each sweep over the \(n\) tasks, RHI computes the improvement rate \(s_i=\frac1n\sum_j \mathbf{1}[y_j^{i}\succ y_j^{i-1}]\) and breaks when \(s_i<\epsilon\). The signal driving the update also halts it: the loop stops once revisions stop reliably winning, exactly the regime where further ascent would be chasing judge noise. (\(\epsilon\) is not given numerically.)

Algorithm (RHI, condensed from Algorithm 1 in the paper):
Input: tasks {x_j}, agent A, evaluator L_eval, harness optimizer L_harness,
       eval prompt x_eval, stopping threshold eps
Initialize harness H(0) per task; history D <- {}; run A(H(0), x) once
for i = 1, 2, ...:
    for each task x_j:
        y(i) <- A(H(i), x_j)                          # run current harness
        D_j  <- D_j U {L_eval(y(i), y(i-1); x_eval)}  # compare vs. predecessor
    s_i <- (1/n) * #{tasks where y(i) beats y(i-1)}   # improvement rate
    if s_i < eps: break                                # revisions stopped winning
    H(i+1) <- L_harness(H(i), D)                       # rewrite spec from history
return task-specific harnesses H*

What a harness actually is here. More specific than "a prompt". Two primary parts:

  • Agent design — for each of \(N\) candidate agents, a role and an instruction.
  • Agent workflow — contracts and hops. A contract is an agent's declared out-to-orchestrator interface: the named fields it must return, i.e. exactly which information crosses that boundary. A hop is one step of orchestrator–subagent control flow: who is invoked when, on what.

Across iterations RHI also induces a task-dependent tier of auxiliary rules — acceptance gates before termination, failure-fallback rules, evidence-motivated recall triggers, agent-to-agent conventions — on top of the design-and-workflow scaffold present every iteration.

The optimizer prompt deliberately prioritizes contracts and hops over agent design, and the stated reason is worth carrying: a task-specific contract is a learned sparsity pattern on inter-agent information flow. A fully shared interaction history is the dense-attention case, where every agent conditions on everything; a contract restricts each edge to what the downstream decision needs. That buys quality and cost at once — hence an efficiency story about KV-cache traffic, not output length.

The component ablation supports the emphasis: embedding each type separately, contracts show the clearest task-dependent clustering, hops and instructions less so, roles barely at all (most ML-research tasks share roles: data prep, training, validation, reporting). Contracts also stabilize fastest — consecutive-iteration cosine 0.48 → 0.66 → 0.69 → 0.72, versus roles at 0.28 → 0.31 → 0.33 → 0.31. The authors flag the confound: contracts are also what the optimizer was told to focus on, and the analysis is correlational.

Results

Figure from the paper: across 30 synthetic ML research tasks, high-reasoning agents with RHI-improved harnesses achieve higher pairwise win counts than test-time-scaling baselines (mean over two LLM judges, three seeds).

Setup. 30 tasks — 10 each in quantitative finance, robotics, pharmaceutical ML — all synthesized by an LLM from three real job postings (Citadel, Amazon frontier-AI robotics, Genentech). Each demands a full repository with standardized deliverables (research_report.md, figures, metrics.json, index.json), which is what makes pairwise judging tractable: the judge sees only those, truncated identically, at 30–40% of its context window. Base agents: Claude Sonnet 4.6, Opus 4.7, Opus 4.8 at high; baselines the same models at xhigh, max, ultracode. Judges: gpt-5.5 at max reasoning and opus-4.7/4.8 at xhigh, three seeds.

Performance. After two iterations sonnet-4.6-high + H[2] beats sonnet-4.6-max on 20 of 30 comparisons, and \(i=3,4\) keep winning. On Opus 4.7 the hand-written \(H[0]\) loses to xhigh and max; one iteration flips both. On Opus 4.8, \(H[2]\) beats all three — including ultracode, not merely more reasoning but the provider's built-in dynamic workflow that spawns its own subagents. A prompt-level user harness beating the provider's system-level multi-agent scaffold is the strongest single claim.

Where the 60% comes from. Resource numbers are normalized per model to that model's own high agent = 1.0, averaged over the 30 tasks. On Opus 4.8: high + H[2] costs 1.69, max 2.19, ultracode 4.15. The headline is \(1 - 1.69/4.15 \approx 60\%\) — the final RHI run against the most expensive baseline on the strongest model. Against max it is 23%; Opus 4.7 high + H[1] (2.11) is 18% below max (2.60); Sonnet 4.6 high + H[2] (2.38) is 7% below max (2.56). "Up to 60%" is one cell of a table whose typical value is 7–23%.

Cache traffic moves the same way and is the mechanism evidence: −33% for Sonnet (4.91 → 3.31), −37% for Opus 4.7 (3.37 → 2.11), −32% vs max and −64% vs ultracode for Opus 4.8 (4.74 → 1.69). Output tokens stay flat while performance climbs — 1.71–1.86 across Sonnet's five iterations, 1.42–1.81 across Opus 4.8's three — the decoupling that rules out "it just thinks longer". (Opus 4.7 is the honest exception: there tokens rose with performance, and the authors say the two explanations cannot be separated.)

Mechanism, as a hypothesis. §6.3 proposes that the trajectory is consistent with increasing

\[J(g_i)=\underbrace{\sum_{\texttt{hc}\in\mathcal{C}_{\mathrm{ext}}}\tfrac{1}{K^{\texttt{hc}}_{Xi}}\sum_{k}I\big(z^{\texttt{hc},(i)}_{Xk};X\big)}_{f_{\mathrm{ext}}}\;-\;\beta\underbrace{\mathrm{TC}\big(\{z^{\texttt{hc},(i)}_{Xk}\}\mid X\big)}_{f_{\mathrm{int}}},\qquad \beta>0\]

where \(z^{\texttt{hc},(i)}_{Xk}\) is the embedding of the \(k\)-th component of type hc, \(X\) the random task, \(\mathcal{C}_{\mathrm{ext}}=\{\texttt{contract},\texttt{hop}\}\) the types the optimizer prompt emphasizes, and \(\mathrm{TC}\) total correlation. In words: make workflow components maximally informative about the task while keeping them non-redundant with each other given the task. \(f_{\mathrm{ext}}\) is set by the optimizer prompt; \(f_{\mathrm{int}}\) is a property of the optimizer's base model and blocks the degenerate solution where every component restates the task.

Limits the authors find. RHI does not substitute for a better model: sonnet-4.6-high + H[i], \(i\le4\), fails to close the gap to opus-4.7-high/xhigh, and gains plateau at 2–4 iterations. A useful negative result from the appendix: simply telling the agent "Create an agent team" scores lower Elo than the plain single agent at higher cost, on both models. Multi-agent execution is not free value; the specification is what makes it pay.

How it connects

  • Rethinking Harness Evolution: RHI cites it directly (§2.2) as the reason the method must be cheap — once search cost is counted, automatic harness evolution fails to beat simple test-time scaling. RHI concedes that and changes the cost structure to \(\Theta(1)\); whether it escapes the critique is separate, since the held-out generalization test is not run here.
  • Meta-Harness: the explicit foil. RHI's §3.1 argues Meta-Harness instantiates the finite-population approximation — an archive of harnesses with source, scores, and traces on a filesystem, proposer free to inspect anything — whereas RHI's comparator is only \(H^{(i-1)}\). They now bracket the design space: maximal feedback bandwidth over a population versus one comparison per step with a compressed history.
  • Training Agents Inside Their Harnesses (OpenForgeRL): the literal other half of the co-evolution loop — it trains the model inside a fixed harness; RHI improves the harness around a fixed model.
  • Harness Handbook: the same "harnesses must evolve" problem from the code side. RHI sidesteps it by staying in prompt-space — which is exactly why it applies to user harnesses and not Claude Code-scale codebases. No Universally Best Harness supplies the premise: if harness choice is a model–problem-specific hyperparameter, per-task adaptation is forced.
  • Long-Horizon Agents survey places RHI in the "self-evolution" cell; also related: AREX, evolving-benchmarks, agentic-context-management.
  • Prior work: ADAS searched agentic designs in code with a meta-agent; the Darwin Gödel Machine had agents rewrite scaffold code under empirical validation; DSPy and GEPA optimize prompts programmatically. RHI's bets: prompt-level representation of the whole loop, feedback over revision history, trace-quality framing.

Critical take

  • It is not recursive in the improver. \(\mathcal{L}_{\mathrm{harness}}\) is a fixed external model outside the edit set, and the loop's memory is a list of preferences, not a modified optimizer. Nothing here bears on RSI in the Gödel-machine sense; the right comparison class is GEPA and DSPy, not DGM-style self-editing.
  • All 30 tasks are synthetic, LLM-generated from job postings, with a standardized deliverable schema imposed so the judge has a common interface. That schema does real work — it is precisely the structure a contract-optimizing loop can specialize against. On real repos with ambiguous goals and no fixed deliverable list, both method and protocol need rebuilding.
  • Pairwise self-judging admits Goodharting the judge. The only signal is one LLM's preference between two repositories, and the optimizer reaches the criteria only through it. Nothing distinguishes "the repository got better" from "the repository got more legible to gpt-5.5 and opus-4.x judges" — and the judge families overlap heavily with the agent's own. Two evaluator configurations and three seeds control judge variance, not bias. The missing experiment is a held-out evaluator, or a deliverable that can be executed.
  • No held-out split, and the search is not costed. Harnesses are optimized per task and reported on the same task, so the numbers cannot separate better harness design from adaptation to the instance — the decomposition the Rethinking paper demands. And the 60% is the final run only: producing \(H^{(2)}\) took two extra agent executions and two judged comparisons per task, so the true total is roughly 3× the reported per-run figure. RHI pays off when a harness is reused.
  • Trace quality is asserted, not closed-loop tested, and the mechanism story is correlational: no experiment shows a model trained on RHI traces improving, and the information-theoretic objective is a hypothesis that is never optimized, crediting exactly the components the optimizer prompt named.

If you remember three things

  • RHI = the agent loop written as a prompt, rewritten from pairwise comparisons against its own revision history at \(\Theta(1)\) per iteration instead of population search's \(\Theta(m^2)\).
  • The optimizer is a fixed external model — the recursion is over revision history, not over the editor — and what it mostly rewrites is the contract: which fields cross each inter-agent boundary. That is where the quality and the 32–64% cache savings come from.
  • One to two iterations let a high-reasoning configuration beat the same model at max and ultracode at up to 60% lower final-run cost — on 30 synthetic tasks, scored by LLM judges, with no held-out split and search cost excluded.
