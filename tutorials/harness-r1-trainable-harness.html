Harness-R1: Training the Harness Engineer, Not the Agent

23 min read · arXiv:2608.02276 · arXiv · X post · Self-Improving Agents & Harnesses

TL;DR

  • "Harness-R1: Learning to Edit Executable Runtime Harnesses from Agent Failure Trajectories" (arXiv 2608.02276; Shuai Shao, Kangning Zhang, Qingyao Li, Shijian Wang, Hao Wang, Wenxiang Jiao, Yuan Lu, Yi Guo, Weiwen Liu, Weinan Zhang — SJTU / Xiaohongshu / Southeast University; code and weights released) is, per the authors, the first method that makes failure-conditioned, lifecycle-wide editing of an existing executable runtime a learned capability: a dedicated 9B "harness engineer" reads batches of a frozen agent's failures and writes validated executable patches into four typed hooks in the runtime around it.
  • Two stages: cold-start SFT on 877 teacher-proposed, validation-filtered edits, then online GRPO on ~1,500 failure packets whose only reward is the realized success change from rerunning the frozen target on the same task batch. No KL penalty, no entropy bonus, no format reward — a patch is worth exactly what it does, and an invalid or inert one is worth zero.
  • The trained engineer lifts a frozen Qwen3.5-9B from 44.3% to 53.6% average success across WebShop, ALFWorld, and DBBench (+9.3), beating every prompted frontier editor (best: GLM-5.2, 48.8%); the editing policy transfers to 20 unseen targets (+7.06, no retuning), turns 10 observed failures into a patch worth +8.9 ± 1.5 on 1,270 unseen tasks where frontier editors go negative, and still adds +5.0 after the target is fine-tuned.

Why this matters

This tracker has been circling one question all year: when an agent system improves, should the gradient flow into the model or into the harness? Microsoft's "Training Agents Inside Their Harnesses" put RL on the model with the scaffold fixed; the Sakana/Berkeley recursive-harness work and the Harness Handbook improve the harness but with frozen prompted models; the "Model or Harness" taxonomy argues most production agent bugs live on the seams between model and scaffolding, so the repair often belongs to the harness side.

Harness-R1 is the missing quadrant: weight-updating RL applied to a separate engineer model whose actions are harness edits, while the deployed agent stays frozen. Its related-work section names the gap — across Meta-Harness, AutoHarness, Agentic Harness Engineering, and HarnessX, "the harness proposer usually remains fixed: outcomes select or iteratively refine patches without directly updating proposer parameters," and HarnessX's GRPO trains the task model, not the editor.

That is an attractive operating point for anyone who can't retrain the production model — API models, compliance-frozen checkpoints, multi-tenant targets — but accumulates failure trajectories for free. The headline negative result matters as much: prompting GPT-5.5-class models to do the same job is unreliable because, in the authors' framing, they "optimize for plausibility" — reasonable-looking edits from a model that never reruns the target and so cannot tell whether an edit raises success. Appendix H makes it vivid: Gemini-3.5-Flash, given the full lifecycle interface and full failure evidence on ALFWorld, lowers success from 208/500 to 177/500 (−6.2 points), 21 of its 39 valid patches reducing batch success. Outcome grounding, not scale, is what makes an editor safe to point at a running system.

The core idea

A frozen target agent — a model plus the runtime around it — runs a batch of tasks and fails some of them. A deterministic extractor, not a model, keeps only the failed episodes and compacts them into a failure packet: task constraints, action–observation excerpts, outcomes, and the environment state a fix would need. A second model, the harness engineer, reads that packet once and writes an executable overlay — Python installed at four fixed points in the runtime's lifecycle (episode initialization, pre-decision context injection, pre-action mediation, post-feedback recovery), around the frozen policy rather than inside it. The engineer never answers a task, never calls an environment tool, never joins a rollout. Its entire job is to change what the frozen agent sees and what the environment will accept from it.

The patch is then installed and the same frozen target reruns every task in the batch, including the ones it already passed. The change in average batch performance is the engineer's reward, and it is the only reward: no format bonus, no plausibility judge, no KL penalty, no entropy term. A patch that doesn't parse, doesn't install, or does nothing scores exactly zero; a valid patch that makes things worse scores negative. The failure mode is priced, not filtered.

The paper is direct about what this objective is: "Using the same tasks before and after editing controls task composition but defines a same-batch, transductive objective, with no iterative refinement within an instance or persistent patch memory across batches." Transductive means the patch is graded on the exact tasks whose failures it was written from. That licenses a strong claim — the reward is a realized causal effect on the frozen target, not a proxy score, measured against a matched baseline so task difficulty cannot confound it. It does not license the claim that a high-reward patch generalizes; that must be earned separately, which is what §4.4 exists for.

Two stages get the engineer there. A cold-start SFT pass on 877 teacher-proposed, validation-filtered edits gives it a prior over what a valid edit even looks like; online GRPO on ~1,500 failure packets then optimizes realized utility, with the success change as the only signal. Only the engineer's weights ever move; the target's never do.

How it works

Figure 2 from the paper: the failure-to-edit-to-rerun loop. The trainable engineer (left) and the frozen task agent (right) are strictly separated; the patch touches episode-init, pre-decision, pre-action, and post-feedback hooks only.

The loop in one sentence. One training step is: let the frozen agent fail a batch of tasks, compress those failures into a fixed-format packet, have the engineer write eight candidate patches from it, actually install each one and rerun the whole batch to see what changed, then push the engineer's weights toward the candidates that helped.

One training step, start to finish

The instance below is the paper's WebShop case study — one batch of ten tasks, one patch — placed inside the training loop that produced the policy writing it. (The case study is reported as a worked example of a patch, not as a training step; the two have the identical shape, which is itself the paper's design and the source of the caveat at the end of this section.)

Step 1 — Run the frozen agent and bank the baseline. Ten WebShop tasks, the unmodified agent, the unmodified runtime. Two of the ten succeed; mean shaped reward is 0.682. Every trajectory and reward is cached and never recomputed. This is the matched baseline that every candidate patch will be scored against, and it is what stops task difficulty from confounding the reward — the two arms differ only by the patch.

Step 2 — Compact the failures mechanically, not with a model. The eight failed episodes go through a hand-written extractor that discards prose and keeps typed fields: normalized action records, state counters, the task's own constraints, the relevant world state — plus precomputed yes/no flags for conditions like a required product option was never selected or the same link was clicked twice. The output is a single packet, capped so it always fits the engineer's context. Nothing at this step is summarized by a model, which turns out to matter.

Step 3 — Ask the engineer for eight patches, not one. The engineer reads the packet once and samples eight candidates at temperature 0.7. Each candidate is a small program in JSON: which benchmark it targets, a description, and one or more blocks of Python to be installed at named points in the runtime. It is forbidden to write the answers in — no product IDs, no list indices, no ground-truth SQL — which is what keeps the artifact a harness and not a lookup table.

Step 4 — Throw away the ones that don't run. Every candidate is parsed and validated before anything is installed. Wrong shape, an installation point that doesn't exist, an action the environment would not accept, an attempt to encode an answer: the candidate scores exactly zero. Zero, not a penalty, and not a retry — invalid patches are never repaired, so writing runnable code is part of what the engineer has to learn rather than something the framework fixes for it.

Step 5 — Install each survivor and rerun the whole batch. All ten tasks, including the two that already passed. The winning candidate here is a guard sitting between the agent and the environment: when the agent proposes buying the item while a required option is still unselected, the guard suppresses that action and sends the agent back to choose one. Rerunning the batch takes success from 2/10 to 5/10 and mean shaped reward from 0.682 to 0.768. The candidate's score is that difference averaged over all ten tasks — so any regression on the two that were already passing comes straight out of it.

Step 6 — Score the eight against each other, then update. The eight scores are compared within their own group: subtract their mean, divide by their spread. What matters is which candidates beat their siblings, not the absolute size of any one delta, so a packet where every patch helps a little and a packet where one patch helps enormously produce learning signals of comparable size. That normalized score is then applied to every token of the candidate's text and the engineer's weights move toward the candidates that earned it. The patch itself is discarded — nothing is cached, nothing carries into the next batch.

The machinery behind steps 2–6

Step 2, what fills 28,672 tokens. The extractor turns the failed baseline trajectories \(\tau_i^0\) into a single packet \(s_B\) for batch \(B\). The size of that packet is where this design is the mirror image of Meta-Harness. Meta-Harness bets on bandwidth: unrestricted filesystem access to ~10 MTok of raw traces per iteration, navigated with grep and cat, and its ablation says this is the ingredient (50.0 vs 34.6 median with scores only; LLM-written summaries recover nothing, 34.9). Harness-R1 does the opposite: the engineer prompt is capped at 28,672 tokens, about 0.029 MTok — roughly 350× less, barely above the 0.002–0.026 MTok band Meta-Harness dismisses as the old text-optimizer regime. What fills it is not a summary but a typed extraction — normalized action fields, state counters, task constraints, world/database state, and the interesting part, precomputed predicates: required_options_unselected, product_price_over_budget, stalled product page and repeated click/search on WebShop; premature/empty commit, unknown column, repeated SQL, remaining-rounds-low on DBBench; repeated observation/action, invalid-action signals, inventory and the admissible set on ALFWorld. The two findings are not in conflict: Meta-Harness showed that LLM compaction destroys the signal, and Harness-R1's answer is that deterministic, typed compaction does not — outcome-grounded training then teaches the editor which fields are load-bearing instead of making it rediscover them by grepping.

Step 3, the four hooks are the real interface, each specified in Appendix C by invocation point and permitted return effect. A patch is a JSON object with keys benchmark, description, actions, where each action is an add_code_hook carrying Python source defining hook(ctx, nb) — no imports, no global state:

Hook Fires Admissible effect
on_init before the first target decision reusable task guidance or a tool hint (skills/tool_hint), or nothing
make_pre_hint before any target decision a state-conditioned message injected into context — cannot execute an action
on_before_action after the target proposes an action, before the environment sees it block_and_prompt (suppress and re-ask), or where supported rewrite_action / force_action
on_post_step after environment feedback inject_hint, or where supported force_action to schedule a next step

The asymmetry is deliberate: the first two hooks can only speak to the frozen policy, the second two can overrule it. The walkthrough's buy-now guard is an on_before_action returning block_and_prompt. Per-benchmark rules narrow the space further — ALFWorld and DBBench patches use two to four hooks, each at most once; a mediated ALFWorld action must come from the environment's admissible set; DBBench v1 accepts guidance and blocking but no SQL rewrites or forced commits.

Step 5, what the reward is exactly. For a batch \(B=\{x_i\}_{i=1}^{n}\) of tasks and a candidate patch \(P\):

\[\Delta_{B}(P)=\frac{1}{n}\sum_{i=1}^{n}\left(R_{i}^{P}-R_{i}^{0}\right),\qquad r(B,P)=\begin{cases}\Delta_{B}(P), & \text{if valid and complete},\\ 0, & \text{otherwise},\end{cases}\]

Symbol by symbol: \(n\) is the batch size (ten in the walkthrough) and \(i\) indexes its tasks. \(R_i^0\) is task \(i\)'s reward under the unmodified runtime — the cached baseline from Step 1. \(R_i^P\) is the same task's reward after \(P\) is installed, produced by the same frozen agent \(A\), which never appears as a variable because it never changes. \(\Delta_B(P)\) is their average difference across the whole batch, previously-passing tasks included, so a regression subtracts. \(r(B,P)\) is the reward actually handed to the learner: \(\Delta_B(P)\) when the patch parsed, installed, and did something, and 0 otherwise. WebShop contributes its native shaped reward; ALFWorld and DBBench binary success. (The cases form is transcribed from Eq. 1.)

The prior behind step 3. Before any of the above runs, cold-start SFT teaches the engineer what a valid patch looks like. A GPT-5.5 teacher proposes patch texts for the same kind of failure packet; each is validated on the frozen target, and at most one executable, complete, non-regressive response per packet is kept — 877 pairs. The engineer is trained on them by next-token prediction:

\[\mathcal{L}_{\mathrm{SFT}}(\theta)=-\frac{1}{\sum_{j}|y_{j}^{T}|}\sum_{j=1}^{M}\sum_{t=1}^{|y_{j}^{T}|}\log H_{\theta}\!\left(y_{j,t}^{T}\mid s_{j},y_{j,<t}^{T}\right).\]

Here \(H_\theta\) is the engineer model with parameters \(\theta\) — the only thing in the system that is ever updated; \(j\) indexes the \(M\) surviving teacher examples; \(s_j\) is the failure packet for example \(j\); \(y_j^T\) is the teacher's patch text for it, \(y_{j,t}^T\) its \(t\)-th token, \(y_{j,<t}^T\) everything before that token, and \(|y_j^T|\) its length. The leading fraction divides by the total token count across the dataset, making this a per-token rather than a per-example average.

Step 6, the update. The \(K=8\) candidates from one packet form a group, and each candidate's reward is standardized inside it:

\[\widehat{A}_{k}=\frac{r_{k}-\mu_{B}}{\sigma_{B}}\]

where \(k\) indexes the eight candidates for one packet, \(r_k\) is that candidate's \(r(B,P_k)\) from above, and \(\mu_B,\sigma_B\) are the mean and standard deviation of those same eight rewards. \(\widehat{A}_k\) is the candidate's advantage: how far it beat its siblings, in units of the group's own spread. There is no learned value function and no separate baseline model — the siblings are the baseline, which is what "group-relative" means and why the absolute scale of the deltas does not matter. That single number is shared by every token of candidate \(k\)'s response and dropped into a token-averaged clipped surrogate:

\[\mathcal{J}(\theta)=\mathbb{E}\!\left[\frac{1}{K}\sum_{k=1}^{K}\frac{1}{T_{k}}\sum_{t=1}^{T_{k}}w_{k,t}\,\min\!\Big\{\rho_{k,t}\widehat{A}_{k},\ \operatorname{clip}(\rho_{k,t},1-\epsilon_{\ell},1+\epsilon_{h})\widehat{A}_{k}\Big\}\right]\]

with \(T_k\) the number of tokens in candidate \(k\); \(\rho_{k,t}\) the importance ratio for token \(t\) — the probability the current policy gives that token divided by the probability the policy that generated it gave, so \(\rho=1\) means nothing has drifted; \(\operatorname{clip}(\rho,1-\epsilon_\ell,1+\epsilon_h)\) bounding how far one update may push a single token, with the deliberately asymmetric \(\epsilon_\ell=0.20\) and \(\epsilon_h=0.28\) (DAPO-style clip-higher) leaving more headroom to raise the probability of a rare high-advantage patch than to suppress anything; the \(\min\) of clipped and unclipped taking whichever is more pessimistic; and \(w_{k,t}=\operatorname{clip}(\exp(\ell^{\mathrm{tr}}_{k,t}-\ell^{\mathrm{ro}}_{k,t}),0,2)\) a truncated importance weight, where \(\ell^{\mathrm{tr}}\) and \(\ell^{\mathrm{ro}}\) are the log-probabilities the training engine and the rollout engine assign the same token — a correction for the two engines not agreeing numerically, capped at 2 so it can never blow up one token's gradient. \(\mathbb{E}\) averages over sampled packets.

Reported RL hyperparameters: lr \(10^{-6}\) constant, Adam \(\beta=(0.9,0.98)\), weight decay 0.1, global batch 32 sequences, four rollout iterations per update, policy staleness ≤8, truncated IS weights ≤2.0, entropy and explicit-KL coefficients both 0 — all on one node of 8×H800. Splits are made before any trajectory collection: 17,843 training tasks (SFT and RL partitions disjoint), 299 validation tasks for checkpoint selection only, 1,300 test tasks.

What the reward does not measure

The reward is transductive by construction: a patch is graded by rerunning the very batch whose failures it was written from. At training time the paper says so outright, and it is a defensible design — the signal is a realized causal effect rather than a proxy. The complication is that Appendix H indicates the main results work the same way: the stored evaluations behind Table 1 use ten-task batches in which "the patched run uses the same ten tasks as its baseline evidence." So the headline +9.3 is a per-batch repair number — patch mined from these ten failures, scored on these ten tasks — held out in task identity but not in evidence, and the 500-task test sets are never a single 500-task generalization test. (Inferred from Appendix H; the main text never states the evaluation batch size — verify against the released code.) That is a legitimate deployment setting ("fix my agent on the traffic I just saw"), and §4.4's held-out experiment is the honest answer to the harder question, but the framing invites conflating the two.

Two things the reward cannot see at all. First, the ALFWorld test set is not the canonical one: 391 of the 500 tasks are a stratified sample from train_valid rather than the official new_std split, only 109 come from the canonical unseen set, and the engineer's training tasks are drawn from the same pool. Second, every editor is matched on protocol — same target, same evidence, same interface, one patch, one episode per task, which is the right comparison among editors and why the frontier-editor result convinces — but nothing is matched on target-inference budget against the obvious non-editor alternative: spend the extra rollouts on the target instead. There is no best-of-\(k\) arm, and the paper's own table holds the uncomfortable datapoint: Reflection's two-episode success@2 reaches 55.8%, above Harness-R1's single-episode 53.6%. The authors correctly note the protocols aren't comparable, which is exactly why the matched-cost version — Harness-R1 at success@2, or repeated sampling at equal spend — is the comparison a skeptic wants and the one not reported.

The loop end to end, from offline caching to weight update:

# Offline: cache base runs
for each task batch B:
    run frozen target A with base harness  ->  trajectories tau^0, rewards R^0
    extractor(failures)                     ->  failure packet s_B  (<= 28,672 tok)

# Stage 1: cold-start SFT
GPT-5.5 teacher proposes edits y^T for packets; validate on frozen A
keep <=1 executable, complete, non-regressive edit per packet
SFT engineer H_theta on 877 (s, y^T) pairs   # 2 epochs, lr 1e-5, ctx 32k

# Stage 2: online, outcome-grounded GRPO
repeat until budget exhausted:
    sample update bundle U from cached records (B, s_B, R^0)   # 4 prompts/rollout
    for each (B, s_B, R^0) in U:
        sample K=8 patch candidates P_1..P_K ~ H_theta(. | s_B)   # T=0.7, top-p 0.95
        for each P_k: parse + validate
            if valid: install P_k, rerun A on ALL of B  ->  R^{P_k}
                      r_k = mean_i(R_i^{P_k} - R_i^0)
            else:     r_k = 0                       # invalid / no-op / incomplete
        A_hat_k = (r_k - mean_k r) / std_k r          # group-relative
    update theta on clipped surrogate (eps 0.20/0.28, trunc-IS <=2.0, no KL, no entropy)

Results

Figure 1 from the paper: matched-baseline reward changes across the three benchmarks; diamonds mark the equal-weight average. Prompted frontier editors are unstable; the outcome-trained engineer is consistently positive.

  • Main result (Qwen3.5-9B target; 500/500/300 test tasks). Average success 44.3% → 53.6% (+9.3): WebShop 31.2 → 42.2 (shaped score 66.0 → 69.9), ALFWorld 40.6 → 53.2, DBBench 61.0 → 65.3. The outcome-trained engineer beats the supervised-only engineer (46.4%) by 7.1 points — the RL stage, not the SFT prior, carries most of the value.
  • ALFWorld by task family is the revealing row: Clean 16.9 → 58.4, Cool 9.2 → 34.5, Heat 28.8 → 43.8, Look 66.7 → 81.0, Pick 75.8 → 77.8 — but Pick2 47.5 → 39.3. Gains concentrate where a transformation step is being skipped; the sole regression is the two-object family, which Appendix H independently identifies as where stage tracking breaks.
  • Versus alternatives: GLM-5.2 48.8%, GPT-5.5 47.9, DeepSeek-V4-Pro 45.9, Qwen3.5-397B 45.8, Kimi-K2.6 45.3, Gemini-3.5-Flash 44.3 — exactly the unpatched baseline. Fixed prompt strategies are not reliably positive: ReAct +3.2, Self-Refine −2.5. Reflection's 55.8% is cumulative two-episode success@2; every other row is success@1.
  • Co-evolution: after direct SFT of the target on 2,515 successful deduplicated trajectories (59.2% avg), a target-specific engineer adds +5.0 to 64.2%, ALFWorld 71.2 → 84.0.
  • Cross-target transfer: 20 unseen targets, each supplying its own failures and receiving a fresh patch, benchmark-averaged +7.06, every target-level average positive; aggregated, WebShop 28.3 → 32.4, ALFWorld 29.4 → 39.1, DBBench 43.6 → 50.9. Across the 21×3 matrix, 56 of 63 cells improve, 4 are unchanged (all WebShop), and the three regressions are ≤2.0 points. Gains are largest on weak-to-mid targets (Qwen3-4B +12.3, Gemma-3-4B +12.0, Llama-3.1-8B +10.5), smallest on the strongest (Qwen3.5-27B +3.6) and tiniest (Gemma-3-1B +1.2).
  • Held-out tasks — the load-bearing generalization test. Each engineer sees the same 10 failures per benchmark per seed, writes one patch, applies it to all remaining tasks: 1,270 pooled tasks, three matched seeds. Harness-R1 installs a real intervention in 9/9 seed-benchmark cells and gains +8.9 ± 1.5 (+9.2 ± 1.5 on the full 1,300 split), positive on every seed. Qwen3.5-397B: 8/9 valid, −4.3 ± 2.5. DeepSeek-V4-Pro: 6/9 valid, −0.4 ± 3.6. The frontier editors don't merely average worse; they straddle zero.
  • Lifecycle ablation (patches and target fixed, one position disabled at a time): full patch 53.1% avg, 8.9 above the 44.2% no-intervention control. Removing pre-action costs 3.9 (WebShop collapses 41.6 → 31.5, back to baseline), post-feedback 3.3 (ALFWorld 52.1 → 41.9), episode-init and pre-decision only 0.9 and 0.6 — conditional effects, the authors caution, not a universal ranking.
  • Case studies show the mechanism executing: WebShop 2/10 → 5/10 (mean reward 0.682 → 0.768) from one guard blocking Buy Now while a required option is unselected; ALFWorld 1/10 → 6/10 from a four-hook closed loop firing 56 times across the batch, rescuing six failures and regressing one; DBBench 4/10 → 6/10 by recovering schema and preserving the stored convention (4 Hours, not 4 hours) where a valid GLM-5.2 patch reached only 5/10.

How it connects

  • The only trained editor in this corpus. Darwin Gödel Machine rewrites its own agent code and archives every functioning variant; Meta-Harness searches harness source with a frozen coding agent given ~10 MTok of raw traces. Both improve the artifact by selection while the proposer's weights never move. Harness-R1 moves the learning target one level down: the artifact is discarded after each batch, and what improves is the editing policy. Its frontier-editor baselines are the prompted-proposer approach run head-to-head under a matched protocol — and they lose.
  • The only system with no memory across edits. Living-Harness commits gated updates into episodic memory and a state graph; DarwinX keeps an archive of lineages under a preserve-and-extend contract; SkillHone persists the decision history behind each skill change. Harness-R1 keeps none of it, by design, so the engineer's weights are the sole carrier of everything learned. That is what makes it a clean RL problem and what makes it wasteful at deployment; a memory layer over a trained editor is the obvious unbuilt hybrid.
  • Rethinking Harness Evolution is the standing budget-matching skeptic, and Harness-R1 answers half of it. The critique's kill shot — evolved harnesses gain +0.6 held-out, "memorizing fixes rather than distilling strategies" — is exactly what §4.4 rebuts at +8.9 ± 1.5 over 1,270 unseen tasks. What it skips is the repeated-sampling control: no best-of-\(k\) arm, and the table's one two-episode number (Reflection, 55.8%) sits above the single-episode 53.6%.
  • EvoHarness-RL is the other weights-touching system here, and the instructive contrast: it trains the target to use its harness (meta-actions sharing the interaction budget, cost-aware GRPO), whereas Harness-R1 trains a bystander to rewrite the harness while the target stays untouched — same algorithm family, opposite side of the interface. Training Agents Inside Their Harnesses is the model-side dual; the three bracket the co-evolution space that Towards Long-Horizon Agents maps as \(\text{Agent} = \pi_\theta \oplus H\).
  • Recursive Harness Self-Improvement and the Harness Handbook sit on the "what can the editor see and change" axis; Harness-R1's four typed hooks are its narrow extreme — no behavior-localization problem at all, because the edit sites are fixed in advance. Model or Harness: Attributing 41 Agent Failure Modes to Component-Interaction Edges supplies the diagnostic vocabulary and the ablation agrees: the value is at the action and feedback seams. RLSVR and ISO are the backdrop — rerun deltas manufacture a verifiable signal where none exists natively.

Critical take

The two structural caveats flagged in What the reward does not measure are the load-bearing ones — a transductive reward that reaches into the headline table, and no control that spends the same extra compute on the target instead of on an editor. Three more sit on top of them.

Three small resettable academic worlds. WebShop, ALFWorld, and DBBench have short episodes, cheap resets, a 4,096-token target cap, and thinking disabled — exactly the regime where up to eight full-batch reruns per GRPO group is affordable. On an SWE-agent-scale harness, where lifecycle edits would matter most, the loop costs orders of magnitude more per candidate and there is no reset button.

Contamination is never addressed: all three benchmarks predate every model tested, and no decontamination control is reported. It is partly defused by the absolute numbers (Llama-3.2-1B scores 0.0% on WebShop) and by the matched-baseline design, which cancels anything helping both arms equally. Less defused is the ALFWorld split problem above — the engineer's training tasks and 391 of its 500 "test" tasks are drawn from the same pool.

The no-memory design is elegant and wasteful in equal measure. Because nothing persists across batches, the system re-derives the same fix every time it meets the same failure mode — the WebShop buy-now guard presumably rewritten from scratch for every batch containing a premature purchase. The engineer's weights are the only carrier, which keeps the RL clean, but the deployment-time artifact is thrown away ~50 times over a 500-task test set. A SkillHone-style history layer, or just caching validated patches keyed by predicate signature, looks like free performance. None of this undercuts the central finding, but the scaling story to production harnesses is still unwritten.

If you remember three things

  1. The harness is now a trainable component: a separate 9B engineer, post-trained with GRPO against same-batch rerun deltas, writes Python into four typed hooks (on_init, make_pre_hint, on_before_action, on_post_step) around a frozen agent — +9.3 average over three benchmarks, beating its own SFT prior by 7.1.
  2. Outcome beats plausibility, and beats bandwidth: prompted frontier editors write valid-looking patches that often don't help (GLM-5.2 48.8% at best) or actively hurt (Gemini-3.5-Flash −6.2 on ALFWorld; −4.3 held-out for Qwen3.5-397B). A 9B engineer reading a ≤28.7K-token typed failure packet — ~350× less than Meta-Harness's raw traces — wins because its reward is realized task success.
  3. The gains sit at the action and feedback seams, and nothing is remembered: pre-action mediation and post-feedback recovery carry 7.2 of the 8.9 ablation points against 1.5 for the two context-only hooks; and because no patch survives its batch, everything learned lives in the engineer's weights.
