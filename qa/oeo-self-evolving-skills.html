Q&A: Rethinking Self-Evolving Agents (OEO)

Session 2026-08-20

Q: Does OEO do harness optimization (editing the agent's entire code) or just skill optimization (the skill file only)?

A: Skill optimization only — the harness is completely frozen. The mutable artifact is a persistent natural-language skill: a Markdown text document injected into the target model's context. The optimizer's action space over the artifact is limited to Revise(s′) (commit a new version of the skill text), Select(j) (choose a checkpoint), Inspect, RunTarget, and Stop; the contract fixes the objective, target model, permitted operations, budget, frozen evaluator, and sealed eval split, and does not permit modifications to the agent's control loop, tools, or memory system. The paper doesn't position itself against harness-optimization work at all.

The naming is a bit of a trap: OEO's "open-endedness" refers to the optimization process — the frontier optimizer composes its own improvement procedure instead of following a prescribed analyze→edit→validate pipeline — not to the scope of what can be edited.

Placement in the harness-optimization walkthrough taxonomy: OEO belongs to the skills line of Thread A (alongside MSCE, Skill Self-Play, and Evo-Harness's skill compilation), not with RHI / DarwinX / Living-Harness, which mutate harness content or structure. Open transfer question: OEO shows frontier optimizers do better without prescribed pipelines at a median 34.3% of the reference interaction budget — whether that survives when the mutable object is the harness itself (where DarwinX and RHI still impose prescribed evolutionary/pairwise pipelines) is untested.

Session 2026-08-23

Q: What exactly are the baselines OEO keeps comparing against — GEPA and SkillOpt?

A: They are the two prescribed optimization pipelines OEO is arguing against, chosen deliberately because they prescribe the procedure in opposite ways — so beating both means the result isn't an artifact of one pipeline's design.

SkillOpt (Yang et al., arXiv 2605.23904, Microsoft — "Training Skills Like Weights") is pipeline-centric prescription. It fixes rollout and reflection batches, separates success-diagnosis from failure-diagnosis, restricts revisions to a set of bounded patch operators, commits only candidates that improve validation (a strict improvement gate, with a memory of rejected edits), and runs for fixed stages and epochs. The framework decides evidence routing, edit form, acceptance, and update cadence; the model only fills in slots. Think of it as SGD-for-skill-files: fixed schedule, gated updates.

GEPA (reference [9] in the paper) is search-centric prescription. It allows free-form, trace-conditioned textual mutation — the model writes whatever revision it wants — but each revision lives inside a framework-defined Pareto-aware evolutionary loop: the framework picks parents and minibatches, updates a candidate pool by Pareto dominance, and runs a budgeted evolutionary schedule. Think of it as an evolutionary search where the model is the mutation operator.

The contrast that makes the experiment meaningful. Both share the same external contract with OEO (objective, initial skill, target model, permitted data and operations, budget, selection-data boundary, sealed final split) — so the comparison is fair on resources and evaluation. What differs is who controls the task-specific procedure, across seven dimensions the paper tabulates (Table 1): evidence scheduling, diagnosis, revision space, candidate retention, schedule/stopping, and which skill is returned. SkillOpt and GEPA hard-code these in different ways; OEO leaves all of them to the optimizer, which decides online when to inspect, run, revise, roll back to a checkpoint, or stop.

How to read the headline numbers. "12 wins, 1 tie, 1 narrow loss across 14 head-to-head comparisons" decomposes into 8 settings versus SkillOpt (7 wins, 1 tie) and 6 confirmatory settings versus GEPA (5 wins, 1 loss of 0.21 points). The "median 34.3%" figure is realized target-interaction tokens as a fraction of SkillOpt's configured budget — OEO had the same budget available and chose to stop earlier. Because the two comparators encode different edit spaces and search topologies, winning against both is stronger evidence than beating either alone.

One naming trap worth noting: the reference list contains several SkillOpt-family papers (SkillOpt-Lite, arXiv 2607.03451; SkillAudit, arXiv 2606.14239). The baseline here is the original SkillOpt (2605.23904) plus its official repo, not the Lite variant.
