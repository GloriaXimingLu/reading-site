Q&A: Darwin Gödel Machine

Session 2026-08-23

Q: In "Python repository powered by frozen, pretrained FMs" — what is FM?

A: Foundation model — the pretrained LLM the agent calls (Claude 3.5 Sonnet, o1, and so on). The paper uses the abbreviation throughout.

The word frozen is the load-bearing part. A DGM agent is a Python repository that makes API calls to a model whose weights never change; everything it evolves is the code around that model — tools, prompts, control flow, retry logic. The 20.0% → 50.0% gain on SWE-bench Verified involves no gradient steps at all: the same frozen model, wrapped in better scaffolding.

Two consequences that carry across the rest of the corpus:

  • It is what makes the archive cheap. A node in DGM's tree is a directory of Python, not a model checkpoint, so retaining every functioning ancestor indefinitely costs kilobytes. Contrast Harness-R1, which trains a 9B editor and consequently has no archive: its only memory across edits is the weights.
  • It bounds what "self-improvement" can mean here. DGM can discover that it should validate patches before submitting, or generate three candidates and rank them. It cannot become a better reasoner. The paper files "rewrite your own training script" as future work, which is roughly the boundary between harness optimization and the recursive self-improvement that Hyperagents and AIDE² probe.

One DGM-specific wrinkle: the diagnosis step calls a separate frozen FM (OpenAI o1), not the agent's own model. It is fed the agent's code, run logs, the GitHub issue, the predicted patch, and SWE-bench's private test patch, and returns a structured ticket. So "the agent diagnoses its own failure" is slightly generous — an external model reads the evidence and writes the instruction the agent then implements.

Q: "Analyzes its own benchmark evaluation logs, gets a proposed feature" — where do the logs and the proposed feature come from? Another analyzer model?

A: Two different sources, and yes, a second model is involved.

The logs are the agent's own, already on hand: every archived agent has been run against the benchmark to be scored, and that run produced trajectory logs, the patch it generated, and test results. Nothing extra is executed to obtain them.

The proposed feature comes from a separate frozen FM — OpenAI o1, not the agent's own model. It receives the agent's code, its run logs, the GitHub issue, the predicted patch, and SWE-bench's private test patch, and returns a five-field JSON: log_summarization, potential_improvements, one chosen improvement_proposal, an implementation_suggestion, and a problem_description written as a GitHub issue.

Only the last two fields reach the parent agent. It never sees the reasoning that selected the feature — it gets a ticket and an implementation hint, then does what it does for any other ticket. That framing is what makes self-modification tractable for a coding agent: it is indistinguishable from its ordinary work.

Two details:

  • The implementation hint is explicitly biased toward modifying an existing tool over inventing a new one, and the prompt ships a repo map (coding_agent.py, its forward() entry point, the tools/ contract) plus guardrails — tools must generalize across repositories, do not force tool usage, no while True loops.
  • The private test patch sits inside the diagnosis prompt. The authors flag the hard-coding risk and report no memorization on inspection, but this is why DGM earns only a partial mark on contamination.

The division of labour is therefore: parent agent as editor, frozen o1 as diagnostician, and neither is modifiable. That is precisely why DGM is partial rather than yes on recursion — and it is the step Hyperagents deletes, replacing the whole diagnosis stage with a one-line "modify any part of the codebase" instruction so the agent must invent its own analysis function, which it does.
