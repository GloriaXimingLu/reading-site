Q&A: Codex cross-session memory

Dedicated Codex memory tutorial

Session 2026-09-21

Q: Is this the same as Codex compaction?

A: No. Compaction shortens the active context of an unfinished task. Cross-session memory extracts evidence from prior eligible sessions and supplies useful context to later work. They can be used together and should be controlled separately in an experiment.

Q: Who actually writes memory?

A: In the audited V1 pipeline, a structured per-session model call produces a rollout summary and candidate raw memory. The program persists these in a database and materializes selected inputs as files. A separate internal consolidation agent updates the shared handbook, optional skills, and small summary/index. The ordinary solver retrieves from this library; it does not automatically edit the handbook after every reply.

Q: What does “raw memory” mean?

A: It is already an LLM-written extraction, not the original transcript. The original rollout, its Markdown recap, and its reusable raw-memory note are distinct objects.

Q: How are abstractions created?

A: The consolidation agent groups compatible tasks, preserves provenance and applicability, resolves supported changes, and writes reusable guidance. A recurring proven workflow may become a SKILL.md procedure. This is prompted editing of external text, not weight training or a separate formal abstraction algorithm.

Q: Is retrieval a vector search?

A: Not in the inspected local paths. V1 automatically supplies a small index and instructs the solver to select keywords, search MEMORY.md, and follow relevant pointers. The optional dedicated search backend uses substring matching, with paths and line numbers. The model interprets relevance and chooses subsequent reads.

Q: Does the writer see ground truth?

A: It receives filtered session evidence. Recorded tests, user corrections, and any answer information already exposed in that evidence can be visible. There is no additional gold-answer input. Hidden benchmark references must stay outside the writer's inputs unless the evaluation protocol explicitly allows them.

Q: Can the consolidator reopen the original session?

A: The audited consolidation prompt forbids it: consolidation uses staged raw notes, recaps, existing memory, and extension inputs. The V1 later-solver read prompt separately allows following rollout_path when exact evidence is needed.

Q: Which Codex version should we reproduce first?

A: The tutorial proposes V1 because its handbook/skill hierarchy matches the cross-session abstraction mechanism of interest. This is a starting hypothesis, not a performance claim. The same pinned checkout also includes V2, which consolidates per-session recaps into a compact summary with direct pointers and does not request the V1 handbook/skill layers. Keep the pipelines separate.

Q: Will enabling memories automatically train memory from benchmark codex exec runs?

A: Do not assume so. The audited native candidate filter accepts interactive sources, not the Exec source. A benchmark port needs explicit ingestion, a defined post-task feedback policy, and a completed-consolidation barrier before later evaluation uses the snapshot.
